## 债券/行业上攻排查结论（v4.0）

用户要求排查债券上攻、行业上攻是否存在同样问题。实测结论：

### 债券上攻：潜在风险存在，但当前未触发
- **数据流**：`attack-ranking/bond` → `_enrich_bond_data` → `_get_bond_change_pct_batch` → Redis优先，未命中走 `_get_bond_change_pct_from_mysql`
- **MySQL SQL 写死字段**：`bond_code, change_pct, price, amount, min1_change_pct, min1_amount`（monitor.py 第775行）
- **实测**：8个交易日的 `monitor_zq_sssj_*` 表这些字段**都存在**（当前未触发崩溃）
- **⚠️ 隐患**：债券表列数波动很大（28~38列），同样是"建表时机决定列结构"。若某天建表异常导致上述 SQL 字段缺失，`_get_bond_change_pct_from_mysql` 会**同样崩溃**（写死字段，零容错）
- **结论**：**债券路径有与股票相同的脆弱性**，虽当前未触发，但应一并加固

### 行业上攻：风险低
- **数据流**：`data_service.get_ranking_at_time` industry分支 → Redis优先，MySQL fallback
- **MySQL SQL**：只查 `code, name, count, industry_cumulative_main_net`，**不涉及派生字段**
- **实测**：`monitor_hy_top30_*` 表列数稳定（15列）
- **结论**：**行业路径无此问题**，无需修改

### 排查汇总表

| 上攻类型 | 数据流 | 是否写死派生字段 | 当前是否触发 | 需否加固 |
|---------|--------|-----------------|-------------|---------|
| **股票** | `_get_change_pct_and_main_net_batch` MySQL路径 | ✅ 写死(含consecutive_attacks) | ✅ 已触发(20260727) | **必须** |
| **债券** | `_get_bond_change_pct_from_mysql` | ✅ 写死(6个字段) | ❌ 未触发(字段恰好都在) | **建议** |

## 零、consecutive_attacks 字段溯源（v3.0，回答用户三问）

### 问1：这个字段干什么用的？

**`consecutive_attacks`（连续上攻次数）**：
- **定义位置**：`monitor_derived_fields.py` 的 `DERIVED_FIELDS` 注册表
- **计算逻辑**：`(prev + 1) if in_top30 else 0`
  - 若该股票当前 tick 进入 top30 上攻榜 → 在上一 tick 值上 +1
  - 若跌出 top30 → 归零
- **业务含义**：衡量一只股票**连续多少个 tick 停留在上攻榜**，反映"持续上攻强度"
- **数据特征**：极稀疏。实测 20260724 全天 1911万条记录中仅 13215 条 >0（0.07%），最大值23

### 问2：什么时候取消了这个字段？

**从未被取消。** Git 历史实测：
- **6d0f82b (2026-05-12)**：`feat: 派生字段引擎+连续上攻次数` — 字段引入
- 此后代码中 `DERIVED_FIELDS`、`DERIVED_DISPLAY_FIELDS` 一直保留该字段，**无任何删除提交**
- 20260716~20260724 共7个交易日的表**都有该列且有数据**

**结论**：不是"取消了字段"，而是 **20260727 那天该列压根没建起来**。

### 问3：为什么偏偏 20260727 缺列？（真正原因：建表时机异常）

**实测关键证据 —— 建表时间对比**：

| 日期 | 建表时间 | consecutive_attacks | 最早非0数据 |
|------|----------|--------------------|--------|
| 20260724（正常）| **09:25:00** | ✅ 有列，13215条非0 | 09:30:03 |
| **20260727（缺列）** | **09:29:19** | ❌ 无列 | — |

**机制解释**：
1. sssj 表由**首个 tick 的 `to_sql(if_exists='append')` 自动建表**，表结构（列）由**首个 tick 写入的 DataFrame 决定**。
2. 之后 `_ensure_mysql_columns` 仅在"DataFrame 出现新列"时才 `ALTER TABLE ADD COLUMN`。
3. 派生字段（`consecutive_attacks`）通过 df_prev_main 从 Redis 加载时携带、随主流程延续写入——**依赖 09:25 集合竞价起就正常运转的链条**。

**20260727 的异常**：
- 正常应 **09:25:00 建表**（如 07-24），但 07-27 建表时间是 **09:29:19**，晚了 4 分钟
- 说明当天 **monitor_stock 启动晚了 / 重启了 / 错过了 09:25 集合竞价首 tick**
- 首个 tick 建表时的 DataFrame **恰好不含 consecutive_attacks 列** → 表建成 23 列（缺该列）
- 此后派生字段延续链条断裂，`_ensure_mysql_columns` 也未再补列 → **该列全天缺失**

**一句话**：字段没被取消，是 **20260727 那天 monitor_stock 启动异常（09:29才建表，错过09:25），导致建表时 DataFrame 缺 consecutive_attacks 列，此后一直缺。这是偶发的启动时序问题。**

## 一、关键线索（用户反馈，推翻v1.0结论）

用户指出：**同一天 07-27，09:50:15 全为0，但 14:10:54 各字段又都有值，且代码没改过。**

这直接推翻了 v1.0 的"表缺列导致SQL崩溃"单一结论——**如果表真缺列，无论查哪个时间点，SQL都会报同样的错**，14:10:54 也该失败。但它没有。

**说明存在两条不同的代码路径，只有一条会因缺列崩溃。**

---

## 二、真正的根因（已实测决定性验证）

### 双路径机制

`_get_change_pct_and_main_net_batch()`（monitor.py 约1460-1520行）有**两条数据获取路径**：

```
时间轴点击 → /attack-ranking/stock?time=xxx → _enrich_change_pct_and_main_net
          → _get_change_pct_and_main_net_batch(date, time_str, codes)
          ├─ 路径1：get_cached_sssj_df(redis_key)  ← Redis/内存缓存命中
          │         用 _extract_all_vectorized 逐字段提取
          │         【关键】if 'xxx' in df.columns 判断 → 缺列自动跳过，不崩溃 ✅
          │
          └─ 路径2：Redis未命中 → 查 MySQL
                    SELECT stock_code, change_pct, cumulative_main_net,
                           consecutive_attacks, ...  ← 写死字段名
                    【关键】一个字段不存在 → 整条SQL崩溃 → except → 全为0 ❌
```

### 实测决定性证据

对 20260727 的两个时间点实测 `get_cached_sssj_df`：

| 时间点 | Redis缓存 | 走的路径 | consecutive_attacks列 | 结果 |
|--------|-----------|----------|----------------------|------|
| **09:50:15** | ❌ **MISS** | 路径2：查MySQL | 表中缺失 | **SQL崩溃 → 全为0** |
| **14:10:54** | ✅ **HIT（5332行）** | 路径1：Redis DataFrame | 缓存中也缺，但**逐字段判断跳过** | **正常显示** |

```
[09:50:15] cache MISS -> MySQL path -> CRASH on missing column
[14:10:54] cache HIT, rows=5332, has consecutive_attacks col=False -> 正常(向量化提取自动跳过缺失列)
```

### 为什么两个时间点缓存命中不同？

- Redis 缓存（`get_cached_sssj_df`）只保留**近期/被访问过的时间点**，有淘汰机制
- 14:10:54 恰好还在缓存中（可能刚被访问过或较新）
- 09:50:15 已被淘汰/未缓存 → 只能查 MySQL → 撞上缺列

**这就是"同一天不同时间一个有值一个没值"的真相**，且**代码确实没改过**——纯粹是缓存命中与否决定走哪条路径。

## 三、三重根因总结（v3.0 更新）

问题是**三个因素叠加**才触发：

| 因素 | 说明 | 角色 |
|------|------|------|
| **因素1：启动时序异常** | 20260727 建表晚4分钟（09:29 vs 正常09:25），错过集合竞价首tick，建表时DataFrame缺consecutive_attacks列 | 偶发导火索（数据缺陷来源）|
| **因素2：建表结构依赖首tick** | sssj表列由首个tick的df决定，首tick缺列则该列全天缺失，`_ensure_mysql_columns`未能补回 | 数据层脆弱性 |
| **因素3：MySQL路径写死字段名，零容错** | SQL把派生字段直接拼进SELECT，一个不存在就整条崩溃；与Redis路径（逐字段判断）容错能力不一致 | **代码层真正根因** |

**关键洞察**：
- 因素1是偶发的（启动时序），因素2让偶发变成"全天数据缺陷"
- **因素3才是最该修的**——即使表偶发缺列，只要 MySQL 路径像 Redis 路径一样容错，用户就不会看到"全为0"。因素3把一个小的数据缺陷放大成了用户可见的严重故障。

## 四、解决方案（v3.0 更新为三层）

### 方案A：统一两条路径的容错能力（治本·最高优先级，强烈推荐）

**目标**：让 MySQL 路径也像 Redis 路径一样，缺字段自动跳过而非崩溃。**这是最该修的**——根治"因素3"。

**改动点**：`_get_change_pct_and_main_net_batch()` 的 MySQL 查询（monitor.py 约1509行）

**方案A-1：查询前检测表实际字段（推荐）**
```python
# 查询前检测表有哪些列（可缓存，开销极小）
existing_cols = _get_table_columns(table_name)  # SHOW COLUMNS，带缓存
safe_derived = [f for f in DERIVED_DISPLAY_FIELDS if f in existing_cols]
base_cols = ['stock_code', 'change_pct', 'cumulative_main_net', 'price']
select_cols = base_cols + safe_derived
query = f"SELECT {', '.join(select_cols)} FROM {table_name} WHERE ..."
# 结果中缺失的派生字段用默认0填充（与Redis路径行为一致）
```
- **优点**：两条路径行为完全一致，缺任何字段都不崩，核心字段永远拿得到；一劳永逸
- **缺点**：每次多一次列检测（缓存后几乎无开销）

**方案A-2：SQL异常降级**
```python
try:
    # 完整查询
except OperationalError:
    # 降级：只查核心字段，派生字段填0
    query = "SELECT stock_code, change_pct, cumulative_main_net, price FROM ..."
```
- **优点**：改动最小
- **缺点**：靠异常兜底不够优雅；降级后派生字段全丢（不如A-1精准）

### 方案B：补 20260727 表的缺失列（治标·修历史数据）

```sql
ALTER TABLE monitor_gp_sssj_20260727 ADD COLUMN consecutive_attacks FLOAT DEFAULT 0;
```
- **优点**：立即让 09:50:15（及所有已淘汰缓存的时间点）恢复正常
- **缺点**：只补列不补值（历史值无法回算，填0；该字段极稀疏，影响极小）

### 方案C：预防建表缺列（治本·防因素1/2，可选）

**目标**：确保建表时表结构完整，不依赖"首个tick恰好带全字段"。

**方案C-1：建表后主动确保派生字段列存在**
```python
# 在 _async_precheck_table_schema 或首次写表后，主动ALTER补齐所有已知派生字段
for fname in DERIVED_DISPLAY_FIELDS:
    if fname not in existing_cols:
        conn.execute(f"ALTER TABLE {table} ADD COLUMN `{fname}` FLOAT DEFAULT 0")
```
- **优点**：无论启动时序如何，表结构始终完整，从源头杜绝
- **缺点**：需改建表逻辑（改动稍大，需测试）

## 五、我的倾向（v3.0 更新）

| 决策 | 倾向 | 理由 |
|------|------|------|
| 治本（代码）| **方案A-1（检测字段）·必做** | 根治因素3，让MySQL路径与Redis路径统一容错，一劳永逸，优先级最高 |
| 治标（数据）| **方案B（补列）·建议做** | 立即修复20260727；填0影响极小 |

**推荐组合**：**A-1（必做）+ B（建议）**，C-1 作为可选加固。

**一句话**：最该修的是"因素3——MySQL路径零容错"。做A-1让两条路径统一容错（治本，即使以后再偶发缺列也不会全为0），再做B补眼前数据。C-1从建表源头杜绝，可作为后续加固。
