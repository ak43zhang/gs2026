# 上攻排行"除次数外全为0"问题诊断与解决方案

> **版本**: v1.0  
> **日期**: 2026-07-28  
> **状态**: 待审核  
> **问题**: 2026-07-27 点击时间轴 09:50:15，股票上攻排行除"次数"外，涨跌幅/主力净额/价格等全部显示为 0

---

## 一、问题现象

用户点击时间轴 09:50:15，股票上攻排行表格：
- ✅ **次数（count）**：正常显示
- ❌ **涨跌幅（change_pct）**：显示 `-`
- ❌ **主力净额（main_net_amount / cumulative_main_net）**：显示 0
- ❌ **价格（price）**：显示 `-`
- ❌ **连续攻击/主力次数/峰值净额等派生字段**：全部 0

---

## 二、根因定位（已通过实测确认）

### 数据流梳理
时间轴点击 → `/api/monitor/attack-ranking/stock?time=09:50:15` → 三步组装：
1. `_get_ranking_fast()` → 返回 **count（次数）** ← 独立函数，正常 ✅
2. `_enrich_stock_data()` → 补充债券/行业信息
3. `_enrich_change_pct_and_main_net()` → 补充**涨跌幅/主力净额/派生字段** ← **问题在这里** ❌

### 核心根因：一个缺失字段拖垮整条 SQL

`_get_change_pct_and_main_net_batch()`（monitor.py 第1509行）执行的 SQL：

```sql
SELECT stock_code, change_pct, cumulative_main_net, 
       consecutive_attacks,          -- ← 该字段在 20260727 表中不存在
       main_net_count, max_cumulative_main_net, price
FROM monitor_gp_sssj_20260727
WHERE time = '09:50:15' AND stock_code IN (...)
```

**实测报错**：
```
(pymysql.err.OperationalError) (1054, "Unknown column 'consecutive_attacks' in 'field list'")
```

**连锁反应**：
- SQL 整条执行，一个字段不存在 → **整条查询崩溃**
- 触发 `except` 分支 → 所有股票 `change_pct='-'`, `main_net_amount=0`
- 而 count 来自另一个正常函数，所以"次数"幸免

### 为什么偏偏 20260727 缺这个字段？

**实测对比 8 个交易日的 sssj 表结构**：

| 表 | consecutive_attacks | 总列数 |
|----|--------------------|--------|
| monitor_gp_sssj_20260716 | ✅ 有 | 24 |
| monitor_gp_sssj_20260717 | ✅ 有 | 24 |
| monitor_gp_sssj_20260720~24 | ✅ 有 | 24 |
| **monitor_gp_sssj_20260727** | ❌ **缺失** | **23** |

**只有 20260727 少了这一列。**

### 深层原因

1. `consecutive_attacks` 是派生字段（monitor_derived_fields.py 定义），由 `calculate_all_derived()` 计算后随 DataFrame 写入 sssj 表。
2. 建列机制 `_ensure_mysql_columns()`（monitor_stock.py 第1926行）：**基于 `df.columns` 判断**，DataFrame 有该列才 `ALTER TABLE ADD COLUMN`。
3. 实测 20260727 的 `main_net_count`、`max_cumulative_main_net`、`cumulative_main_net` **都有正常数据**（派生计算当天跑了），唯独 `consecutive_attacks` 列没建成。
4. **推断**：当天 monitor_stock 启动/首次写表时，DataFrame 中缺少 `consecutive_attacks` 列（可能派生计算初始化时序问题，或首批 tick 该字段未产出），导致 to_sql 建表时未含此列；后续即便产出该列，若写入路径未再触发 `_ensure_mysql_columns` 补列，则该列一直缺失。

> **注**：当天进程运行时的具体状态已无法回溯，但**数据事实明确**——该表缺列，且这是历史偶发问题（其他天都正常）。

---

## 三、问题本质：代码脆弱性

**真正的隐患不是"某天缺个字段"，而是代码对字段缺失零容错**：

- 一个可选派生字段（`consecutive_attacks`，本身大部分为0，20260724 仅17只非0）缺失
- 却导致 change_pct、cumulative_main_net 等**核心字段全部连坐归零**
- 用户看到的是"整行数据都没了"，而实际上核心数据在表里是好的（实测 002580 cum=7871万、000428 cum=822万都在）

---

## 四、解决方案（两层）

### 方案A：修复代码健壮性（治本，推荐）

**目标**：字段缺失时优雅降级，不让一个字段拖垮整条查询。

**改动点**：`_get_change_pct_and_main_net_batch()`（monitor.py 约1509行）

**方案A-1：动态检测存在的字段（推荐）**
```python
# 查询前先检测表实际有哪些字段
existing_cols = _get_table_columns(table_name)  # SHOW COLUMNS 或 information_schema
# 只查存在的派生字段
safe_derived = [f for f in DERIVED_DISPLAY_FIELDS if f in existing_cols]
select_cols = ['stock_code', 'change_pct', 'cumulative_main_net', 'price'] + safe_derived
# 缺失的字段在结果中用默认值0填充
query = f"SELECT {', '.join(select_cols)} FROM {table_name} WHERE ..."
```
- **优点**：彻底健壮，任何字段缺失都不崩；核心字段永远能拿到
- **缺点**：每次多一次列检测（可缓存，开销极小）

**方案A-2：SQL 容错（try 逐字段降级）**
```python
try:
    # 完整查询
except OperationalError:
    # 降级：去掉派生字段，只查核心字段
    query = "SELECT stock_code, change_pct, cumulative_main_net, price FROM ..."
```
- **优点**：改动小
- **缺点**：靠异常兜底，不够优雅；降级后派生字段全丢

### 方案B：修复 20260727 表数据（治标，补历史）

**目标**：给 20260727 表补上 `consecutive_attacks` 列。

```sql
ALTER TABLE monitor_gp_sssj_20260727 
ADD COLUMN consecutive_attacks FLOAT DEFAULT 0;
```
- **优点**：立即让 20260727 恢复正常显示
- **缺点**：
  - 只补列不补值（历史 tick 的 consecutive_attacks 已无法精确回算，只能填默认0）
  - 治标不治本，未来若再发生建表异常，同样问题会复现
- **数据影响评估**：`consecutive_attacks` 本身极稀疏（正常日仅17只非0），填0对整体展示影响很小，核心字段（涨跌幅/主力净额）修复后立即正常

## 五、我的倾向

| 决策 | 倾向 | 理由 |
|------|------|------|
| 治本 | **方案A-1（动态检测字段）** | 彻底解决"字段缺失连坐"的脆弱性，一劳永逸 |
| 治标 | **方案B（补列）** | 让 20260727 立即恢复；consecutive_attacks 填0影响极小 |
| 组合 | **A-1 + B 都做** | A-1 保证未来任何字段缺失都不崩；B 修复眼前的历史数据 |

**一句话**：先做方案A-1（动态检测字段，彻底健壮化查询），再做方案B（给20260727补列）。A-1保证以后不再复发，B修复眼前。
