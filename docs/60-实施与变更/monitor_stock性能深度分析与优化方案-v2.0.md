## 二、你的感受 vs 真实数据

### 你的感受
> "补齐操作效率很慢，每tick执行时间长了很多；主力计算有时候耗时挺长"

### 数据验证

| 你的感受 | 数据结论 | 真相 |
|----------|----------|------|
| 补齐操作慢 | 补齐本身用向量化(isin+concat)，**不慢** | ❌ 补齐不是瓶颈 |
| 每tick变长 | 平均2118ms，比纯采集(632ms)确实多 | ✅ 但主因是恢复+主力查询 |
| 主力有时很慢 | 主力最大4118ms，5%超1秒 | ✅ **偶发尖峰属实** |

### 关键澄清：补齐操作为什么让你"感觉"慢？

补齐操作（`_fill_missing_stocks`）本身**很快**（向量化），但它触发的**连锁效应**：
- 补齐后 df_now 行数增加
- 后续所有阶段（主力计算、衍生字段、保存）处理的行数变多
- **感觉上**是补齐导致慢，**实际上**是补齐后的下游处理

## 三、真正的性能问题定位

### 问题1：恢复阶段重复Redis查询 🔴

**现象**：`_get_cached_prev_main` 在一个tick内被调用**2次**
- 行3031（阶段3）：用于恢复无效+补齐漏采
- 行3171（阶段5）：用于主力净额计算

**分析**：
- 两次参数相同（`sssj_table, time_full`）
- 理论上第2次应 L1 内存命中（TickStateCache）
- **但阶段3和阶段5之间，df_prev被重新赋值**（行3156用 `load_dataframe_by_offset`）
- 需要确认 L1 缓存是否真的命中，还是又查了一次Redis

**优化**：确保同tick内复用，避免重复查询。

### 问题2：主力计算的尖峰（偶发4118ms）🟡

**现象**：主力平均524ms，但最大4118ms

**根因**（代码已向量化，尖峰来自）：
- `pd.merge`（df_now × df_prev_main，5000行内连接）
- `pd.to_numeric` 转换（df_prev_main来自MySQL时是Decimal）
- Redis查询 df_prev_main 本身的波动

**优化**：merge优化 + 减少类型转换。

### 问题3：采集尖峰（最大2661ms）🟡

**现象**：采集平均632ms，最大2661ms

**根因**：网络IO波动（通达信接口），非代码问题

**优化**：已有超时控制（FETCH_TIMEOUT=2.5s），A-4已去重试。可考虑并发数调优。

### 问题4：清洗阶段偶发（最大808ms）🟢

**现象**：清洗平均161ms，最大808ms

**根因**：`normalize_stock_dataframe` 全量清洗5000行

**优化**：优先级低，收益有限。

## 四、优化方案

### 方案B-1：消除恢复阶段重复查询 🔴（收益最大）

**问题**：同tick内 `_get_cached_prev_main` 调用2次

**当前代码**：
```python
# 阶段3 行3031
df_prev = _get_cached_prev_main(sssj_table, time_full, date_str)
# ... 用df_prev恢复无效+补齐漏采

# 阶段5 行3156（df_prev被覆盖）
df_prev = redis_util.load_dataframe_by_offset(sssj_table, offset=...)

# 阶段5 行3171（又查一次）
df_prev_main = _get_cached_prev_main(sssj_table, time_full, date_str)
```

**优化**：阶段3的 `df_prev`（来自缓存）就是 `df_prev_main`，直接复用：
```python
# 阶段3：获取一次，保存引用
df_prev_cached = _get_cached_prev_main(sssj_table, time_full, date_str)
df_prev = df_prev_cached  # 用于恢复+补齐

# 阶段5：直接复用，不再查询
df_prev_main = df_prev_cached  # ← 复用，省一次Redis/MySQL查询
```

**预期收益**：恢复阶段省 ~150-300ms（尤其L1未命中时）

**风险**：需确认阶段3和阶段5对df_prev的用途一致（都是上一tick主力数据）

### 方案B-2：主力计算merge优化 🟡

**问题**：`pd.merge` 5000行内连接 + 类型转换

**优化点1**：merge前只选必要列（已做）

**优化点2**：类型转换提前到清洗阶段，避免主力阶段重复转换
```python
# 当前：主力阶段转换df_prev_main
df_prev_main['cumulative_main_net'] = pd.to_numeric(...)

# 优化：在_get_cached_prev_main返回时就保证是float
# 或在L2/L3恢复时统一转换一次，缓存float版本
```

**优化点3**：用 `set_index` + `join` 替代 merge（大表更快）
```python
# merge → index join（stock_code作索引）
df_now_idx = df_now.set_index('stock_code')
df_prev_idx = df_prev_main.set_index('stock_code')
merged = df_now_idx.join(df_prev_idx, rsuffix='_prev', how='inner')
```

**预期收益**：主力常态省 ~50-100ms，尖峰省 ~200-500ms

### 方案B-3：采集并发调优 🟡

**当前**：BATCH_SIZE=400, MAX_WORKERS=13

**分析**：5000股票 / 400 = 13批，正好13线程并发

**优化**：可尝试 BATCH_SIZE=300, MAX_WORKERS=17（更细粒度，减少单批阻塞）

**预期收益**：采集尖峰可能降低，需实测

**风险**：并发过高可能触发接口限流，需谨慎

### 方案B-4：清洗阶段跳过不变列 🟢

**优先级低**，收益有限，暂不推荐。

## 五、方案优先级与预期

| 方案 | 优先级 | 改动风险 | 预期收益 | 推荐 |
|------|--------|----------|----------|------|
| **B-1 消除重复查询** | 🔴 高 | 低 | 省150-300ms | ✅ **首选** |
| **B-2 merge优化** | 🟡 中 | 中 | 省50-100ms(常态) | ✅ 推荐 |
| **B-3 采集调优** | 🟡 中 | 中 | 不确定 | ⚠️ 需实测 |
| **B-4 清洗优化** | 🟢 低 | 低 | 有限 | ❌ 暂不 |

### 综合预期

- **B-1 + B-2**：Tick平均 2118ms → **1800~1900ms**
- 超3秒比例：14% → **可能降至 8~10%**
- 主力尖峰：4118ms → **可能降至 3000ms以内**

## 六、重要提醒（客观判断）

### 6.1 当前性能其实"可接受"

- **中位2046ms < 3秒**——常态没问题
- 超3秒仅14%，是偶发尖峰（采集+恢复+主力同时波动）
- **不是代码写得差，是IO波动叠加**

### 6.2 优化的边际收益递减

- 主力计算**已经向量化**（A系列优化过）
- 补齐操作**已经向量化**
- 保存**已经异步**
- 剩余优化空间主要在"消除重复查询"和"merge微调"

### 6.3 最大的不可控因素是采集

- 采集最大2661ms，是网络IO
- 代码层面能做的有限（已有超时+去重试）
- **这部分不是优化重点**
