# 股债联动卡片：新增债券涨跌幅 + 出现次数 + 查询性能优化

> 日期：2026-08-10  
> 状态：已审核，待实施  
> 关联功能：`monitor_gp_zq_rising_signal.py` — 实时监控股票债券上涨信号  
> 前端位置：数据监控页面右上角「🔗 股债联动」卡片

---

## 一、背景

股债联动卡片实时展示「正股 + 对应可转债」同时上涨的信号。当前展示字段为：

| 展示字段 | 来源 | 状态 |
|----------|------|------|
| 时间 | 数据库 | ✅ |
| 转债代码/名称 | 数据库 | ✅ |
| 转债价格 | 前端计算（buy_price/sell_price） | ✅ |
| 正股代码/名称 | 数据库 | ✅ |

**缺失字段**：
1. **债券涨跌幅** — 用户需要看到命中瞬间债券的涨跌幅
2. **出现次数** — 同一转债当天连续命中的次数（前端计算）

**性能问题**：
- `monitor_combine` 表无主键、无索引
- Redis 路径 18 次独立 `load_dataframe_by_key` 查询
- MySQL 回退路径 `ORDER BY time DESC` 全表排序

## 三、问题根因

### 3.1 债券涨跌幅未展示

`get_combine_ranking` 方法（`data_service.py:1002`）构建返回 dict 时，**只取了 `price_now_zq`、`zf_30`、`zf_30_zq`，跳过了 `change_pct_now_zq`**。前端自然拿不到。

### 3.2 出现次数未展示

后端 `monitor_gp_zq_rising_signal.py` 写入数据时**没有 `combo_count` 字段**。每次命中都新增一条记录，不做累计计数。

### 3.3 查询慢的原因

| 瓶颈 | 具体表现 | 影响 |
|------|----------|------|
| **无主键** | MySQL `ORDER BY time DESC` 全表排序 | 每次查询全表扫描 |
| **无索引** | `_get_combine_count` 也是全表 COUNT | check_change 也慢 |
| **Redis 18次独立查询** | 每个时间戳一次 `load_dataframe_by_key`，循环 + 解压 | 18 次 RTT |
| **无去重优化** | 前端/后端都有去重逻辑，但 Redis 路径逐条处理 | 放大循环开销 |

## 四、修改方案

### 4.1 新增债券涨跌幅

| 位置 | 改动 |
|------|------|
| `data_service.py:get_combine_ranking` | Redis 路径：从 row 取 `change_pct_now_zq` 加入 record dict |
| `data_service.py:get_combine_ranking` | MySQL 路径：SELECT 加 `change_pct_now_zq`，record dict 加该字段 |
| `monitor.html:renderCombineSignal` | 第二行展示债券涨跌幅，红绿色 |

### 4.2 新增出现次数（前端计算）

| 位置 | 改动 |
|------|------|
| `monitor.html:renderCombineSignal` | 用 Map 按 `item.code`（转债代码）计数，展示 `N次` |

**算法**：
```js
const countMap = {};
data.forEach(item => {
    const key = item.code || '';
    countMap[key] = (countMap[key] || 0) + 1;
});
// 渲染时：
const count = countMap[item.code] || 1;
html += `... <span class="combine-count">${count}次</span> ...`;
```

### 4.3 查询性能优化

| # | 优化项 | 实现 | 文件 |
|---|--------|------|------|
| 1 | **加主键** | `ALTER TABLE monitor_combine_{date} ADD PRIMARY KEY (time, code)` | `monitor_gp_zq_rising_signal.py` 建表逻辑 |
| 2 | **Redis Pipeline** | 用 `pipeline()` 批量 `GET`，替代 18 次独立 `load_dataframe_by_key` | `data_service.py` |
| 3 | **MySQL 加 time 索引** | `ALTER TABLE monitor_combine_{date} ADD INDEX idx_time(time)` | 建表逻辑 + 存量表迁移 |

## 六、风险评估

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| ALTER TABLE 锁表 | 低 | 148 行瞬间完成，不阻塞 |
| Pipeline 兼容性 | 低 | load_dataframe_by_key 底层也是 GET，Pipeline 只是批量化 |
| 出现次数计数偏差 | 低 | 已去重（seen_keys），同一 code+time 只出现一次 |
| 主键冲突（同时间同code） | 极低 | 数据源去重保证不会出现 |
