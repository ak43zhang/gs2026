# ========================================

## 一、需求背景

**用户需求**：调度中心设置的任务，即使 app.py 不启动也可以调度，改成 Windows 调度模式。

## 二、当前调度中心实现

### 2.1 组件构成

```
scheduler.py           (路由层) - API接口
scheduler_service.py   (服务层) - APScheduler调度逻辑
scheduler.html         (页面)   - 前端界面
scheduler.js           (脚本)   - 前端逻辑
create_scheduler_tables.sql     - 数据库表
```

### 2.2 当前调度流程

```
1. 用户访问调度中心页面
2. 用户点击"启动调度器"按钮
3. 调用 POST /api/scheduler/start
4. scheduler_service.start() 启动 APScheduler
5. APScheduler 从 MySQL 加载 enabled 任务
6. 任务在后台线程按触发器执行
7. 执行结果写入 MySQL
```

### 2.3 核心问题

| 问题 | 说明 |
|------|------|
| 依赖app.py | 调度器是dashboard2的Blueprint，必须在Flask app内启动 |
| 手动启动 | 需要用户点击"启动"或调用API，不能自动运行 |
| 进程绑定 | app.py停止 → 调度器停止 → 所有任务中断 |
| 无持久化调度 | 没有独立的Windows服务，不能开机自启 |

## 三、v1.0 方案：Windows服务化

### 3.1 方案对比

| 方案 | 描述 | 优点 | 缺点 | 推荐 |
|------|------|------|------|------|
| A. Windows服务 | 用pywin32创建Windows服务 | 标准方案，开机自启，稳定 | Windows专用，需管理员权限 | ✅ 首选 |
| B. 计划任务 | Windows Task Scheduler | 无需代码改动，配置简单 | 粒度粗，不适合高频任务 | 备选 |
| C. 独立进程 | pythonw.exe后台运行 | 简单，跨平台 | 无自启，需手动管理 | 不推荐 |
| D. nssm | 用nssm包装成服务 | 简单，无需改代码 | 依赖外部工具 | 备选 |

### 3.2 核心组件（v1.0设计）

- `scheduler_daemon.py`：Windows服务包装脚本（pywin32）
- `install_scheduler_service.bat`：安装脚本
- `manage_scheduler.bat`：管理工具（安装/卸载/启停/状态）
- 修改 `scheduler.py`：移除start/stop，改为查询服务状态

> **注**：v1.0的详细代码在 v3.0 中已重构完善，见 v3.0 章节。

## 一、v2.0 补充：调度链设计与完整数据流

### 1.1 用户场景

| 场景 | 需求 |
|------|------|
| 简单定时 | A进程每周五执行，app.py不启动也能跑 |
| 调度链 | A→B→C依赖执行 |
| 混合调度 | 独立任务 + 调度链并存 |

### 1.2 当前调度链已实现功能

```python
# scheduler_service.py 已实现:
- _execute_chain_job()   # 执行链
- _trigger_next_jobs()   # 触发子任务
- chain_condition:       # 触发条件
    'always'      # 总是触发
    'on_success'  # 成功时触发（默认）
    'on_failure'  # 失败时触发
- next_job_ids           # 下一个任务ID列表
```

### 1.3 当前调度链数据模型

```sql
-- scheduler_jobs 表
job_id           VARCHAR(64)  主键
job_name         VARCHAR(128)
job_type         VARCHAR(32)  -- 'chain' 表示调度链
job_config       JSON        -- 链配置: {"steps": [...]}
trigger_type     VARCHAR(32)  -- 'cron'
trigger_config   JSON        -- {"hour": 9, "minute": 30, "day_of_week": "fri"}
next_job_ids     JSON        -- 链式: ["b", "c"]
chain_condition  VARCHAR(32)  -- 'on_success'
status           VARCHAR(32)  -- 'enabled'
```

### 1.4 当前调度链执行流程

```
1. 触发器触发调度链任务
2. _execute_chain_job() 依次执行 steps
3. 每个 step 执行完成
4. _trigger_next_jobs() 检查 chain_condition
5. 条件满足则调度 next_job_ids
6. 子任务延迟2秒执行（避免阻塞）
```

### 1.5 v2.0 关键问题解答

| 问题 | 答案 |

| app.py不启动能调度吗？ | v2.0设计目标：能（需Windows服务化）|
| 前端设置后立即生效吗？ | 需要变更检测机制（v3.0细化）|
| 调度链A→B→C如何确保顺序？ | 串行执行，同步等待（v3.0细化）|

## 一、【核心原理】前端设置如何生效？（重点解答疑惑）

### 1.1 当前代码的致命问题

**你的疑惑**："前端设置后，读MySQL的是Windows独立运行的服务吗？还是只有app.py执行时MySQL配置才生效？"

**答案**：**当前代码架构下，只有app.py执行时MySQL配置才生效！** 这正是需要改造的核心问题。

### 1.2 为什么？（代码级证据）

#### 证据1：调度器是单例，绑定在进程内

```python
# scheduler_service.py 行814
scheduler_service = SchedulerService()  # 全局单例

# 关键：这个单例是"谁import它，就在谁的进程里"
# - app.py import → 单例在app.py进程
# - Windows服务 import → 单例在服务进程
# 两个进程的单例是【完全独立】的两个实例！
```

#### 证据2：APScheduler用的是内存JobStore（无持久化）

```python
# scheduler_service.py 行92-99
self.scheduler = BackgroundScheduler(
    timezone='Asia/Shanghai',
    job_defaults={...}
    # ❌ 没有配置 jobstore！默认使用 MemoryJobStore
)
```

**MemoryJobStore的含义**：
- 任务调度信息**只存在内存**
- 进程重启 → 内存清空 → 调度信息丢失
- 只能靠 `_load_jobs_from_db()` 重新从MySQL加载

#### 证据3：前端add_job的实际行为

```python
# scheduler_service.py 行652-691
def add_job(self, job_config: Dict) -> str:
    # 1. 写入MySQL（这一步持久化了）
    execute_update(sql, (...))
    
    # 2. 添加到【当前进程的】APScheduler
    if job_config.get('status') == 'enabled':
        self._add_job_to_scheduler(job[0])  # ← 关键！
    
    return job_id
```

**关键问题**：
- `self._add_job_to_scheduler()` 添加到的是**app.py进程内的scheduler**
- 因为前端API请求由**app.py处理**，所以`self`是app.py进程的单例
- **Windows服务进程的scheduler对此一无所知！**

### 1.3 当前架构的数据流（问题所在）

```
前端创建任务
    │
    ▼ POST /api/scheduler/jobs （app.py处理）
┌─────────────────────────────────────┐
│  app.py 进程                         │
│  ┌─────────────────────────────────┐ │
│  │ scheduler_service (单例A)       │ │
│  │ - 写入MySQL ✅                  │ │
│  │ - add到自己的APScheduler ✅     │ │  ← 只有app.py进程知道
│  └─────────────────────────────────┘ │
└─────────────────────────────────────┘

    如果同时有Windows服务进程:
┌─────────────────────────────────────┐
│  Windows服务 进程                    │
│  ┌─────────────────────────────────┐ │
│  │ scheduler_service (单例B)       │ │
│  │ - APScheduler ❌ 不知道新任务   │ │  ← 完全独立，不知道app.py加的任务
│  └─────────────────────────────────┘ │
└─────────────────────────────────────┘
```

**结论**：
- 当前：前端设置 → app.py进程的scheduler生效 → **app.py停止则调度停止**
- Windows服务如果直接跑，**看不到前端通过app.py添加的任务**（除非重启重新加载MySQL）

### 1.4 改造后的正确架构（解决方案）

```
前端创建任务
    │
    ▼ POST /api/scheduler/jobs （app.py处理）
┌─────────────────────────────────────┐
│  app.py 进程（只负责写MySQL）        │
│  - 写入MySQL ✅                      │
│  - 不再add到自己的scheduler ❌       │  ← 改造：app.py不调度
└─────────────────────────────────────┘
    │
    ▼ 写入 scheduler_jobs + 变更通知
┌─────────────────────────────────────┐
│  MySQL（唯一数据源）                 │
│  - scheduler_jobs（任务配置）        │
│  - scheduler_reload_signal（变更信号）│
└─────────────────────────────────────┘
    │
    ▼ 轮询检测（每30秒）
┌─────────────────────────────────────┐
│  Windows服务 进程（唯一调度者）      │
│  ┌─────────────────────────────────┐ │
│  │ scheduler_service               │ │
│  │ - 轮询检测MySQL变更 ✅          │ │
│  │ - 发现新任务→加载到APScheduler  │ │
│  │ - 按触发器执行 ✅               │ │
│  │ - app.py停止也不影响 ✅         │ │
│  └─────────────────────────────────┘ │
└─────────────────────────────────────┘
```

**核心改造点**：
1. **app.py不再调度**：只写MySQL，移除 `_add_job_to_scheduler` 调用
2. **Windows服务唯一调度**：独立进程运行APScheduler
3. **MySQL变更检测**：服务轮询检测新任务/修改/删除
4. **可选：SQLAlchemyJobStore**：用MySQL做jobstore，实现跨进程共享

## 二、两种实现方案对比

### 方案X：轮询检测（推荐，简单可靠）

```python
# Windows服务轮询MySQL，发现变更就重载
class SchedulerService:
    def start(self):
        self.scheduler.start()
        self._load_jobs_from_db()  # 初次加载
        
        # 添加轮询任务，每30秒检查变更
        self.scheduler.add_job(
            func=self._sync_jobs_from_db,
            trigger='interval',
            seconds=30,
            id='__sync_jobs',
            replace_existing=True
        )
    
    def _sync_jobs_from_db(self):
        """同步MySQL任务到调度器"""
        # 1. 查询所有enabled任务
        db_jobs = execute_query("SELECT job_id, updated_at FROM scheduler_jobs WHERE status='enabled'")
        db_job_ids = {j['job_id'] for j in db_jobs}
        
        # 2. 当前调度器中的任务
        scheduler_job_ids = {j.id for j in self.scheduler.get_jobs() if not j.id.startswith('__')}
        
        # 3. 新增的任务（DB有，调度器没有）
        for job in db_jobs:
            if job['job_id'] not in scheduler_job_ids:
                self._reload_single_job(job['job_id'])
            elif self._is_job_updated(job['job_id'], job['updated_at']):
                self._reload_single_job(job['job_id'])
        
        # 4. 删除的任务（调度器有，DB没有或disabled）
        for job_id in scheduler_job_ids - db_job_ids:
            self.scheduler.remove_job(job_id)
```

**优点**：
- 简单可靠，无需额外组件
- 跨进程完全解耦
- app.py和服务完全独立

**缺点**：
- 最多30秒延迟（可调整）

### 方案Y：SQLAlchemyJobStore（高级，实时）

```python
# 用MySQL做APScheduler的jobstore，天然跨进程共享
from apscheduler.jobstores.sqlalchemy import SQLAlchemyJobStore

self.scheduler = BackgroundScheduler(
    jobstores={
        'default': SQLAlchemyJobStore(url='mysql+pymysql://...')
    },
    timezone='Asia/Shanghai'
)
```

**优点**：
- 任务信息持久化在MySQL
- 理论上跨进程共享

**缺点**：
- APScheduler的jobstore存的是"调度信息"，与业务表`scheduler_jobs`是两套
- 需要重构现有数据模型
- 多进程同时运行会冲突（需要额外锁机制）

**结论**：**推荐方案X（轮询）**，改动小、风险低、易理解。

## 三、调度链三种模式详解

### 3.1 串行模式（Sequential）

```
A ──→ B ──→ C
（A完成→B开始→B完成→C开始）
```

**配置**：
```json
{
  "job_id": "chain_serial",
  "job_name": "串行调度链",
  "job_type": "chain",
  "trigger_type": "cron",
  "trigger_config": {"day_of_week": "fri", "hour": 9, "minute": 0},
  "job_config": {
    "mode": "serial",
    "steps": [
      {"job_id": "task_a", "name": "步骤A"},
      {"job_id": "task_b", "name": "步骤B"},
      {"job_id": "task_c", "name": "步骤C"}
    ],
    "continue_on_error": false
  }
}
```

**执行逻辑**：
```python
def _execute_chain_serial(self, steps, parent_id, continue_on_error):
    for step in steps:
        result = self._execute_chain_step_sync(step['job_id'], parent_id)
        if result['status'] == 'failed' and not continue_on_error:
            return f"链在 {step['job_id']} 中断"
    return "串行链完成"
```

### 3.2 并行模式（Parallel）

```
    ┌──→ A ──┐
Start├──→ B ──┤──→ (全部完成)
    └──→ C ──┘
（A、B、C同时开始，各自独立）
```

**配置**：
```json
{
  "job_id": "chain_parallel",
  "job_name": "并行调度链",
  "job_type": "chain",
  "trigger_type": "cron",
  "trigger_config": {"day_of_week": "fri", "hour": 9, "minute": 0},
  "job_config": {
    "mode": "parallel",
    "steps": [
      {"job_id": "task_a", "name": "步骤A"},
      {"job_id": "task_b", "name": "步骤B"},
      {"job_id": "task_c", "name": "步骤C"}
    ],
    "wait_all": true
  }
}
```

**执行逻辑**：
```python
def _execute_chain_parallel(self, steps, parent_id, wait_all):
    from concurrent.futures import ThreadPoolExecutor, as_completed
    
    with ThreadPoolExecutor(max_workers=len(steps)) as executor:
        futures = {
            executor.submit(self._execute_chain_step_sync, step['job_id'], parent_id): step
            for step in steps
        }
        results = []
        for future in as_completed(futures):
            results.append(future.result())
    return f"并行链完成: {len(results)}个步骤"
```

### 3.3 并行后串行模式（Parallel-then-Serial / DAG）

```
    ┌──→ A ──┐
Start├──→ B ──┤──→ D ──→ E
    └──→ C ──┘
（A、B、C并行；全部完成后→D→E串行）
```

**配置**：
```json
{
  "job_id": "chain_dag",
  "job_name": "混合调度链",
  "job_type": "chain",
  "trigger_type": "cron",
  "trigger_config": {"day_of_week": "fri", "hour": 9, "minute": 0},
  "job_config": {
    "mode": "dag",
    "stages": [
      {
        "stage": 1,
        "mode": "parallel",
        "steps": [
          {"job_id": "task_a", "name": "并行A"},
          {"job_id": "task_b", "name": "并行B"},
          {"job_id": "task_c", "name": "并行C"}
        ]
      },
      {
        "stage": 2,
        "mode": "serial",
        "steps": [
          {"job_id": "task_d", "name": "串行D"},
          {"job_id": "task_e", "name": "串行E"}
        ]
      }
    ],
    "continue_on_error": false
  }
}
```

**执行逻辑**：
```python
def _execute_chain_dag(self, stages, parent_id, continue_on_error):
    """DAG模式：按stage顺序执行，stage内按mode执行"""
    for stage in stages:
        stage_mode = stage.get('mode', 'serial')
        steps = stage.get('steps', [])
        
        if stage_mode == 'parallel':
            # 本阶段并行，等待全部完成
            results = self._execute_chain_parallel(steps, parent_id, wait_all=True)
        else:
            # 本阶段串行
            results = self._execute_chain_serial(steps, parent_id, continue_on_error)
        
        # 检查本阶段是否有失败
        if self._stage_has_failure(results) and not continue_on_error:
            return f"链在 stage{stage['stage']} 中断"
    
    return "DAG链完成"
```

### 3.4 三种模式对比

| 模式 | 结构 | 适用场景 | 配置字段 |
|------|------|----------|----------|
| **串行** | A→B→C | 有依赖，必须顺序执行 | `mode: "serial"` + `steps` |
| **并行** | A‖B‖C | 无依赖，同时执行提速 | `mode: "parallel"` + `steps` |
| **DAG** | (A‖B‖C)→D→E | 部分并行+部分依赖 | `mode: "dag"` + `stages` |

## 四、完整参数配置详解

### 4.1 触发器参数（trigger_config）

#### Cron触发器（定时）

```json
{
  "trigger_type": "cron",
  "trigger_config": {
    "year": "*",           // 年（可选）
    "month": "*",          // 月 1-12
    "day": "*",            // 日 1-31
    "week": "*",           // 周数 1-53
    "day_of_week": "fri",  // 星期几 mon-sun 或 0-6
    "hour": 9,             // 时 0-23
    "minute": 0,           // 分 0-59
    "second": 0            // 秒 0-59
  }
}
```

**常用示例**：
```json
// 每周五09:00
{"day_of_week": "fri", "hour": 9, "minute": 0}

// 每天09:30
{"hour": 9, "minute": 30}

// 每月1号00:00
{"day": 1, "hour": 0, "minute": 0}

// 工作日每天15:00
{"day_of_week": "mon-fri", "hour": 15, "minute": 0}

// 每小时执行
{"minute": 0}
```

#### Interval触发器（间隔）

```json
{
  "trigger_type": "interval",
  "trigger_config": {
    "weeks": 0,
    "days": 0,
    "hours": 1,      // 每1小时
    "minutes": 0,
    "seconds": 0
  }
}
```

#### Date触发器（一次性）

```json
{
  "trigger_type": "date",
  "trigger_config": {
    "run_date": "2026-08-01 09:00:00"
  }
}
```

### 4.2 任务参数（job_config）

#### Python脚本任务

```json
{
  "job_type": "python_script",
  "job_config": {
    "script_path": "gs2026.analysis.worker.xxx",  // 模块路径

    },
    "working_dir": "F:/pyworkspace2026/gs2026",
    "timeout": 3600                                // 超时秒数
  }
}
```

```python
def _sync_jobs_from_db(self):
    """轮询处理变更信号（daemon模式）"""
    signals = execute_query(
        "SELECT * FROM scheduler_reload_signal WHERE processed=0 ORDER BY id"
    )
    for sig in signals:
        job_id = sig['job_id']
        action = sig['action']
        
        if action in ('add', 'update', 'toggle'):
            self._reload_single_job(job_id)
        elif action == 'delete':
            try:
                self.scheduler.remove_job(job_id)
            except:
                pass
        
        # 标记已处理
        execute_update(
            "UPDATE scheduler_reload_signal SET processed=1 WHERE id=%s",
            (sig['id'],)
        )
```

### Q1: 前端设置后，读MySQL的是Windows独立服务还是app.py？

### Q3: 当前代码为什么不行？

### Q4: 三种调度链模式如何选？

- **串行**：任务有严格依赖（A的输出是B的输入）
- **并行**：任务无依赖，追求速度
- **DAG**：混合场景（先并行采集，再串行处理）

## 一、【问题1】交易日动态调度（基于MySQL查询控制）

### 1.1 你的需求

> "我只想交易日执行，交易日可能是周三、周四，下周可能是周二、周五。能否通过SQL确定交易时间再转换成调度时间？"

**答案**：✅ **完全可以**，而且你的系统已经有现成的交易日历表 `data_jyrl`。

### 1.2 现有基础（已确认）

**表 `data_jyrl`**（交易日历表）：
```
trade_date    DATE    日期
trade_status  INT     1=交易日, 0=休市
```

**实测数据**（已验证）：
```

2026-07-30 - 交易日
2026-07-31 - 交易日
2026-08-01 - 休市（周六）
2026-08-02 - 休市（周日）
2026-08-03 - 交易日
...
```

**现成工具** `trading_day_util.py`：
```python

get_next_trading_day(ref_date)   # 下一交易日
get_date_list(ref_date)          # 日期区间
```

### 1.3 核心难点分析

**Cron的局限**：
- 标准cron只能表达"固定规律"（如每周五、每天9点）
- **无法表达"交易日"**（交易日不规律：遇节假日会变）

**举例**：
```
国庆节 2026-10-01~10-07 休市
- 9-30(周三)是交易日
- 10-08(周四)才是下一个交易日
- 中间的10-01~10-07全部跳过
标准cron做不到这种"动态跳过"
```

### 1.4 解决方案：两种模式

#### 方案A：每日检查 + 交易日判断（推荐，简单可靠）

**原理**：每天固定时间触发，但执行前先查 `data_jyrl` 判断今天是否交易日，非交易日直接跳过。

```python
# 新增触发器类型: 'trading_cron'（交易日专用）
def _create_trigger(self, trigger_type, trigger_config):
    if trigger_type == 'trading_cron':
        # 底层仍用cron每天触发，但包装交易日判断
        return CronTrigger(
            hour=trigger_config.get('hour', 9),
            minute=trigger_config.get('minute', 30)
        )
    # ...其他类型

# 任务执行前判断交易日
def _execute_job_by_id(self, job_id, execution_id):
    job = self.get_job(job_id)
    trigger_config = json.loads(job['trigger_config'])
    
    # 如果是交易日专用触发器，先判断今天是否交易日
    if job['trigger_type'] == 'trading_cron':
        if not self._is_trading_day_today():
            logger.info(f"今日非交易日，跳过任务: {job_id}")
            self._finish_execution(execution_id, 'skipped', '非交易日跳过')
            return
    
    # 是交易日，正常执行
    # ...

def _is_trading_day_today(self) -> bool:
    """查询data_jyrl判断今天是否交易日"""
    sql = "SELECT trade_status FROM data_jyrl WHERE trade_date = CURDATE()"
    result = execute_query(sql)
    return result and result[0]['trade_status'] == 1
```

**配置示例**：
```json
{
  "job_id": "trading_task",
  "job_name": "交易日数据处理",
  "trigger_type": "trading_cron",
  "trigger_config": {
    "hour": 9,
    "minute": 30,
    "check_field": "trade_status",
    "check_table": "data_jyrl"
  }
}
```

**优点**：
- 逻辑简单，用现成的cron机制
- 交易日历更新（如临时调休），自动适应
- 执行记录会记录"skipped"状态，可追溯

**缺点**：
- 非交易日也会"触发"（但立即跳过，开销极小）

#### 方案B：动态计算下次执行时间（高级，精确）

**原理**：每次执行后，查询 `data_jyrl` 计算下一个交易日，动态设置下次触发时间。

```python
def _schedule_next_trading_day(self, job_id, hour, minute):
    """动态调度到下一个交易日"""
    # 查询下一个交易日
    sql = """
        SELECT trade_date FROM data_jyrl 
        WHERE trade_date > CURDATE() AND trade_status = 1 
        ORDER BY trade_date ASC LIMIT 1
    """
    result = execute_query(sql)
    if not result:
        logger.warning("未找到下一个交易日")
        return
    
    next_trading_date = result[0]['trade_date']
    run_date = datetime.combine(next_trading_date, time(hour, minute))
    
    # 动态添加date触发器
    self.scheduler.add_job(
        func=self._execute_and_reschedule,
        trigger='date',
        run_date=run_date,
        args=[job_id, hour, minute],
        id=f"{job_id}_next",
        replace_existing=True
    )
    logger.info(f"下次执行时间: {run_date}")

def _execute_and_reschedule(self, job_id, hour, minute):
    """执行任务并调度下一个交易日"""
    self._execute_job_by_id(job_id, self._create_execution(job_id, 'trading'))
    # 执行完后，立即调度下一个交易日
    self._schedule_next_trading_day(job_id, hour, minute)
```

**优点**：
- 精确，只在交易日触发
- 无空触发

**缺点**：
- 逻辑复杂，依赖"执行后重新调度"链条
- 若服务重启，需要重新初始化下次调度
- 交易日历临时变更时，已调度的可能不准

### 1.5 推荐选择

| 场景 | 推荐方案 |
|------|----------|
| **一般交易日任务** | **方案A（每日检查+跳过）** |
| 对精确性要求极高 | 方案B（动态计算）|

**理由**：方案A简单可靠，"非交易日空触发+立即跳过"的开销可忽略（每天1次判断），且对交易日历变更天然适应。

### 1.6 SQL查询交易时间转调度的完整逻辑

### 2.6 关键增强：链式执行时写入每步记录

**当前问题**：现有 `_execute_chain_job` 可能没有为每个步骤创建独立记录。

**改造**：确保链的每一步都写 `scheduler_execution_log`，用 `parent_execution_id` 关联：

```python
def _execute_chain_step_sync(self, job_id, parent_execution_id):
    """执行链中一步，写入独立执行记录"""
    # 为这一步创建执行记录（关联父链）
    step_execution_id = self._create_execution(
        job_id, 'chain', parent_execution_id  # ← parent关联
    )
    
    try:
        self._update_execution_status(step_execution_id, 'running')  # 标记运行中
        result = self._execute_job_by_id(job_id, step_execution_id)
        self._finish_execution(step_execution_id, 'success', result)
        return {'status': 'success', 'execution_id': step_execution_id}
    except Exception as e:
        self._finish_execution(step_execution_id, 'failed', str(e))
        return {'status': 'failed', 'execution_id': step_execution_id}
```

这样前端就能通过 `parent_execution_id` 查到链的完整进度。

## 四、v4.0 关键问题解答

### Q1: 交易日不规律（周三周四/周二周五），能调度吗？

**能**。方案A：每天固定时间触发，执行前查 `data_jyrl`，非交易日跳过。交易日历表已有未来数据，临时调休也自动适应。

### Q2: 如何知道任务执行了没有？

查 `scheduler_execution_log` 有无当天记录。有=执行过，无=未执行。

### Q3: 成功失败怎么看？

看 `status` 字段：success/failed/timeout/skipped/running/pending 六种状态。

### Q4: 调度链执行到哪一步了？

通过 `parent_execution_id` 查询链的所有步骤，找 `status='running'` 的就是当前阶段。前端可视化展示Stage和Step进度。

```
⑤ Windows服务轮询（每30秒）：
   - 读 scheduler_reload_signal 有无未处理信号
   - 发现 add 信号 → 从 scheduler_jobs 加载该任务到 APScheduler
```

## 五、当前已知问题与风险（含解决办法）

### 风险1：多进程重复调度 🔴

**问题**：如果 app.py 和 Windows 服务**都**在调度（改造不彻底），同一任务会执行两次。

**解决**：
- P1改造时，app模式**严格不本地调度**（`mode='app'` 时 add_job 不调用 `_add_job_to_scheduler`）
- daemon是唯一调度者
- 上线前用 Q12 灰度验证

### 风险2：服务重启丢失动态调度 🟡

**问题**：交易日方案B（动态计算）依赖"执行后重新调度"，服务重启会断链。

**解决**：采用方案A（每日触发+跳过），不依赖动态链，服务重启后从MySQL重新加载即可。

### 风险3：轮询延迟 🟡

**问题**：前端改动后最多30秒才生效。

**解决**：
- 一般场景30秒可接受
- 若需即时，提供"手动触发"按钮（Q2选B），或前端保存后调用 `/scheduler/reload` 主动通知

### 风险4：Windows服务权限 🟡

**问题**：LocalSystem账户可能无法访问F盘/网络/数据库。

**解决**：用当前用户账户运行服务（Q4选B），或配置服务账户权限。

### 风险5：链式执行阻塞 🟡

**问题**：串行链某步耗时很长，占用调度线程。

**解决**：
- 链在独立线程执行（不阻塞主调度）
- 设置 step 级 timeout
- `max_instances=1` 防止同一链并发

### 风险6：现有任务兼容 🟢

**问题**：当前 scheduler_jobs 已有任务，改造后可能不兼容。

**解决**：P0阶段先备份，P8测试现有任务，保留旧 job_type 兼容分支（代码已有）。
