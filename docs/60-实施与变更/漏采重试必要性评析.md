# 漏采重试必要性评析：无重试时净额类累积值能否正常存在

> **版本**: v1.0  
> **日期**: 2026-07-28  
> **状态**: 评析报告（待用户决定是否保留重试）  
> **背景**: 用户指出"重试成本大，且重新能采集到的数据少之又少"，要求评析无重试时净额类值能否正常存在

---

## 一、核心结论（先给答案）

**✅ 去掉重试后，净额类累积值仍能正常存在，不会丢失或归零。**

原因：净额累积值的正确性由**"继承 + 补齐"机制保证**，与"重试"无关。重试只是"尽量拿到漏采股票的真实当前值"，即使不重试，补齐兜底也能让累积值完整延续。

**并且实测数据支持去掉重试**：今日全天 1071 个 tick，**重试触发 0 次、补齐兜底 0 次**——重试机制实际几乎从不生效，却每 tick 都有潜在判断成本。

---

## 二、净额累积值的保护机制（三层，重试只是其一）

### 数据流（漏采股票视角）

```
采集(可能漏采某股) 
  → 阶段3: _fill_missing_stocks 补齐(用上tick的amount/volume)
  → 阶段5: _carry_forward_cumulative_fields 无条件继承上tick累计值
  → calculate_main_force: delta = amount_now - amount_prev
  → 补齐股票 amount_now = amount_prev → delta=0 → 累计值 = 继承值 + 0 = 保持不变 ✅
```

### 三层保护各自的作用

| 层 | 机制 | 作用 | 依赖重试? |
|----|------|------|-----------|
| **第0层（根基）** | `_carry_forward_cumulative_fields` | **无条件继承**上tick所有累计字段(cum/max_cum/count) | ❌ 不依赖 |
| 第1层 | fetch重试 | 尽量拿漏采股票的**真实当前值** | 就是重试本身 |
| 第2层 | `_fill_missing_stocks` | 重试仍缺时，用上tick的amount补齐→delta=0→累计延续 | ❌ 不依赖 |
| 第3层 | 峰值Redis兜底 + NaN防护 | 防峰值字段异常显示"-" | ❌ 不依赖 |

**关键洞察**：
- 累积值的**延续性**由第0层（继承）+ 第2层（补齐使delta=0）共同保证
- **重试（第1层）只影响"漏采股票这一tick的净额增量是否反映真实变化"**
- 去掉重试，最坏情况：漏采股票这一tick的净额增量记为0（而非真实值），**但累积值不会丢失、不会归零**，下一tick采集成功后自动恢复真实累积

## 三、去掉重试的实际影响评析

### 无重试时会发生什么？

| 场景 | 有重试 | 无重试（仅补齐） |
|------|--------|-----------------|
| 漏采股票累积值 | 延续 ✅ | 延续 ✅（继承+delta=0）|
| 漏采股票本tick净额增量 | 拿到真实值 | 记为0（少算一次增量）|
| 漏采股票下一tick | 正常 | 采集成功即恢复真实累积 ✅ |
| 前端显示 | 正常 | 正常（有补齐行，is_filled=1标记）|

### 无重试的唯一代价

**漏采股票在"漏采的那个tick"少记一次净额增量。**

但考虑到：
1. 净额是**累积值**，单tick少记一次增量，下一tick成功采集后 `cumulative = 继承值 + 新增量` 会**自动追上**（因为下一tick的amount是最新的，delta包含了漏采期间的累积变化）
   - ⚠️ 需确认：delta基于 amount_now - amount_prev，若prev是补齐值(=上上tick)，则下一tick的delta会**包含漏采期间的完整变化**，即"迟到但不丢失"
2. 漏采是小概率事件（实测今日0次）
3. 补齐行标记 `is_invalid=3, is_filled=1`，前端可识别

## 五、评析结论与建议

### 关于"是否去掉重试"

| 维度 | 评析 |
|------|------|
| **净额正确性** | 去掉重试**不影响**累积值存在性（继承+补齐保证），仅漏采tick少记一次增量，下tick自动追回 |
| **实际收益** | 重试全天0次触发，去掉它对时效**几乎无直接影响**（因为本就没触发）|
| **潜在成本** | 重试逻辑每tick有"集合差判断"开销（虽小），去掉可简化代码路径 |
| **风险** | 极低——补齐兜底+继承机制仍在，漏采股票不会丢 |

### 我的建议

**可以去掉重试（第1层），保留继承（第0层）+ 补齐兜底（第2层）+ 峰值保险（第3层）。**

理由：
1. 重试实测0次触发，"重新能采集到的数据少之又少"（你的观察正确）
2. 去掉重试不影响净额累积值的正确性
3. 简化主路径，去掉每tick的重试判断开销

**但需注意**：真正的超时大头**不是重试**（重试没触发），而是：
- 采集偶发尖峰（网络，最大2662ms）
- 主力/恢复偶发尖峰（可能与之前发现的**双进程并发**、GC、Redis/MySQL争用有关）

**所以：去掉重试能简化代码，但要让Tick稳定回到3秒内，还需解决偶发尖峰**（建议单独排查双进程问题——之前已定位PID 48800 vs 32664双进程抢写）。
