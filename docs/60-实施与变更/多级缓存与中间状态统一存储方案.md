## 一、设计原则（v3.0 最终版）

| 原则 | 说明 |
|------|------|
| **同构存储** | JSON 结构与 DataFrame 同构，便于 `pd.DataFrame(json)` 直接解析 |
| **短 key** | 尽量缩短 key 长度，中间状态加 `_m_` 前缀便于识别 |
| **兼容现有** | 不影响原有计算逻辑，原有字段保持不变 |
| **零侵入** | 不阻塞主流程，状态恢复失败自动降级 |
| **实时/回填一致** | 同一套 `calculate_func`，同一套状态恢复逻辑 |
| **每 tick 存储** | 保持现状，每 tick 存储完整状态 |
| **四级缓存** | L1 内存 → L2 Redis → L3 MySQL → L4 重新计算 |
| **固定大小** | 中间状态字段大小固定，不随时间膨胀 |

### 3.2 字段命名规则

| 类型 | 前缀 | 示例 | 说明 |
|------|------|------|------|
| 大盘结果 | `mkt_` | `mkt_vw_bias` | 大盘级结果指标（原有，不变） |
| 个券结果 | 无前缀 | `ws2m`, `c1m` | 个券级结果指标（原有，不变） |
| 大盘中间状态 | `_m_` | `_m_vwap_pv` | 大盘级中间状态（新增） |
| 个券中间状态 | `{code}_m_` | `123456_m_ss` | 个券级中间状态（新增） |
| 元数据 | `_m_` | `_m_ver`, `_m_t` | 版本、时间等（新增） |

**设计意图**：
- `_m_` 前缀 = "memory state"，明确标识中间状态
- 与结果字段区分，便于识别和过滤
- 短key减少存储空间

```python
# L3: MySQL（持久化）

# L4: 重新计算（兜底）
```

### 4.2 查询函数

```python
def get_prev_tick(table: str, time_full: str) -> Optional[pd.DataFrame]:
    """
    获取上一tick数据（四级缓存）
    顺序: L1内存 → L2Redis → L3MySQL → L4None
    """
    global _prev_tick_cache
    
    # L1: 内存命中（<1μs）
    if _prev_tick_cache['t'] == time_full:
        return _prev_tick_cache['df'].copy()
    
    # L2: Redis（1-5ms）
    df = redis_util.load_dataframe_by_offset(table, offset=0)
    if df is not None:
        _update_l1(df, time_full)
        return df
    
    # L3: MySQL（10-50ms）
    df = _load_from_mysql(table, time_full)
    if df is not None:
        _update_l1(df, time_full)
        return df
    
    # L4: 无数据
    return None

def _update_l1(df: pd.DataFrame, time_full: str):
    """更新L1缓存"""
    global _prev_tick_cache
    _prev_tick_cache['t'] = time_full
    _prev_tick_cache['df'] = df.copy()
```

## 五、状态恢复（实时/回填统一）

### 5.1 统一恢复函数

```python
def recover_state_from_ext(ext: dict) -> bool:
    """
    从 ext_indicators 恢复中间状态
    
    用途：
    1. 实时：服务重启后恢复
    2. 回填：每个tick恢复上一tick状态
    """
    global _mkt_trend_vwap_sum_pv, _mkt_trend_vwap_sum_v
    global _mkt_trend_day_high, _mkt_trend_day_low
    global _mkt_shape_history, _mkt_trend_slope_10m_cache
    
    try:
        # 恢复标量状态
        _mkt_trend_vwap_sum_pv = float(ext.get('_m_vwap_pv', 0))
        _mkt_trend_vwap_sum_v = float(ext.get('_m_vwap_v', 0))
        _mkt_trend_day_high = float(ext.get('_m_high', -999))
        _mkt_trend_day_low = float(ext.get('_m_low', 999))
        
        # 恢复形态历史（同构：list[dict] → list[dict]）
        shape_h = ext.get('_m_shape_h', [])
        _mkt_shape_history = [{"t": d['t'], "p": d['p']} for d in shape_h]
        
        # 恢复斜率缓存（同构：list[list] → deque[tuple]）
        s10m = ext.get('_m_s10m', [])
        _mkt_trend_slope_10m_cache.clear()
        for item in s10m:
            _mkt_trend_slope_10m_cache.append(tuple(item))
        
        logger.info(f"[状态恢复] VWAP={_mkt_trend_vwap_sum_pv:.0f}, 形态历史={len(_mkt_shape_history)}点")
        return True
    except Exception as e:
        logger.warning(f"[状态恢复] 失败，从0开始: {e}")
        return False
```

## 六、中间字段膨胀问题分析与优化（v4.0）

### 6.1 问题发现

**关键问题**：`_mkt_shape_history` 是 **普通 list，无 maxlen**，会随时间无限增长！

| 字段 | 内存结构 | maxlen | 是否膨胀 | 风险 |
|------|----------|--------|----------|------|
| `_mkt_shape_history` | `list` | ❌ 无 | 🔴 是 | **高** |
| `_mkt_trend_slope_10m_cache` | `deque` | ✅ 500 | 🟢 否 | 低 |
| `_mkt_ext_price_cache` | `deque` | ✅ 300 | 🟢 否 | 低 |
| `_mkt_slope_buf_short/long` | `deque` | ✅ 60/300 | 🟢 否 | 低 |
| `_mkt_trend_vwap_sum_pv/v` | `float` | - | 🟢 否 | 低 |
| 个券级缓存 | `deque` | ✅ 60/300 | 🟢 否 | 低 |

### 6.2 膨胀速度估算

**`_mkt_shape_history` 膨胀分析**：

```
假设：
  - 交易时间：4小时 = 14400秒
  - tick间隔：3秒
  - 每个点存储：{t: int, p: float} ≈ 16字节

计算：
  全天点数：14400 / 3 = 4800点
  存储大小：4800 × 16B = 76.8 KB/天
  JSON序列化后：约100-150 KB/天

对比其他字段（固定大小）：
  _mkt_slope_10m (maxlen=500)：500 × 16B = 8 KB（固定）
  _mkt_ep (maxlen=300)：300 × 16B = 4.8 KB（固定）

问题：
  _mkt_shape_history 是其他字段的 10-20 倍！
```

### 6.4 优化方案：分级存储策略

**核心思路**：区分"必须全量"和"可以截断"的中间状态

| 级别 | 字段 | 存储策略 | 原因 |
|------|------|----------|------|
| **P0-必须全量** | `_m_shape_h` | ✅ 存全天 | 形态识别需要全天数据 |
| **P1-可截断** | `_m_s10m`, `_m_ep` | ⚠️ 只存最近500/300点 | 斜率计算只需要近期 |
| **P2-标量** | `_m_vwap_pv`, `_m_high` | ✅ 存标量 | 本身固定大小 |

**P0 字段优化：形态历史压缩存储**

```python
# 原方案：存储每个tick（4800点/天）
"_m_shape_h": [
    {"t": 32400, "p": -0.5},  # 每个tick都存
    {"t": 32403, "p": -0.48},
    {"t": 32406, "p": -0.47},
    # ... 4800个点
]
# 大小：约 150 KB/天

# v4.0 优化：只存关键转折点（压缩90%）
"_m_shape_h": [
    {"t": 32400, "p": -0.5, "type": "start"},      # 开盘
    {"t": 33600, "p": -0.85, "type": "low"},      # 日内低点
    {"t": 34200, "p": 0.5, "type": "high"},       # 日内高点
    {"t": 34800, "p": 0.2, "type": "mid"},        # 中间点（每30分钟）
    # ... 约 200-300个点（压缩90%）
]
# 大小：约 10-15 KB/天

# 压缩算法：只存极值点和采样点
def compress_shape_history(history: list, max_points: int = 300) -> list:
    """
    压缩形态历史，保留关键信息
    
    策略：
    1. 必存：开盘点、当前点
    2. 必存：日内最高/最低点
    3. 采样：每30分钟一个点
    4. 如果点数仍超过max_points，均匀采样
    """
    if len(history) <= max_points:
        return history
    
    # 提取关键信息
    start = history[0]  # 开盘
    current = history[-1]  # 当前
    
    # 找极值
    min_idx = min(range(len(history)), key=lambda i: history[i]['p'])
    max_idx = max(range(len(history)), key=lambda i: history[i]['p'])
    
    # 每30分钟采样
    sample_interval = 30 * 60 // 3  # 30分钟 = 600个tick
    samples = [history[i] for i in range(0, len(history), sample_interval)]
    
    # 合并关键点（去重）
    key_points = {0, min_idx, max_idx, len(history)-1}
    for s in samples:
        idx = history.index(s)
        key_points.add(idx)
    
    # 如果仍超过限制，均匀采样
    if len(key_points) > max_points:
        step = len(history) // max_points
        key_points = set(range(0, len(history), step))
        key_points.add(len(history)-1)  # 确保包含当前点
    
    # 按时间排序
    compressed = [history[i] for i in sorted(key_points)]
    
    return compressed
```

### 6.6 压缩后的形态识别适配

```python
def compute_mkt_shape_v4(dependencies: dict, compressed_history: list) -> str:
    """
    v4.0 适配压缩后的形态历史
    
    改动：
    1. 解压（插值还原）
    2. 原有逻辑不变
    """
    # 解压：线性插值还原全天数据
    history = decompress_shape_history(compressed_history)
    
    # 原有逻辑完全不变
    return compute_mkt_shape(dependencies, history)

def decompress_shape_history(compressed: list) -> list:
    """
    解压形态历史
    
    策略：线性插值还原
    """
    if len(compressed) < 2:
        return compressed
    
    decompressed = []
    for i in range(len(compressed) - 1):
        p1, p2 = compressed[i], compressed[i+1]
        # 插值中间点
        dt = p2['t'] - p1['t']
        dp = p2['p'] - p1['p']
        steps = dt // 3  # 每3秒一个tick
        for j in range(steps):
            t = p1['t'] + j * 3
            p = p1['p'] + dp * j / steps
            decompressed.append({'t': t, 'p': round(p, 4)})
    
    decompressed.append(compressed[-1])
    return decompressed
```

### 6.1 个券中间状态是什么？

| `_high_state` | 个券日内高点状态 | 计算 `high_distance` |

### 6.2 为什么需要个券中间状态？

**场景**：服务重启后，个券指标计算失真

```
例：债券 123456 的 weighted_slope_2m

正常流程（连续运行）：
  tick1: 缓存 [1.0] → slope = 0
  tick2: 缓存 [1.0, 1.2] → slope = 0.2
  tick3: 缓存 [1.0, 1.2, 1.3] → slope = 0.15
  ...

重启后（无状态恢复）：
  tick1: 缓存 [] → slope = 0（错误！应为0.15）
  tick2: 缓存 [1.3] → slope = 0（错误！）
  需要60个tick才能恢复正常
```

**影响**：
- 斜率指标重启后约10-15分钟才能稳定
- `peak_vol_bias`、`high_distance` 等日内极值指标完全错误

### 6.3 动态 code 作为 key 的设计问题

**你的质疑是对的！** 动态 code 作为 key 有以下问题：

| 问题 | 说明 | 严重程度 |
|------|------|----------|
| **存储膨胀** | 400只债券 × 每条约7KB = 每tick 3MB | 🔴 高 |
| **Redis key 爆炸** | 400个债券 × N个字段 = 数千个key | 🔴 高 |
| **查询低效** | 需要遍历所有 code 前缀的key | 🟡 中 |
| **维护困难** | code 变动（退市/上市）导致key失效 | 🟡 中 |

**存储大小估算**：
```
单债券状态：
  - slope_short: 60 × 8B = 480B
  - slope_long: 300 × 8B = 2400B
  - ext_price_cache: 300 × 16B = 4800B
  - peak_vol_state: 2 × 8B = 16B
  - high_state: 1 × 8B = 8B
  ≈ 7.7 KB/债券

400只债券：400 × 7.7KB = 3 MB/tick

每3秒一个tick，一天4小时：
  4800 tick × 3MB = 14.4 GB/天（仅个券状态）
```

### 6.4 重新设计：个券状态分级处理

**核心原则**：大盘状态必须存，个券状态选择性存

| 级别 | 存储策略 | 原因 |
|------|----------|------|
| **大盘级** | ✅ 必须存储 | 影响所有债券，无法从个券反推 |
| **个券级-活跃** | ⚠️ 可选存储 | 只存TOP30活跃债券，减少90%存储 |
| **个券级-普通** | ❌ 不存储 | 10-15分钟自恢复，影响可接受 |

**优化后的存储结构**：


### 6.5 个券状态恢复策略

```python
def recover_bond_state(ext: dict, code: str):
    """
    恢复个券状态（分级策略）
    """
    # 尝试从ext恢复（只存了TOP30）
    ss_key = f"_m_{code}_ss"
    sl_key = f"_m_{code}_sl"
    
    if ss_key in ext:
        # 有存储，直接恢复
        _slope_buf_short[code] = deque(ext[ss_key], maxlen=60)
        _slope_buf_long[code] = deque(ext[sl_key], maxlen=300)
        logger.debug(f"[个券恢复] {code} 从存储恢复")
    else:
        # 无存储，从0开始（10-15分钟自恢复）
        _slope_buf_short[code] = deque(maxlen=60)
        _slope_buf_long[code] = deque(maxlen=300)
        logger.debug(f"[个券恢复] {code} 从0开始（非活跃债券）")
```

### 6.6 设计利弊总结

| 方面 | 原设计（存全部） | 优化设计（只存TOP30） |
|------|----------------|---------------------|
| **存储** | 3MB/tick，14GB/天 | 231KB/tick，1.1GB/天 |

**结论**：
- ✅ **大盘级状态**：必须存储（影响全局）
