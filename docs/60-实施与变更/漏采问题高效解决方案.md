# 漏采问题最优解决方案（设计稿）

**问题**: 采集批次超时 → 部分股票整行缺失 → 累计值（峰值净额）级联丢失，前端显示"-"  
**设计时间**: 2026-07-27 14:00  
**状态**: 🔴 待审核（最优方案设计，未改代码）

---

## 一、根因回顾（已定位）

```
采集: fetch_all_concurrently 批次超时(FETCH_TIMEOUT=2.5s) → 整批400只股票丢弃
      → 这些股票【完全不在 df_now】
恢复: _recover_invalid_data_vectorized 用 .update() → 只更新已存在行，无法补缺失行
      → 缺失股票无 is_invalid 标记 → 阶段3跳过 → 级联丢失峰值
```

---

## 二、最优方案（已定夺，无需选择）

经过对整条 tick 流水线的分析，最优设计是：**在阶段3末尾，用上一tick数据补齐"完全缺失"的股票整行，让后续流水线自然处理，delta天然=0，累计值完整延续。**

### 为什么这是最优（对比其他思路）

| 思路 | 评价 |
|------|------|
| **补齐整行(选定)** | ✅ 复用已加载的df_prev；✅ delta天然=0累计不断裂；✅ 走原生流水线不改计算 |
| 只在peak更新时兜底 | ❌ 治标不治本，其他累计字段(cumulative_main_net/count)仍丢 |
| Redis历史峰值max | ✅ 好兜底，但单靠它 cumulative_main_net 仍会跳变；作为**第二道保险**保留 |
| 改.update为补行 | ❌ 混在恢复函数里，语义混乱（无效值恢复 vs 缺失补齐是两回事） |

**结论**：**主方案=补齐整行** + **保险=峰值单调兜底**。两者都不改核心累计计算。

## 三、详细设计

### 设计1（主）：`_fill_missing_stocks` — 补齐缺失股票

**位置**：阶段3，在 `_recover_invalid_data_vectorized` 之后，作为独立函数。

**关键点**：
1. **独立于现有恢复逻辑**（缺失补齐 ≠ 无效值恢复，语义分离）
2. **必须无条件加载 df_prev**（当前只在有 is_invalid 时才加载，漏采时可能没有 invalid 股票 → 需调整加载条件）
3. **补齐行的字段处理**：
   - `price/volume/amount/change_pct` → 用上tick值（保证阶段4/5计算不报错，且 delta=0）
   - `stock_code/short_name` → 用上tick值
   - `is_invalid = 3`（新标记：漏采补齐，区别于1无效/2已恢复）
   - `is_body_*/open_price/is_zt/main_net_*` → **不填**，让阶段4/5自然重算（price有效即可算）

```python
def _fill_missing_stocks(df_now: pd.DataFrame, df_prev: pd.DataFrame,
                         time_full: str) -> tuple:
    """补齐【完全缺失】的股票（漏采导致整行不在df_now）。

    用上一tick数据补齐基础字段(price/volume/amount/change_pct)，
    补齐行的成交量/额沿用上tick → 阶段5主力净额delta自然=0 → 累计值完整延续。
    标记 is_invalid=3 区分来源。异常降级(返回原df)，不影响主流程。
    """
    if df_prev is None or df_prev.empty or df_now is None:
        return df_now, 0
    try:
        now_codes = set(df_now['stock_code'].astype(str).str.zfill(6))
        prev_codes = set(df_prev['stock_code'].astype(str).str.zfill(6))
        missing = prev_codes - now_codes
        if not missing:
            return df_now, 0

        # 只补基础字段（阶段4/5会重算衍生字段）
        base_cols = ['stock_code', 'short_name', 'price', 'change',
                     'change_pct', 'volume', 'amount']
        avail = [c for c in base_cols if c in df_prev.columns]
        fill_rows = df_prev[df_prev['stock_code'].astype(str).str.zfill(6).isin(missing)][avail].copy()
        if fill_rows.empty:
            return df_now, 0
        fill_rows['is_invalid'] = 3          # 漏采补齐标记
        fill_rows['is_filled'] = 1           # 供前端识别(可选)

        df_now = pd.concat([df_now, fill_rows], ignore_index=True)
        logger.warning(f"[{time_full}] 补齐漏采股票 {len(missing)} 只 "
                       f"(now={len(now_codes)}, prev={len(prev_codes)})")
        return df_now, len(missing)
    except Exception as e:
        logger.error(f"[{time_full}] 补齐漏采股票失败(降级): {e}")
        return df_now, 0
```

**阶段3调用调整**（关键：df_prev 需无条件加载）：
```python
# ========== 阶段3：恢复无效数据 + 补齐漏采股票 ==========
t3 = time.time()
recovered_count = 0
filled_count = 0
try:
    sssj_table = f"monitor_gp_sssj_{date_str}"
    df_prev = _get_cached_prev_main(sssj_table, time_full, date_str)  # 无条件加载

    if df_prev is not None and not df_prev.empty:
        # 3a: 恢复"存在但值无效"的股票（原逻辑）
        if 'is_invalid' in df_now.columns and df_now['is_invalid'].sum() > 0:
            invalid_codes = df_now[df_now['is_invalid'] == 1]['stock_code'].tolist()
            recovered_count = _recover_invalid_data_vectorized(
                df_now, df_prev, invalid_codes, time_full)
        # 3b: 补齐"完全缺失"的股票（新增）
        df_now, filled_count = _fill_missing_stocks(df_now, df_prev, time_full)
except Exception as e:
    logger.error(f"[{time_full}] 阶段3异常: {e}")
t3_elapsed = (time.time() - t3) * 1000
```

**性能**：`prev_codes - now_codes` 集合差 O(n)，n≈5000，<1ms。补齐通常0~400只 concat，<2ms。总增量 <3ms（tick预算3000ms内可忽略）。

### 设计2（保险）：峰值单调兜底

即使设计1漏网（如df_prev本身也缺该股），加第二道保险——peak 从 Redis hash 历史峰值兜底，只增不减。

> **关键利好（已查证）**：`_save_cumulative_to_redis_hash` 用 `hset mapping` 写入，**只增改、从不删除**缺失股票的field。所以某股票即使某tick漏采，它在hash里的历史峰值**依然保留**。这让"读hash兜底峰值"天然可靠——漏采期间hash仍有该股的last-good峰值。

**位置**：`calculate_main_force_and_cumulative` 峰值更新后。
```python
# 峰值更新后，用Redis历史峰值兜底（peak是历史最大值，不该变小）
try:
    hist_peak = _load_peak_from_redis_hash(sssj_table)  # {code: max_peak}
    if hist_peak:
        df_now['_hp'] = df_now['stock_code'].map(hist_peak).fillna(0.0)
        df_now['max_cumulative_main_net'] = df_now[
            ['max_cumulative_main_net', '_hp']].max(axis=1)
        df_now.drop(columns=['_hp'], inplace=True)
except Exception as e:
    logger.warning(f"峰值兜底失败(非关键): {e}")
```
> `_save_cumulative_to_redis_hash` 已存在（每tick写 cum,max_cum,count），只需加读取函数 `_load_peak_from_redis_hash`（复用现有hash格式 `{code:"cum,max_cum,count"}`，取 parts[1]）。

## 四、副作用评估

| 关注点 | 评估 |
|--------|------|
| 累计计算逻辑 | ✅ 不变（补齐行delta=0，走原生流水线） |
| 补齐行的价格 | 沿用上tick（略旧），但漏采本就无新数据，这是合理近似 |
| 前端展示 | 补齐行有 `is_filled=1` 标记，可选择性提示（如灰色显示）；不加标记则与正常行无异 |
| 涨停判定(is_zt) | 补齐行用上tick的change_pct重算，结果与上tick一致，合理 |
| 红绿柱(is_body) | 补齐行price有效，阶段4正常算 |
| 存储 | 补齐行正常存Redis/MySQL，下tick若真实数据回来则覆盖 |
| 性能 | +<3ms/tick，可忽略 |
| 异常安全 | 补齐函数try/except降级，失败返回原df，不影响主流程 |

## 五、不做什么（避免过度设计）

- ❌ 不改 `FETCH_TIMEOUT`/`BATCH_SIZE`（调参有风险，且补齐已能兜住漏采后果）
- ❌ 不加超时重试（增加tick耗时，补齐更稳）
- ❌ 不改 `_recover_invalid_data_vectorized`（保持无效值恢复语义纯粹）
- ❌ 不加单例锁（已确认无双进程问题）

> 若后续发现漏采频繁（补齐数量大），再考虑源头优化（方案3调参）。当前先用"补齐+兜底"稳住结果。
