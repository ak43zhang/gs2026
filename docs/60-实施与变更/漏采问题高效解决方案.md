# 漏采问题高效解决方案

**问题**: 数据采集时批次超时/失败，导致部分股票**完全缺失**于当前tick，引发累计值（峰值净额）级联丢失  
**诊断时间**: 2026-07-27 13:42  
**状态**: 🔴 待审核（仅方案，未改代码）

---

## 一、漏采根源（已定位）

### 采集环节（`fetch_all_concurrently` 第2052行）
```python
for future in as_completed(futures, timeout=FETCH_TIMEOUT):
    ...
except TimeoutError:
    # 总超时 → 未完成的批次【直接丢弃】
    logger.warning(f"数据采集总超时，已完成{done_count}/{len(futures)}批")
```
**结论**：某批次超时 → 该批次所有股票**完全不在 df_now 中**（不是值无效，是整行缺失）。

### 当前配置（已查证）
| 参数 | 值 | 说明 |
|------|-----|------|
| `BATCH_SIZE` | 400 | 每批股票数 |
| `MAX_WORKERS` | 13 | 采集线程池 |
| `INTERVAL` | 3秒 | tick周期 |
| `FETCH_TIMEOUT` | **2.5秒** | 采集总超时 |
| 股票总数 | ~5000+ | 约13批（正好占满13线程） |
| 数据源 | `adata.stock.market.list_market_current` | 单批一次API |

**关键隐患**：`FETCH_TIMEOUT=2.5s` 很紧（tick才3s）。**任一批次慢于2.5s，就整批丢400只股票** → 大面积漏采 → 峰值大面积归零。这与"峰值突然变-"的现象高度吻合。

### 恢复环节的缺口（`_recover_invalid_data_vectorized` 第2766行）
```python
df_now_indexed.update(prev_recovery)  # ← .update()只更新【已存在】的行
```
**关键缺陷**：
- 当前恢复只处理 `is_invalid==1`（存在但值无效，如price<=0）的股票
- **完全缺失的股票没有 `is_invalid` 标记**（它压根不在df里）
- `.update()` **无法新增行** → 缺失股票永远不被恢复

### 级联丢失链
```
T1: A批次超时 → 股票X不在df_now → 无is_invalid标记 → 阶段3不管它
    → put_current存内存(无X) 
T2: X恢复采集 → 但L1(df_prev_main)无X → 累计值从0开始 → 峰值归零 → 前端"-"
```

## 二、解决方案（三选一，或组合）

### 🔴 方案1（推荐，最高效）：阶段3增加"缺失股票补齐"

**思路**：在现有阶段3恢复逻辑中，**新增一步**——识别"上一tick存在、本tick完全缺失"的股票，用上一tick数据补齐整行（标记为补齐来源）。

**实现**（新增函数，不改动现有 `_recover_invalid_data_vectorized`）：
```python
def _fill_missing_stocks(df_now, df_prev, time_full):
    """补齐【完全缺失】的股票（漏采），用上一tick数据整行补入。
    只补累计相关+基础字段，标记 is_invalid=3(补齐)，不污染正常计算。
    """
    if df_prev is None or df_prev.empty:
        return df_now, 0
    now_codes = set(df_now['stock_code'])
    prev_codes = set(df_prev['stock_code'])
    missing = prev_codes - now_codes          # 上tick有、本tick没有的
    if not missing:
        return df_now, 0
    # 从df_prev取缺失股票的整行
    fill_rows = df_prev[df_prev['stock_code'].isin(missing)].copy()
    fill_rows['is_invalid'] = 3               # 3=漏采补齐（区别于1无效/2已恢复）
    # 增量归零（补齐行本tick无新成交，volume/amount沿用上tick→delta=0）
    df_now = pd.concat([df_now, fill_rows], ignore_index=True)
    logger.info(f"[{time_full}] 补齐漏采股票 {len(missing)} 只")
    return df_now, len(missing)
```

**调用点**：阶段3现有恢复之后追加：
```python
# 阶段3现有：恢复is_invalid==1的股票
...
# 【新增】补齐完全缺失的股票（漏采）
df_now, filled = _fill_missing_stocks(df_now, df_prev, time_full)
```

**为什么高效**：
- 集合运算 `prev_codes - now_codes` 找缺失，O(n)
- 只对缺失股票 concat，通常0~几只，开销极小
- 补齐行 volume/amount 沿用上tick → 主力净额增量自然=0，**累计值完整延续**
- **不改动现有计算逻辑**，只是补回"本该在的行"

**风险**：中低。补齐行的 price/change_pct 是上tick的（略旧），但对累计净额无影响（增量=0）。需确认前端展示能接受"沿用上tick价格"。

### 🟡 方案2（兜底加固）：峰值单调性保护（Redis历史峰值）

即使方案1漏网，加一道保险——峰值**只增不减**：
```python
# calculate_main_force_and_cumulative 峰值更新后
# 从Redis hash读历史峰值，取max（峰值不可能变小）
redis_peak = _load_peak_from_redis_hash(sssj_table)  # {code: max_peak}
df_now['redis_hist_peak'] = df_now['stock_code'].map(redis_peak).fillna(0)
df_now['max_cumulative_main_net'] = df_now[
    ['max_cumulative_main_net', 'redis_hist_peak']].max(axis=1)
df_now.drop(columns=['redis_hist_peak'], inplace=True)
```
**效果**：峰值是历史最大值，天然不该变小。即使某tick数据异常，也能从Redis恢复。
**风险**：低。纯兜底，不改主逻辑。

### 🟢 方案3（治本，需实测）：减少漏采本身

排查为何批次超时：
- `FETCH_TIMEOUT` 是否过小？盘中高峰期批次响应慢
- `BATCH_SIZE` 是否过大？单批股票太多易超时
- 数据源（adata）是否限流？

**可选优化**：超时批次**重试1次**（快速重试可能成功）：
```python
# 总超时后，对未完成批次快速重试一次
failed_batches = [b for f, b in futures.items() if not f.done()]
if failed_batches:
    retry_futures = {_fetch_executor.submit(fetch_batch, b): b for b in failed_batches}
    for f in as_completed(retry_futures, timeout=2):  # 2秒快速重试
        ...
```
**风险**：中。重试增加tick耗时，需控制重试超时。

## 三、推荐组合与顺序

| 优先级 | 方案 | 效果 | 风险 | 改计算逻辑 |
|--------|------|------|------|-----------|
| **P0** | 方案1 缺失股票补齐 | **根治级联丢失** | 中低 | 否（只补行） |
| **P0** | 方案2 峰值单调兜底 | 双保险 | 低 | 否（只兜底） |
| **P1** | 方案3 超时重试 | 减少漏采源头 | 中 | 否（改采集） |

**建议**：**方案1 + 方案2 组合**——方案1从根本补齐缺失，方案2做兜底保险。两者都**不改动核心累计计算逻辑**，只是"补回本该在的数据"和"峰值防跌"。
