## 一、可行性分析（实证数据支撑）

### 采集耗时实测（1071个tick样本）
| 指标 | 值 |
|------|-----|
| 最小采集耗时 | 110.7ms |
| 平均采集耗时 | 632.2ms |
| 最大采集耗时 | 2661.5ms（逼近2.5s超时线） |
| tick周期预算 | 3000ms |
| **采集后剩余预算** | **平均 ~2368ms（3000-632）** |
| 总超时次数 | 9次（偶发，占比极低） |

### 结论：重试完全可行 ✅
1. **时间充裕**：平均采集632ms，tick预算3000ms，**剩余~2300ms**足够重试1-2个失败批次
2. **只重试失败批次**：正常13批中通常只有0~2批失败，重试成本 ≈ 130~300ms（单批并行）
3. **超时是偶发抖动**：9次/1071tick，说明是**瞬时网络抖动**，重试**大概率成功**拿到真实数据
4. **重试拿真实数据** > 补齐用旧数据：这是本方案比v1"补齐"更优的核心——**数据真实**

### 你的思路是对的
"重试某批 + 性能加不了多少" —— 实测支撑：单批重试~130-300ms，远小于2300ms余量。**采纳为主方案。**

## 二、最优方案（重试为主 + 补齐兜底）

### 分层设计
```
第1层（主）: 失败批次即时重试 → 拿【真实数据】       ← 解决90%+漏采
第2层（兜底）: 重试仍失败的极少数 → 用上tick补齐      ← 兜住剩余，防级联
第3层（保险）: 峰值Redis历史值max → 防万一            ← 双保险
```

**为什么三层而非单一**：重试解决绝大多数（真实数据最优）；万一重试也失败（数据源持续故障），补齐兜住不让累计值断裂；峰值兜底是最后防线。层层递进，既追求真实又保证不丢。

## 三、详细设计

### 设计1（主）：`fetch_all_concurrently` 增加失败批次重试

**核心思路**：
1. 第1轮采集后，**用"请求的代码"减"实际返回的代码"**精确识别缺失股票（比只看future状态更准，能抓住超时、异常、空返回、部分返回**所有**漏采情形）
2. 对缺失股票**重新分批、重试1轮**（快速超时，避免拖累tick）
3. 重试结果合并

```python
def fetch_all_concurrently(codes):
    """并发采集 + 失败批次重试（v2）。

    第1轮采集后，识别缺失代码(请求-返回)，对缺失代码重试1轮。
    重试用更短超时(RETRY_TIMEOUT)，避免拖累tick周期。
    """
    def _fetch_round(code_list, timeout):
        """一轮采集，返回 (合并df, 已成功返回的代码集合)"""
        batches = batch_codes(code_list, BATCH_SIZE)
        futures = {_fetch_executor.submit(fetch_batch, b): b for b in batches}
        collected = []
        try:
            for future in as_completed(futures, timeout=timeout):
                try:
                    df = future.result(timeout=0.5)
                    if not df.empty:
                        collected.append(df)
                except Exception as e:
                    logger.warning(f"[采集] 单批异常: {e}")
                    continue
        except TimeoutError:
            done = sum(1 for f in futures if f.done())
            logger.warning(f"[采集] 本轮超时({timeout}s)，完成{done}/{len(futures)}批")
        if collected:
            df_all = pd.concat(collected, ignore_index=True)
            got_codes = set(df_all['stock_code'].astype(str).str.zfill(6)) \
                        if 'stock_code' in df_all.columns else set()
            return df_all, got_codes
        return pd.DataFrame(), set()

    # 第1轮
    all_codes = set(str(c).zfill(6) for c in codes)
    df1, got1 = _fetch_round(codes, FETCH_TIMEOUT)
    missing = all_codes - got1

    # 第2轮：只重试缺失的代码
    if missing:
        logger.warning(f"[采集] 第1轮缺失{len(missing)}只，重试...")
        df2, got2 = _fetch_round(list(missing), RETRY_TIMEOUT)
        still_missing = missing - got2
        if still_missing:
            logger.warning(f"[采集] 重试后仍缺失{len(still_missing)}只（将由补齐兜底）")
        frames = [d for d in (df1, df2) if not d.empty]
        return pd.concat(frames, ignore_index=True) if frames else pd.DataFrame()

    return df1
```

**新增常量**：
```python
RETRY_TIMEOUT = 1.5   # 重试轮超时（秒），短于首轮，控制tick总耗时
```

**时间上界保证**：首轮 FETCH_TIMEOUT(2.5s) + 重试 RETRY_TIMEOUT(1.5s) = 最坏4s。但：
- 首轮正常632ms完成，不会吃满2.5s
- 只有缺失时才触发重试，且重试批次少
- **实际最坏 ≈ 632ms + 300ms ≈ 1s，远小于3s**
- 极端持续故障时，首轮2.5s+重试1.5s=4s > 3s tick，会延后下一tick —— 但这种极端情况本就该告警（数据源挂了）

### 设计2（兜底）：重试仍失败 → 补齐上tick数据

重试后仍缺失的极少数股票（数据源持续故障），用 `_fill_missing_stocks` 补齐上tick整行（delta=0，累计延续）。**这是v1方案降级为第2层兜底**——只在重试也拿不到时才用旧数据。

（实现同 v1 的 `_fill_missing_stocks`，位置在阶段3）

### 设计3（保险）：峰值Redis历史值兜底 + NaN防护

## 四、方案对比（v1补齐 vs v2重试）

| 维度 | v1（补齐为主） | v2（重试为主）✅ |
|------|---------------|----------------|
| 数据真实性 | ❌ 用旧数据 | ✅ **重试拿真实数据** |
| 漏采解决率 | 100%兜住但数据旧 | 90%+真实 + 剩余兜底 |
| 性能 | +<3ms | +~130-300ms（仅缺失时） |
| tick超时风险 | 无 | 极端故障时最坏4s（可告警） |
| 复杂度 | 低 | 中 |

**结论**：v2更优。多花~200ms（仅在漏采时）换**真实数据**，值得。补齐降级为兜底，双重保障。

## 五、副作用与风险

| 关注点 | 评估 |
|--------|------|
| 正常tick性能 | ✅ 无影响（无缺失则不重试，走原路径） |
| 漏采tick性能 | +130-300ms（重试1-2批），预算内 |
| 极端持续故障 | 最坏4s>3s，会延后下tick；但此时数据源已挂，应告警而非硬扛 |
| 累计计算逻辑 | ✅ 不变 |
| 重试识别准确性 | ✅ 用"请求-返回"集合差，抓住所有漏采情形（超时/异常/空/部分） |
| 异常安全 | 每轮try/except降级 |

**风险控制**：`RETRY_TIMEOUT=1.5s` 限制重试上界；只重试1轮不无限重试；重试仍失败有补齐兜底。
