## 二、架构设计（行业最优：策略模式 + 注册表 + 管道）

### 2.1 设计原则
- **开闭原则**：新增模式只写一个策略类 + 注册，**不改任何现有代码**。
- **单一职责**：数据加载、指标计算、模式判定、结果合并、落库，各司其职。
- **数据复用**：一次性加载共享数据（日行情、交易日历），所有模式共用，避免重复查询。
- **可测试**：每个模式策略独立可单测；纯函数式计算（DataFrame in → DataFrame out）。
- **幂等**：支持全量重算与增量（按日期范围）两种模式，重算安全。

### 2.2 目录结构

```

├── runner.py                 # 主入口：编排整个流程（CLI 可调）
├── context.py                # 共享数据上下文（日行情、交易日历，一次加载多处复用）
├── base.py                   # GreenBondStrategy 抽象基类 + 结果数据结构
```

### 2.3 核心抽象

**策略基类 `base.py`**：
```python
from abc import ABC, abstractmethod
import pandas as pd

class GreenBondStrategy(ABC):
    """绿名单模式策略基类。每个模式实现一个子类。"""

    # 模式编号（写入 green_bond_list.model 字段），字符串，全局唯一
    model: str = None
    # 模式名称/描述（日志、文档用）
    name: str = ""
    # 阈值等参数（子类覆盖，集中声明便于调参）
    params: dict = {}

    @abstractmethod
    def evaluate(self, ctx: "GreenBondContext") -> pd.DataFrame:
        """
        输入共享上下文（含日行情+已算窗口指标+交易日历），
        输出满足本模式的记录 DataFrame，列固定为 [code, trigger_date]。
        （buy_date 由框架统一用 trigger_date → next_trade_date 映射，避免各模式重复实现）
        """
        ...
```

**共享上下文 `context.py`**：
```python
class GreenBondContext:
    """一次性加载 + 预计算，供所有策略复用，避免重复查询/重复算窗口。"""
    def __init__(self, bond_daily: pd.DataFrame, calendar: pd.DataFrame):
        self.bond_daily = bond_daily          # 日行情（已按 code,date 排序）
        self.calendar = calendar              # 交易日历（含 next_trade_date）
        self._windowed = None                 # 惰性计算的窗口指标缓存

    @property
    def windowed(self) -> pd.DataFrame:
        """前1日/前2日等 lag 指标，惰性计算一次，多模式共享。"""
        if self._windowed is None:
            self._windowed = self._compute_window_metrics()
        return self._windowed
```

**注册表 `registry.py`**：
```python
_REGISTRY: dict[str, GreenBondStrategy] = {}

def register(strategy_cls):
    """装饰器：注册一个策略。model 唯一性校验。"""
    inst = strategy_cls()
    if inst.model in _REGISTRY:
        raise ValueError(f"重复的 model: {inst.model}")
    _REGISTRY[inst.model] = inst
    return strategy_cls

def all_strategies() -> list:
    return list(_REGISTRY.values())
```

**一个模式的样子（`strategies/model01_zgzf.py`）**：
```python
@register
class Model01Zgzf(GreenBondStrategy):
    model = "1"
    name = "当日最高涨幅>4"
    params = {"zgzf_threshold": 4.0}

    def evaluate(self, ctx):
        df = ctx.bond_daily
        hit = df[df["zgzf"] > self.params["zgzf_threshold"]]
        return hit[["code", "trigger_date"]].copy()  # trigger_date = 当日
```

**模式2（`strategies/model02_stzf_sum.py`）**：
```python
@register
class Model02StzfSum(GreenBondStrategy):
    model = "2"
    name = "前两日实体涨幅和>4且均>0"
    params = {"sum_threshold": 4.0, "min_each": 0.0}

    def evaluate(self, ctx):
        w = ctx.windowed  # 含 prev1_stzf, prev2_stzf
        p = self.params
        hit = w[(w["prev1_stzf"] > p["min_each"]) &
                (w["prev2_stzf"] > p["min_each"]) &
                (w["prev1_stzf"] + w["prev2_stzf"] > p["sum_threshold"])]
        return hit[["code", "trigger_date"]].copy()
```

### 2.4 主流程 `runner.py`（编排）

```
1. repository.load_bond_daily(start, end)      # 一次加载日行情
2. repository.load_calendar()                  # 一次加载交易日历
3. ctx = GreenBondContext(bond_daily, calendar)
4. results = []
   for strat in registry.all_strategies():     # 遍历所有已注册模式
       hits = strat.evaluate(ctx)              # [code, trigger_date]
       hits["model"] = strat.model
       results.append(hits)
5. merged = concat(results)                    # 合并所有模式
6. merged["buy_date"] = calendar.map_next(merged["trigger_date"])  # 批量映射下一交易日
7. dedup = merged.groupby(["code","buy_date"]).model.min()          # 去重取最小model（与Scala一致）
8. repository.write(dedup, mode="full"|"incremental")               # 落库
```

### 2.5 落库策略（幂等）

两种写入模式（CLI 参数 `--mode`）：
- **full（全量重算）**：`DELETE FROM green_bond_list` → 批量 INSERT（对齐 Scala 现有行为，默认）。
- **incremental（增量按日期）**：只删指定 `buy_date` 范围再插入，适合每日增量跑，不动历史。

> 推荐给 `green_bond_list` 加唯一索引 `(code, buy_date)` 以支持 `ON DUPLICATE KEY UPDATE` 幂等写入（现表无主键/唯一键）。是否加索引由你定；不加则用 DELETE+INSERT 方案。

## 三、关键技术决策

| 决策点 | 方案 | 理由 |
|---|---|---|
| 扩展机制 | 策略类 + `@register` 装饰器注册表 | 新增模式=新增1文件+注册，零改动现有代码（开闭原则） |
| buy_date 计算 | 框架统一做 trigger_date→next_trade_date **批量映射** | 各模式只输出触发日，不重复实现日历逻辑；批量 map 避免逐行查库 |
| 窗口指标 | Context 惰性计算 lag(prev1/prev2...)，多模式共享 | 一次算，处处用；用 pandas `groupby+shift` 替代 Spark 窗口 |
| 数据加载 | Repository 层集中 SQL，一次性加载全量/区间 | 与计算解耦，SQL 可审查、可优化、可加索引 |
| 计算引擎 | pandas（DataFrame 向量化） | 债券日行情数据量小（千级 code × 日），单机 pandas 足够，无需 Spark |
| 去重 | groupby(code,buy_date).model.min() | 完全对齐 Scala 语义 |
| 落库幂等 | full(DELETE+INSERT) / incremental(按日期) | 支持全量重算 + 每日增量两种运维场景 |
| 参数管理 | 每个策略 `params` dict 声明阈值 | 调参集中、可读；未来可外置配置文件 |

## 四、pandas 实现窗口指标（替代 Spark lag）

Scala 的 `Window.partitionBy(code).orderBy(date) + lag()`，pandas 等价：
```python
df = df.sort_values(["code", "date"])
g = df.groupby("code")
df["prev1_zgzf"] = g["zgzf"].shift(1)
df["prev1_stzf"] = g["stzf"].shift(1)
df["prev2_stzf"] = g["stzf"].shift(2)
df["trigger_date"] = df["date"]   # 触发日=当日
```
next_trade_date 批量映射（替代 Spark lead + join）：
```python
cal = calendar.sort_values("trade_date")
cal["next_trade_date"] = cal["trade_date"].shift(-1)
next_map = dict(zip(cal["trade_date"], cal["next_trade_date"]))
merged["buy_date"] = merged["trigger_date"].map(next_map)
```

## 九、唯一索引与幂等写入（落库详设）

### 9.1 现状（已实测确认）
- `green_bond_list` 表**当前无任何索引**
- `code` 实际最大长度 6，`model` 实际最大长度 1
- **无重复 (code, buy_date)** → 可直接建唯一索引，无需预清理

### 9.2 表结构调整 DDL
```sql
-- 1. 收窄列类型（text → varchar，text 无法直接建唯一索引且无必要）
ALTER TABLE green_bond_list
    MODIFY COLUMN code  VARCHAR(16) NOT NULL,
    MODIFY COLUMN model VARCHAR(8)  NOT NULL;

-- 2. buy_date 非空（唯一索引要求）
ALTER TABLE green_bond_list
    MODIFY COLUMN buy_date DATE NOT NULL;

-- 3. 建唯一索引（幂等写入的基础）
ALTER TABLE green_bond_list
    ADD UNIQUE KEY uk_code_buydate (code, buy_date);
```

> 说明：唯一键选 `(code, buy_date)` 而非含 model，因业务语义是"同一债券同一 buy_date 只保留一条（取 model 最小）"，与 Scala 的 `groupBy(code, buy_date).min(model)` 完全一致。索引同时加速消费端 `WHERE buy_date=?` 查询。

### 9.3 幂等写入逻辑
- 计算侧已做 `groupby(code, buy_date).model.min()` 去重，保证写入前无冲突。
- 落库用 `INSERT ... ON DUPLICATE KEY UPDATE model=VALUES(model)`（复用 `MysqlTool.batch_insert(key_fields=['model'])`）。
- **full 模式**：`DELETE FROM green_bond_list` → 批量 upsert（全量重算，对齐 Scala）。
- **incremental 模式**：仅对指定 `buy_date` 范围 upsert，历史数据不动；同一天重复跑结果幂等（唯一键保证不重复插入）。

## 十、验收方法（一致性校验）

新增校验脚本 `tools/green_bond/verify.py`：

1. **备份基线**：跑之前先把现有 `green_bond_list` 快照存入临时表 `green_bond_list_baseline`（或 DataFrame 落 CSV）。
2. **运行新系统**：`python -m gs2026.tools.green_bond.runner --mode full`。
3. **集合比对**：以 `(code, buy_date, model)` 三元组为键，比对新旧两个结果集：
   - `只在旧` 的记录数（新系统漏掉的）
   - `只在新` 的记录数（新系统多出的）
   - `交集` 记录数
   - 输出差异样本（各取前 20 条）供人工核对
4. **判定标准**：
   - 若差异为 0 → 逻辑完全一致，验收通过。
   - 若有差异 → 逐条分析原因（如 Scala 用 `zgzf > 4` 严格大于、边界 code 数据差异、交易日历口径），确认是"新系统更正确"还是"逻辑偏差"，修正后重跑。
5. **抽样验证**：另取 2~3 个历史交易日，人工核对某几只债券的 zgzf/stzf 原始值与判定结果，确认无误。

> 注：现有 `green_bond_list` 是 Scala 长期跑出来的历史沉淀，可能包含旧阈值/旧逻辑的数据。验收以"**同一份 `data_bond_daily_ods` 输入，新 Python 系统 vs Scala 逻辑，产出应一致**"为准；若历史表因口径变更有差异，以最新 Scala 逻辑为基准。

## 十一、新增模式流程（SOP）

新增一个绿名单模式（如 model=3），完整步骤：

1. **确定模式定义**：明确触发条件、用到 `data_bond_daily_ods` 的哪些字段、阈值、model 编号（需全局唯一、字符串）。
2. **新建策略文件** `strategies/modelNN_xxx.py`：
   ```python
   from gs2026.tools.green_bond.base import GreenBondStrategy
   from gs2026.tools.green_bond.registry import register

   @register
   class Model03DoubleLimit(GreenBondStrategy):
       model = "3"
       name = "连续2日涨停"
       params = {"days": 2}

       def evaluate(self, ctx):
           # 用 ctx.bond_daily / ctx.windowed 计算
           w = ctx.windowed
           hit = w[...]  # 你的条件
           return hit[["code", "trigger_date"]].copy()
   ```
3. **注册导入**：在 `strategies/__init__.py` 增加一行 `from . import model03_double_limit`。
4. **（可选）扩展窗口指标**：若模式需要新的 lag 指标（如 prev3、连板计数），在 `context.py` 的 `_compute_window_metrics` 里补充列（惰性计算，所有模式共享，只算一次）。
5. **跑验证**：`runner --mode incremental --start <日期> --end <日期>`，检查该 model 产出是否符合预期。
6. **更新文档**：在 `README.md` 的"模式清单"表格追加一行（model 编号、名称、条件、字段、阈值、上线日期）。
7. **上线**：接入定时任务全量/增量跑。

**约束**：
- `model` 编号一旦上线**不可复用/不可变更语义**（消费端与历史数据依赖它）。
- 新增模式**只允许新增文件 + 注册 + 可选扩列**，禁止修改 runner/repository 主流程（开闭原则）。
- 新模式的 `evaluate` 必须是纯函数（无副作用、不写库），落库统一由框架负责。

## 十二、删除/下线模式流程（SOP）

下线一个模式（如不再需要 model=2），完整步骤：

1. **评估影响**：确认消费端（`green_bond_list_cache.py` 等）是否对该 model 有特殊依赖（现状消费端只按 buy_date 查 code，不区分 model，故通常无影响）。
2. **停止产出**（二选一）：
   - **软下线（推荐）**：在策略类加 `enabled = False`，注册表跳过 `enabled=False` 的策略。保留代码与历史数据，可快速恢复。
   - **硬删除**：删除 `strategies/modelNN_xxx.py` + 移除 `strategies/__init__.py` 的 import 行。
3. **历史数据处理**（三选一，按需）：
   - **保留**：历史该 model 记录不动（默认，最安全）。
   - **清理该 model 全部历史**：`DELETE FROM green_bond_list WHERE model = 'N'`（需确认无消费依赖）。
   - **重算覆盖**：跑一次 full 全量重算，产出自然不再含该 model（但历史其他 model 记录会按当前逻辑重建，需谨慎）。
4. **更新文档**：`README.md` 模式清单中标注该 model 为"已下线（日期 + 原因）"，保留记录以备追溯。
5. **model 编号处理**：下线的 model 编号**不建议回收复用**（避免与历史数据语义混淆），新模式继续用新编号。

**约束**：
- 软下线优先于硬删除（可回滚）。
- 删除模式**不得影响其他模式**的产出（策略间完全独立）。
- 清理历史数据前必须备份（`trash > rm` 原则：先快照到 baseline 表再 DELETE）。
