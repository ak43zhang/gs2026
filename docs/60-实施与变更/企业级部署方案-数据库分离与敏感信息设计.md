## §5 库名不一致调查结论（先说这个，影响全局）

### 真相：不是"不一致"，而是"双库并存"

系统**实际同时使用两个数据库**：

| 数据库 | 表数 | 用途 | 代码引用 |
|--------|------|------|----------|
| **gs** | 517张 | 主库（采集/分析/监控/交易） | 全项目 |
| **gs_platform** | **3张** | 报告中心 | `dashboard2/models/database.py` |

**gs_platform 的3张表**：`reports`、`report_types`、`report_tasks`（报告中心功能）

### 关键发现：项目已有多库基础设施

`src/gs2026/dashboard2/models/database.py` 已经实现了双库管理：

```python
DATABASE_CONFIG = {
    'gs':          {...},   # 主库
    'gs_platform': {...},   # 报告中心库
}
def get_engine(db_name='gs'):   # 按库名取引擎
def init_platform_db():          # SQLAlchemy ORM 自动建表
```

**这意味着**：你的决策6（分库）不是从零开始，项目本就是多库设计，只是没有贯彻到底。这让分库方案的实施难度大大降低。

### 数据库清单（当前MySQL实例）

```
gs             ← 主库（517表，196GB）
gs_platform    ← 报告中心（3表）
gs_test        ← 测试库
sakila/world   ← MySQL自带示例（无关，可删）
```

## §4 敏感信息环境变量化（决策4：3个方案供选）

### 现状：明文散落在2处

| 位置 | 明文内容 |
|------|----------|
| `configs/settings.yaml` | DB密码、阶跃API密钥、火山API密钥、Flask secret |
| `dashboard2/models/database.py` | **硬编码**DB密码（password: '123456'） |

### 方案A：.env 环境变量文件（推荐，改动最小）

**做法**：敏感值移到 `.env`（不提交git），配置文件读环境变量

```bash
# .env (git忽略)
GS_MYSQL_HOST=192.168.x.x
GS_MYSQL_PASSWORD=<强密码>
GS_STEP_API_KEY=xxx
GS_VOLCENGINE_API_KEY=xxx
GS_DASHBOARD_SECRET=xxx
```

```python
# config_util.py 改造：优先读环境变量，回退yaml
import os
def get_secret(key, yaml_path):
    return os.getenv(key) or get_config(yaml_path)
```

| 优点 | 缺点 |
|------|------|
| 改动小、python-dotenv已在依赖中 | 密钥仍在服务器明文文件 |
| 标准做法、迁移友好 | — |

### 方案B：配置模板 + 部署时填充

**做法**：提交 `settings.yaml.template`（占位符），部署时生成实际配置

```yaml
mysql:
    password: "${MYSQL_PASSWORD}"   # 部署脚本替换
```

| 优点 | 缺点 |
|------|------|
| git中零敏感信息 | 需部署脚本处理替换 |
| 模板清晰 | 多份环境需多份配置 |

### 方案C：Windows凭据管理器 / 加密存储

**做法**：用 Windows Credential Manager 或 `cryptography` 加密密钥文件

| 优点 | 缺点 |
|------|------|
| 安全性最高 | 实现复杂、依赖平台 |
| 符合企业安全规范 | 运维成本高 |

### 我的推荐

**方案A + 方案B 组合**：
1. 提交 `settings.yaml.template`（git无敏感信息）
2. 实际密钥走 `.env`（git忽略）
3. 统一改造 `config_util.py` 和 `database.py` 读环境变量

→ 请选择 A / B / C / A+B。

## §6 业务表与数据表分库设计（决策6：核心方案）

### 设计目标

把"业务表"（小、需备份、需建表）和"数据表"（大、可重采、按日期生成）分离到不同库，实现：
- 备份只需备份业务库（2.5GB vs 196GB）
- 新服务器只需建业务库
- 数据库职责清晰

### 方案总览：三库分离

| 新库名 | 内容 | 来源 | 大小 | 备份策略 |
|--------|------|------|------|----------|
| **gs_biz**（业务库） | C类固定表 + gs_platform | 102+3张 | ~2.5GB | 每日备份 |
| **gs_data**（数据库） | A类每日动态表 | 306张 | 178GB | 不备份，可重采 |
| **gs_archive**（归档库） | B类年度表 | 108张 | 10.7GB | 按需备份 |

### 方案对比（三选一）

#### 方案1：完全三库分离（最彻底）

```
gs_biz     ← 业务表（账户/命中/交易/调度/报告等）
gs_data    ← 每日动态表（行情/日线）
gs_archive ← 年度归档表（分析/公告）
```

| 优点 | 缺点 |
|------|------|
| 职责最清晰、备份最优 | 改造量大（跨库查询处理） |
| 新服务器建库最简单 | 需改所有表名引用逻辑 |

⚠️ **风险**：代码中大量 `SELECT ... FROM monitor_gp_sssj_xxx` 需加库前缀，跨库JOIN需处理。改造量评估：**高**。

#### 方案2：双库分离（业务 vs 数据，推荐）

```
gs_biz  ← 业务表 + 年度归档表（C类+B类，210张，13GB）
gs      ← 每日动态表（A类，306张，178GB）保持原库名
```

| 优点 | 缺点 |
|------|------|
| 业务库独立备份/迁移 | 仍有一定改造 |
| A类保留在gs，动态建表逻辑不用改 | B类跨库需调整 |
| 利用已有 `get_engine(db_name)` 机制 | — |

#### 方案3：渐进式（仅新增分离，最稳妥）

```
gs           ← 保持现状（所有表不动）
gs_biz       ← 仅新建的核心业务表走新库
```

- 存量不动，新功能表进 `gs_biz`
- 逐步迁移，风险最低
- 缺点：分离不彻底，过渡期双轨

### 改造复杂度评估

| 方案 | 代码改造量 | 风险 | 备份收益 | 部署收益 |
|------|-----------|------|----------|----------|
| 方案1·三库 | 🔴 高 | 🔴 高 | 🟢 最优 | 🟢 最优 |
| 方案2·双库 | 🟠 中 | 🟠 中 | 🟢 优 | 🟢 优 |
| 方案3·渐进 | 🟢 低 | 🟢 低 | 🟡 一般 | 🟡 一般 |

### 我的推荐：方案2（双库分离）

**理由**：
1. 业务表（210张/13GB）独立成 `gs_biz`，可每日备份、快速迁移
2. A类动态表保留在 `gs`，**动态建表代码零改造**（这是最容易出错的部分）
3. 项目已有 `get_engine(db_name)` 双库机制，扩展成本低
4. 新服务器部署只需：建 `gs_biz`（导入结构）+ 建空 `gs`（程序自动建动态表）

**关键改造点**（方案2）：
- `mysql_util.py`：增加 `gs_biz` 引擎（参照现有 `database.py`）
- 业务表的读写指向 `gs_biz`
- B类年度表迁移到 `gs_biz`（或保留gs，视你意见）
- 跨库查询（业务表JOIN动态表）需评估——**这是唯一风险点，实施前我会先扫描全部跨库JOIN**
