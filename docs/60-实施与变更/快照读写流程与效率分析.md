# 快照读写流程与效率分析

**目标**: 分析阶段2/3实际快照读写流程，确认是否一次性写入，评估效率  
**状态**: 待审核

---

## 一、核心结论（先给答案）

| 问题 | 答案 |
|------|------|
| **写入是一次性的吗？** | ✅ **是**。每tick收集全部状态，1次Pipeline写Redis（大盘+个券合并2个HSET） |
| **读取是一次性的吗？** | ✅ **是**。日期切换时1次恢复，按日期缓存，多个consumer共享 |
| **写入频率** | 每tick 1次（Redis），每30秒1次（MySQL） |
| **读取频率** | 每个交易日仅1次（首tick恢复，后续命中缓存） |

## 二、写入流程详解

### 2.1 写入触发点（每tick 1次）

```
deal_zq_works() 主tick末尾（第2067行）
    ↓
_save_intermediate_snapshot(date_str, time_full)
    ↓
① _collect_mkt_snapshot()      # 收集大盘14字段（纯内存）
② _collect_bonds_snapshot()    # 收集个券400只×7字段（纯内存）
    ↓
③ _snapshot_executor.submit(save_snapshot, ...)   # 提交线程池（不阻塞）
    ↓（异步线程中执行）
④ save_snapshot()
    ├── Redis: 1次Pipeline（2个HSET + 2个EXPIRE）
    └── MySQL: 每30秒才执行（2次INSERT）
```

### 2.2 写入是否"一次性"

**✅ 是一次性写入**，关键证据：

```python
# save_snapshot() 中，大盘+个券合并到1次Pipeline
pipe = r.pipeline()
pipe.hset(mkt_key, str(time_sec), mkt_json)      # 大盘（1个大JSON）
pipe.expire(mkt_key, _REDIS_EXPIRE)
pipe.hset(bonds_key, str(time_sec), bonds_json)  # 个券400只（1个大JSON）
pipe.expire(bonds_key, _REDIS_EXPIRE)
pipe.execute()  # ← 1次网络往返，4条命令一起发送
```

**关键点**：
- 大盘14字段 → 序列化为1个JSON → 1个HSET
- 个券400只×7字段 → 序列化为1个JSON → 1个HSET
- 两者通过Pipeline合并 → **1次网络往返**

**不是**逐字段写、也**不是**逐债券写。

### 2.3 写入数据量

| 内容 | 大小 | 说明 |
|------|------|------|
| 大盘JSON | ~10KB | 14字段，含500点形态历史+斜率缓存 |
| 个券JSON | ~200KB | 400只×(60+300斜率点+其他) |
| 单tick合计 | ~210KB | 1次Pipeline发送 |

## 三、读取流程详解

### 3.1 读取触发点（每日仅1次）

```
日期切换时（新交易日首tick）
    ↓
4个compute函数各自触发日期切换分支：
    ① compute_mkt_trend_indicators   → _mkt_snap_recover_market_trend()
    ② compute_market_indicators      → _mkt_snap_recover_market_indicators()
    ③ compute_indicators             → _snap_recover_bond_slopes()
    ④ compute_ext_indicators         → _snap_recover_bond_ext()
    ↓
全部调用 recover_snapshot(date)
    ↓
【关键】按日期缓存机制
    ├── 首次调用：查Redis（1次HGET大盘 + 1次HGET个券）
    └── 后续3次：命中 _recovered_cache，直接返回（0次网络IO）
```

### 3.2 读取是否"一次性"

**✅ 是一次性读取**，关键证据：

```python
# recover_snapshot() 开头
if _recovered_cache['date'] == date:
    return _recovered_cache['mkt'], _recovered_cache['bonds']  # 直接返回缓存

# 首次才查Redis
timestamps = r.hkeys(mkt_key)                # 取所有时间戳
latest = max(...)                            # 找最新
mkt_data = r.hget(mkt_key, str(latest))      # 1次HGET大盘
bonds_data = r.hget(bonds_key, str(latest))  # 1次HGET个券
_recovered_cache = {'date': date, 'mkt': ..., 'bonds': ...}  # 写缓存
```

**关键点**：
- 4个consumer（大盘趋势/大盘指标/个券斜率/个券扩展）
- 只有**第1个**真正查Redis
- 后**3个**命中缓存，**0次网络IO**

### 3.3 读取次数对比

| 场景 | 无缓存设计 | 当前缓存设计 |
|------|-----------|-------------|
| 大盘趋势恢复 | 查Redis | 查Redis（首次） |
| 大盘指标恢复 | 查Redis | 命中缓存 |
| 个券斜率恢复 | 查Redis | 命中缓存 |
| 个券扩展恢复 | 查Redis | 命中缓存 |
| **合计网络IO** | **4次** | **1次** |

## 四、效率分析

### 4.1 主tick性能影响（关键）

| 操作 | 位置 | 耗时 | 是否阻塞主tick |
|------|------|------|----------------|
| 收集大盘快照 | 主线程 | <0.5ms | 是（但极快） |
| 收集个券快照 | 主线程 | <2ms | 是（400只遍历） |
| 提交线程池 | 主线程 | <0.1ms | 是（仅submit） |
| **主线程合计** | - | **<3ms** | **是** |
| Redis写入 | 异步线程 | ~3ms | ❌ 否 |
| MySQL写入 | 异步线程 | ~10ms | ❌ 否（每30秒） |

**结论**：主tick只增加 **<3ms**（收集+提交），真正的IO在异步线程完成。

### 4.2 写入效率

| 指标 | 数值 | 评价 |
|------|------|------|
| Redis网络往返 | 1次/tick | ✅ 优（Pipeline合并） |
| Redis命令数 | 4条/tick | ✅ 优（HSET×2+EXPIRE×2） |
| MySQL写入 | 2条/30秒 | ✅ 优（稀疏，覆盖更新） |
| 数据量 | ~210KB/tick | 🟡 中（可优化） |

### 4.3 读取效率

| 指标 | 数值 | 评价 |
|------|------|------|
| 恢复网络往返 | 1次/日 | ✅ 优（按日期缓存） |
| 恢复耗时 | <20ms | ✅ 优（仅日期切换） |
| consumer共享 | 4→1 | ✅ 优（缓存去重） |

## 五、潜在优化点（供讨论）

### 5.1 收集个券快照的遍历开销

```python
# 当前：每tick遍历400只债券收集
def _collect_bonds_snapshot():
    bonds = {}
    for code in _slope_buf_short.keys():  # 400次循环
        bonds[code] = {
            'ss': list(_slope_buf_short.get(code, [])),  # deque→list拷贝
            'sl': list(_slope_buf_long.get(code, [])),
            'epc': [[int(t), p] for t, p in _ext_price_cache.get(code, [])],  # 列表推导
            ...
        }
    return bonds
```

**开销**：400只 × (2个deque拷贝 + 1个列表推导) ≈ 1-2ms

**优化选项**：
| 方案 | 效果 | 代价 |
|------|------|------|
| A. 保持现状 | <3ms可接受 | 无 |
| B. 降低频率（每10tick收集1次） | 减少90%收集开销 | 重启最多丢30秒 |
| C. 增量收集（只收集变化的债券） | 减少拷贝 | 逻辑复杂 |

### 5.2 JSON序列化开销

```python
# 在异步线程中序列化，不阻塞主tick
mkt_json = json.dumps(mkt_snapshot)      # ~10KB
bonds_json = json.dumps(bonds_snapshot)  # ~200KB
```

**开销**：~200KB序列化 ≈ 2-3ms（异步线程，不影响主tick）

**优化选项**：
| 方案 | 效果 | 代价 |
|------|------|------|
| A. 保持json | 兼容性好 | 慢 |
| B. 改用orjson | 快3-5倍 | 新依赖 |
| C. 改用msgpack | 快+体积小30% | 不可读 |

### 5.3 数据量优化

```
当前：210KB/tick，Redis保留12小时
若每3秒1tick：4800tick/天 × 210KB = ~1GB
```

**注意**：因为是**覆盖写入**（相同time_sec的field会覆盖），实际Redis只保留不同时间戳的快照。

**关键疑问**：当前设计每个tick用不同time_sec作为field，所以**不会覆盖**，会累积4800个field！

## 六、发现的问题（需确认）

### 🔴 问题：Redis field累积

```python
# 当前：field = time_sec，每tick不同
pipe.hset(mkt_key, str(time_sec), mkt_json)
# 37800, 37803, 37806... 每个都是新field
```

**后果**：
- 一天累积4800个field（不是覆盖）
- `snapshot:bonds:20260726` = 4800 × 200KB = **960MB单key**
- 恢复时`hkeys`返回4800个时间戳，`max()`计算

**但恢复只需要最新1个**，历史field是浪费。

### 优化方案

| 方案 | 说明 | 效果 |
|------|------|------|
| **A. 只存最新（推荐）** | field固定为"latest"，每tick覆盖 | Redis只保留1份，~210KB |
| B. 定期清理 | 保留最近N个，删除旧field | 复杂 |
| C. 保持现状 | 需要历史快照回溯时有用 | 占用大 |

**方案A实现**：
```python
# 固定field，每tick覆盖
pipe.hset(mkt_key, "latest", mkt_json)   # 覆盖
pipe.hset(bonds_key, "latest", bonds_json)
# 恢复：直接 HGET latest
mkt_data = r.hget(mkt_key, "latest")
```

**收益**：
- Redis：960MB → 210KB（-99.98%）
- 恢复：无需hkeys+max，直接HGET
- 写入：无变化（仍1次Pipeline）
