## ⚠️ 重要更正：双进程race结论已被推翻

**初版诊断（错误）**：我最初认为是"双进程抢写共享表"导致峰值丢失。**这个结论是错的。**

**实证推翻**：
| 进程 | CPU时间 | 内存 | 结论 |
|------|---------|------|------|
| venv python (父) | **0秒** | **3MB** | **空壳launcher，不干活** |
| python312 (子) | 2076秒 | 183MB | **真正的worker** |

**真相**：
- venv 的 `pyvenv.cfg` 中 `base-executable = F:\python312\python.exe`
- PyCharm 用 venv python 启动脚本时，venv python 只是**薄启动器(stub)**，立即 re-exec 到 base 解释器(python312)
- 所以 venv 进程 CPU=0、内存=3MB，只是**等待子进程**
- **实际只有 1 个 worker 进程**（python312），**不存在双写竞争**
- 验证：杀掉 python312 子进程后，venv 父进程（空壳）也随之退出，且**没有新进程重生**（非保活机制）

**这解释了你的疑问**：你只启动了1个 monitor_stock，看到2个进程是 PyCharm+venv 的正常启动机制，不是真的跑了两份。

## 三、（作废）以下为初版错误分析，仅留存备查



通过进程树分析，确认**每个监控程序都在双实例运行**：

```
monitor_stock.py:
  PID 48800 (.venv\Scripts\python.exe)   ← 父进程: pycharm64.exe（手动启动）
  PID 32664 (F:\python312\python.exe)    ← 父进程: PID 48800（dashboard进程管理器启动）

monitor_bond / monitor_industry / monitor_dp_signal:
  同样都是 2 个进程！
```

**两个进程的行为**：
1. 各自独立采集数据（同一时刻可能拿到**略有差异**的股票集合）
2. 各自维护**独立的内存缓存**（`_MAIN_NET_TICK_CACHE`，进程隔离）
3. 都写入**同一张表** `monitor_gp_sssj_{date}`（Redis + MySQL，仅按日期命名，无进程隔离）

### 为什么会丢失峰值？

```
时间线（两进程都在跑 10:58:51 → 10:59:06 这个tick）：

进程A (PID 48800):
  10:58:51 算出 股票X 峰值=240.7万 → 写表 ✓
  10:59:06 内存有X的峰值 → L1命中 → 继承240.7万 → 写表 ✓

进程B (PID 32664):
  10:59:06 这个tick，X股票【恰好这次采集缺失】或【B的内存无X】
           → 继承不到X的峰值 → X的峰值=0/NaN → 写表 ❌覆盖

结果：谁最后写，谁说了算。
      B在A之后写 → X的峰值被覆盖为0 → 前端显示 "-"
```

**关键**：用户看到的 "L1命中" 是**进程A自己视角**——它确实命中了。但**进程B**用它的（可能残缺的）状态覆盖了共享表。前端读的是共享表，所以看到峰值丢失。

### 为什么是"下一个tick"就丢？

因为两进程的 tick 是**交错写入**的。A 写对了，紧接着 B 写错了覆盖，就在下一个 tick 观察到。这也解释了"时有时无"的诡异现象。

## 二、问题推导链（完整证据）

| 步骤 | 证据 | 结论 |
|------|------|------|
| 1 | `Get-CimInstance` 查到 monitor_stock 有 **2个PID** | 双进程确认 |
| 2 | 两进程启动时间都是 08:58:49 | 同期启动 |
| 3 | PID 48800 父进程=pycharm64.exe | 手动启动（venv） |
| 4 | PID 32664 父进程=PID 48800 | 间接由dashboard启动（python312） |
| 5 | `process_manager.py`: `self.python_exe = r"F:\python312\python.exe"` | dashboard用系统python启动 |
| 6 | `start_monitor` 只检查 `self.processes['monitor']`（自己的记录） | **不检测外部已启动的进程** |

| 8 | `_MAIN_NET_TICK_CACHE` 是模块级全局变量 | **进程隔离，两进程内存独立** |
| 9 | `_carry_forward_cumulative_fields` 用 `how='left'` merge | **本tick缺失的股票不会继承峰值** |

**根因**：**双进程 + 共享表 + 无写入协调 = 后写覆盖先写，峰值随机丢失**

## 三、峰值丢失真正原因（已验证）

### 排除项（经测试验证，均安全）
| 场景 | 测试结果 |
|------|----------|
| 正常继承（股票在df_now中） | ✅ peak 正确保持 |
| 股票本tick无主力活动（valid_data.empty直接return） | ✅ peak 保持 |
| 有主力活动，merge result_cols后 | ✅ peak 不受影响 |
| stock_code int/str类型不一致 | ✅ carry_forward内zfill(6)统一，能匹配 |

**结论**：`_carry_forward_cumulative_fields` + 峰值更新逻辑本身**是正确的**。

### 🔴 真正原因：股票瞬时缺失导致级联丢失（风险A）

单进程下，若某tick数据源**漏采**了某只股票：
```
T0: 股票X 存在, 峰值=240.7万 → put_current存内存(含X)
T1: 股票X 漏采(不在df_now) → carry_forward的 how='left' 不会补X行
    → 该tick df_now无X → put_current存内存(【无X】)
T2: 股票X 恢复采集 → 但L1内存(df_prev_main)已无X的峰值
    → 从0重新累积 → 峰值永久丢失 → 前端 max_cumulative_main_net=0 → 显示"-"
```

**为什么"L1一直命中"却丢峰值**：
- L1 命中是真的（每tick都存了内存）
- 但存入内存的 df_now **本身就缺了漏采的那只股票**
- 缺失从此级联传播：一旦某tick漏采，该股票的峰值就永久归零

**前端"-"的确切含义**（已核对 monitor.html 第2578行）：
```javascript
const peak = item.max_cumulative_main_net || 0;
if (peak === 0) return '<td>-</td>';   // peak为0/null/NaN → 显示"-"
```

### 次要风险B：NaN传播
若 `cumulative_main_net` 和 `max_cumulative_main_net` 同时为 NaN，`.max(axis=1)` 结果为 NaN → 前端 "-"。

## 四、解决方案（单进程加固）

### 🔴 方案A（推荐）：carry_forward 补齐"缺失但有累计值"的股票

**问题**：当前 `how='left'` merge 只保留 df_now 中存在的股票，漏采的股票直接消失。

**修复思路**：carry_forward 时，对"上一tick有非零累计值、但本tick缺失"的股票，**补一行**（延续累计值，增量为0）。这样即使某tick漏采，累计状态也不丢。

**关键**：需谨慎——补的行只延续累计字段，其他字段（price/volume等）需合理处理（标记为缺失/沿用上值），**不能污染其他计算**。

### 🟡 方案B：峰值单调性兜底（Redis历史峰值）

`put_current` 前，用 Redis hash 里的历史峰值兜底（peak 只增不减）：
```python
df_now['max_cumulative_main_net'] = df_now[['max_cumulative_main_net', redis_hist_peak]].max(axis=1)
```
即使某tick漏采导致内存丢失，Redis hash 的历史峰值仍能恢复。

### 🟡 方案C：NaN 防护
peak 更新后 fillna：
```python
df_now['max_cumulative_main_net'] = df_now['max_cumulative_main_net'].fillna(
    df_now['cumulative_main_net']).fillna(0)
```

### 🟢 方案D：定位漏采根因
排查数据采集环节（`fetch_all_concurrently`）为何会漏采股票——是网络超时、并发限流，还是数据源返回不全。若能保证不漏采，则从源头消除问题。
