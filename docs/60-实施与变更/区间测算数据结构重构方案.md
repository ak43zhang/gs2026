# 区间测算数据结构重构方案

## 问题分析

当前设计：
```
monitor_hy_top30_{date}:delta:{time} → {code: delta_pct}  (3960个hash)
```

问题：
- 3960个tick × 90行业 = 35万个小hash
- 区间查询需要读取几百个hash，pipeline也慢
- Redis不适合"按时间范围查询"的场景

## 新方案：时间序列压缩存储

### 核心思想

每个行业一个key，存储该区间的所有tick数据（压缩后）。

### Redis结构

```
# 每个行业一个sorted set，member=tick时间，score=环比值
monitor_hy_top30_{date}:ts:{code} → sorted set {time: delta_pct}

# 行业列表
monitor_hy_top30_{date}:codes → [code1, code2, ...]

# 行业名称映射
monitor_hy_top30_{date}:names → {code: name}
```

### 存储示例

```
monitor_hy_top30_20260729:ts:881001 → {
  "09:30:03": 0.0,
  "09:30:06": 0.05,
  "09:30:09": 0.03,
  ...
}

monitor_hy_top30_20260729:ts:881002 → {
  "09:30:03": 0.0,
  "09:30:06": -0.02,
  "09:30:09": 0.01,
  ...
}
```

### 优势

1. **区间查询极快**：`ZRANGEBYSCORE` 或 `ZRANGE` 直接取范围
2. **累计计算简单**：遍历一个 industry's ticks 即可
3. **存储紧凑**：每个行业一个key，共90个key（vs 3960个key）

### 查询流程

```python
# 1. 获取所有行业codes
codes = client.smembers(f"monitor_hy_top30_{date}:codes")

# 2. 对每个行业，取区间内的delta（pipeline批量）
pipe = client.pipeline()
for code in codes:
    pipe.zrangebyscore(
        f"monitor_hy_top30_{date}:ts:{code}",
        start_time, end_time,
        withscores=True
    )
results = pipe.execute()

# 3. 计算累计Δ并排序
for code, ticks in zip(codes, results):
    cumulative = sum(score for _, score in ticks)
    # ...排序
```

### 写入流程（monitor_stock.py）

```python
def _save_industry_delta_to_redis(df: pd.DataFrame, date_str: str, time_full: str):
    client = redis_util._get_redis_client()
    EXPIRE = 64800  # 18小时
    
    for _, row in df.iterrows():
        code = str(row['code']).strip()
        delta = float(row['delta_change_pct'])
        
        # 添加到该行业的时间序列
        ts_key = f"monitor_hy_top30_{date_str}:ts:{code}"
        client.zadd(ts_key, {time_full: delta})
        client.expire(ts_key, EXPIRE)
        
        # 加入行业集合
        codes_key = f"monitor_hy_top30_{date_str}:codes"
        client.sadd(codes_key, code)
        client.expire(codes_key, EXPIRE)
        
        # 存名称
        name_key = f"monitor_hy_top30_{date_str}:names"
        client.hset(name_key, code, str(row['name']))
        client.expire(name_key, EXPIRE)
```

## 备选方案：MySQL优化索引

如果Redis重构成本高，可以优化MySQL：

```sql
-- 给时间字段加索引
ALTER TABLE monitor_hy_top30_20260729 ADD INDEX idx_time_delta (time, delta_change_pct);

-- 区间查询直接用索引
SELECT code, name, SUM(delta_change_pct) as cumulative
FROM monitor_hy_top30_20260729
WHERE time BETWEEN '10:16:06' AND '11:23:45'
GROUP BY code, name
ORDER BY cumulative DESC;
```

优势：
- 无需改Redis结构
- MySQL擅长范围查询
- 聚合计算在DB完成

劣势：
- 依赖MySQL性能
- 不如Redis快（但可能比当前Redis方案快）

## 推荐

**推荐方案A：Redis sorted set**
- 90个key vs 3960个key
- 区间查询从O(n)降到O(log n)
- 适合实时高频查询

**如果实施成本高，选方案B：MySQL索引优化**
