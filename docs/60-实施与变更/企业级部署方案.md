## 一、项目架构分析

### 1.1 系统组成

gs2026 是一个**量化交易数据采集分析系统**，包含 5 大子系统：

| 子系统 | 模块路径 | 作用 | 部署要求 |
|--------|----------|------|----------|
| **数据采集** | `collection/` (30个py) | 采集股票/债券/公告/新闻/涨停数据 | 跨平台 |
| **AI分析** | `analysis/` (62个py) | DeepSeek/火山方舟/阶跃 AI 分析 | 跨平台 + 部分需浏览器 |
| **实时监控** | `monitor/` (18个py) | 盘中实时行情监控、斜率共振信号 | 跨平台 |
| **Web看板** | `dashboard2/` (173个py) | Flask+SocketIO 前端看板 | 跨平台 |
| **自动交易** | `scripts/huatai_trader/` (38个py) | 华泰客户端自动买卖/止盈止损 | ⚠️ **仅 Windows** |

### 1.2 关键：操作系统限制

| 组件 | Windows | Linux | 说明 |
|------|---------|-------|------|
| 数据采集/分析/监控/看板 | ✅ | ✅ | 纯 Python，跨平台 |
| **huatai_trader 自动交易** | ✅ | ❌ | 依赖 `win32api`、华泰同花顺客户端 GUI |
| **playwright 浏览器自动化** | ✅ | ✅ | Linux 需装 headless 依赖 |
| DeepSeek 浏览器分析 | ✅ | ⚠️ | 需要图形界面或 headless Chrome |

**结论**：
- 若新服务器是 **Linux** → 可部署数据/分析/监控/看板，但**自动交易无法运行**
- 若新服务器是 **Windows** → 可完整部署

### 1.3 外部依赖服务

| 服务 | 版本要求 | 当前配置 | 用途 |
|------|----------|----------|------|
| **MySQL** | 8.0+ | 192.168.0.101:3306 | 主数据库（517表/196GB） |
| **Redis** | 5.0+ | localhost:6379 | 实时缓存（1634 keys） |
| **Python** | 3.11+ | .venv 虚拟环境 | 运行时 |

## 二、数据库分析（部署最大难点）

### 2.1 数据库现状

```
数据库名: gs
总表数:   517 张
总大小:   196 GB (数据 116GB + 索引 79GB)
引擎:     InnoDB
字符集:   utf8mb4（混用了5种collation，需统一）
```

### 2.2 表分类（关键洞察）

**517张表分为两类**，部署策略完全不同：

| 类型 | 数量 | 特征 | 示例 | 部署策略 |
|------|------|------|------|----------|
| **结构表** | 209张 | 固定表名 | accounts, reports, quant_screen_hits | ✅ 必须建表 |
| **动态表** | 308张 | 按日期/年份生成 | monitor_gp_sssj_20260624 | ⚙️ 程序自动建，无需手工 |

**动态表说明**：程序运行时按交易日自动创建（如 `monitor_gp_sssj_YYYYMMDD`），单表可达 3000 万行/10GB。**这些表不需要在部署时创建**，也不建议迁移历史数据。

### 2.3 最大的表（Top 5）

| 表名 | 行数 | 大小 |
|------|------|------|
| monitor_gp_sssj_20260624 | 3014万 | 10.3 GB |
| monitor_gp_sssj_20260703 | 2329万 | 7.5 GB |
| monitor_gp_sssj_20260708 | 2150万 | 7.0 GB |

→ 这些是每日实时行情表，属于动态表，**不迁移**。

### 2.4 建表 SQL 现状问题

| 问题 | 详情 | 影响 |
|------|------|------|
| **无统一建表脚本** | 建表逻辑散落在 24 个 SQL + 5 个 py 文件 | 需整合 |
| **库名不一致** | SQL 写 `gs_platform`，运行用 `gs` | 需统一 |
| **仅22个显式CREATE TABLE** | 大量表结构靠采集程序运行时动态生成 | 首次部署需"跑一轮采集"来建表 |

## 四、部署流程（完整步骤）

> 以下以 **全新服务器** 为例。根据 §审核要点的决策，部分步骤可能调整。

### 阶段 0：环境准备

```bash
# ---- Linux (Ubuntu 22.04 为例) ----
# 1. 系统依赖
sudo apt update && sudo apt install -y python3.11 python3.11-venv python3-pip \
    default-libmysqlclient-dev build-essential pkg-config git

# 2. MySQL 8.0
sudo apt install -y mysql-server-8.0
sudo systemctl enable --now mysql

# 3. Redis
sudo apt install -y redis-server
sudo systemctl enable --now redis

# ---- Windows ----
# 1. 安装 Python 3.11 (python.org)
# 2. 安装 MySQL 8.0 (MySQL Installer)
# 3. 安装 Redis (Memurai 或 Redis for Windows)
```

### 阶段 1：拉取代码

```bash
git clone git@github.com:ak43zhang/gs2026.git
cd gs2026
```

### 阶段 2：Python 环境

```bash
# 创建虚拟环境
python3.11 -m venv .venv

# 激活 (Linux)
source .venv/bin/activate
# 激活 (Windows)
.venv\Scripts\activate

# 安装依赖
pip install -r requirements.txt

# 安装 playwright 浏览器（如需AI浏览器分析）
playwright install chromium
# Linux 额外装系统依赖
playwright install-deps
```

### 阶段 3：数据库初始化

#### 3.1 创建数据库

```sql
CREATE DATABASE gs DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'gs2026'@'%' IDENTIFIED BY '<强密码>';
GRANT ALL PRIVILEGES ON gs.* TO 'gs2026'@'%';
FLUSH PRIVILEGES;
```

#### 3.2 建表方案（三选一，需审核决策）

**方案A：只建结构表 + 数据重新采集（推荐，适合新环境）**
- 执行整合后的建表脚本（209张结构表）
- 动态表由程序运行时自动创建
- 历史数据通过采集程序重新拉取
- 优点：干净、快；缺点：需重新采集历史数据

**方案B：全量迁移（适合"原样搬迁"）**
```bash
# 源服务器导出（196GB，耗时数小时）
mysqldump -u root -p --single-transaction --routines gs | gzip > gs_full.sql.gz
# 传输 + 导入
gunzip < gs_full.sql.gz | mysql -u gs2026 -p gs
```
- 优点：数据完整；缺点：196GB传输/导入极慢，需大磁盘

**方案C：结构+近期数据（折中）**
- 迁移结构表 + 最近N天动态表
- 老数据丢弃

> **待整合工作**：目前没有统一建表脚本，实施阶段我会先扫描全部209张结构表的 `SHOW CREATE TABLE`，生成一份 `deploy/schema_full.sql`。

#### 3.3 执行迁移脚本（migrations目录）

```bash
mysql -u gs2026 -p gs < migrations/20260712_backtest_history_result_data.sql
mysql -u gs2026 -p gs < migrations/20260712_mainline_summary_fields.sql
mysql -u gs2026 -p gs < migrations/20260713_quant_screen_hits_exit_tracking.sql
mysql -u gs2026 -p gs < migrations/add_scheduler_job_types.sql
```

### 阶段 4：配置修改

```bash
# 复制配置模板并修改
cp configs/settings.yaml configs/settings.yaml.bak
```

需修改 `configs/settings.yaml`：

```yaml
common:

```

### 阶段 5：启动服务

| 服务 | 启动命令 | 说明 |

## 五、企业级增强建议

### 5.1 进程管理（生产必备）

**Linux — systemd**（我会生成 service 文件）：
```ini
# /etc/systemd/system/gs2026-dashboard.service
[Unit]
Description=GS2026 Dashboard
After=network.target mysql.service redis.service
[Service]
WorkingDirectory=/opt/gs2026
Environment=PYTHONPATH=/opt/gs2026/src
ExecStart=/opt/gs2026/.venv/bin/python -m gs2026.dashboard2.app
Restart=always
[Install]
WantedBy=multi-user.target
```

**Windows — NSSM** 把 bat 注册为服务。

### 5.2 数据库调优（196GB级别）

```ini
# my.cnf 建议
innodb_buffer_pool_size = 8G      # 内存的50-70%
innodb_log_file_size = 2G
max_connections = 200             # 代码连接池10+20/进程
innodb_file_per_table = ON
```

### 5.3 反向代理（Nginx）

```nginx
server {
    listen 80;
    location / { proxy_pass http://127.0.0.1:5000; }
    location /socket.io/ {
        proxy_pass http://127.0.0.1:5000;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}
```

### 5.4 敏感信息环境变量化

```bash
# .env（不提交git）
GS_MYSQL_PASSWORD=xxx
GS_STEP_API_KEY=xxx
GS_VOLCENGINE_API_KEY=xxx
```
需改造 `config_util.py` 支持从环境变量读取（实施阶段处理）。

### 5.5 定时任务（数据采集）

系统有 APScheduler 调度（scheduler_jobs表）。需确认：
- 盘中监控进程常驻
- 每日采集任务定时触发
- AI分析worker进程数（bin/run_5_workers.bat 显示5个）
