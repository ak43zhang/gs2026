| 层 | 内容 | 状态 |
|----|------|------|
| 第1层（主） | fetch失败批次重试——用"请求-返回"集合差识别缺失，重试1轮拿**真实数据** | ✅ |

| 第3层（保险） | 峰值Redis历史值兜底 + NaN防护 | ✅ |

**关键实现**：
- 新增常量 `RETRY_TIMEOUT = 1.5`（重试超时）
- 重构 `fetch_all_concurrently`，加 `_fetch_round` 辅助函数 + 两轮重试逻辑
- 新增 `_fill_missing_stocks`（第2层兜底）
- 新增 `_load_peak_from_redis_hash`（第3层峰值读取）
- `calculate_main_force_and_cumulative` 加 NaN 防护

**特性保证**：正常tick零影响（无缺失不触发重试）；追求真实数据优先；性能可控（RETRY_TIMEOUT=1.5s，实测余量~2300ms足够）

**验证**：语法通过 + 4项单元测试全过（缺失识别/补齐逻辑/delta=0/峰值兜底+NaN防护）

### ✅ 5. 上攻排行"除次数外全为0"问题彻底修复 — 2026-07-28 07:59-08:56 【本时段重点】

**问题现象**：2026-07-27 点击时间轴 09:50:15，股票上攻排行除"次数"外，涨跌幅/主力净额/价格全部显示0；但点击 14:10:54 又都正常。

**排查过程（4次深挖，用户线索驱动）**：
1. **v1.0**：初判 20260727 表缺 `consecutive_attacks` 列导致 SQL 崩溃
2. **v2.0**（用户反馈"14:10:54又有值"）：发现**双路径容错差异**——Redis缓存路径逐字段判断（容错），MySQL路径写死字段（不容错）
3. **v3.0**（用户问"07-24也走MySQL为何有值"）：实测建表时间——**20260724建表09:25:00（正常24列），20260727建表09:29:19（晚4分钟，23列缺列）**
4. **v4.0**：确认三重根因 + 排查债券/行业

**三重根因**：
| 因素 | 说明 | 角色 |
|------|------|------|
| 因素1 | 启动时序异常（07-27建表晚4分钟，错过集合竞价首tick）| 偶发导火索 |
| 因素2 | 建表结构依赖首tick，首tick缺列则全天缺 | 数据层脆弱 |
| 因素3 | **MySQL路径写死字段名零容错**，把小数据缺陷放大成严重故障 | **代码层真正根因** |

**已实施修复（用户确认方案）**：
- **建表完整性**（`monitor_stock.py`）：写MySQL前主动补齐所有 `DERIVED_FIELDS` 列 → 无论启动早晚，表结构始终完整

- **债券路径加固**：`_get_bond_change_pct_from_mysql`（2处）同样改为字段检测
- **补历史数据**：`ALTER TABLE monitor_gp_sssj_20260727 ADD COLUMN consecutive_attacks INT DEFAULT 0`（已执行，24列）

**债券/行业排查结论**：

## 六、经验总结

1. **用户线索驱动的根因排查极其有效**：上攻排行问题，用户三次提供反例（"14:10有值"、"07-24也走MySQL"），每次都推翻了阶段性结论，最终定位到"双路径容错差异 + 建表时序"的真正根因。**不能满足于第一个看似合理的解释**。

2. **代码脆弱性比偶发数据问题更该修**：一个极稀疏的可选字段缺失，因MySQL路径"写死字段零容错"被放大成严重故障。**治本是统一容错能力，而非只补数据**。

3. **建表依赖首tick是隐患**：表结构由首个写入决定，启动时序异常会导致列缺失。**主动补齐所有已知字段可从源头杜绝**。

4. **方案先行、审核后实施**：本时段所有重大改动都遵循"出方案→用户审核→实施→验证"流程，降低了风险。
