# 量化选债收益计算 - 性能分析与方案对比

## 一、当前方案性能分析

### 1.1 当前实现（数据库计算方案）

**每tick操作**:
```
1. 查询: SELECT * FROM quant_screen_hits WHERE trade_date = :today
   - 全表扫描（或索引扫描）当天所有命中记录
   - 假设一天100条命中，每tick都要查100条
   
2. 逐条处理: Python循环100条
   - 计算浮动收益
   - 判断触发条件
   - 分类到4个更新列表
   
3. 批量UPDATE: 
   - 持仓中: UPDATE current_price, current_return_pct
   - 新触发: UPDATE exit_*, lock_*
```

**性能瓶颈**:
| 操作 | 耗时估算 | 问题 |
|------|---------|------|
| 查询100条 | ~10-20ms | 可接受 |
| Python循环100条 | ~5-10ms | 可接受 |
| UPDATE 100条（持仓中） | **~100-200ms** | **主要瓶颈** |
| 数据库IO | 每次UPDATE都有网络+磁盘IO | 累积延迟 |

**总每tick耗时**: ~150-250ms（假设100条持仓中记录）

### 1.2 性能问题根源

- **每tick全量UPDATE**: 即使价格只变动0.01%，也要UPDATE所有持仓中记录
- **数据库压力**: 3秒tick间隔，每天4小时交易 = 4800次查询+UPDATE
- **并发问题**: 如果命中记录多（比如500条），UPDATE会成为瓶颈

## 二、前端计算方案分析

### 2.1 方案设计

**核心思想**: 数据库只存**静态数据**，实时计算移到前端

```
数据库存储（写入后不变）:
- entry_price（入场价）
- take_profit_price（止盈价）
- stop_loss_price（止损价）
- max_hold_time（最大持仓时间）
- tick_time（入场时间）
- is_locked（是否锁定）
- exit_price（平仓价，触发后写入）
- final_return_pct（最终收益，触发后写入）

前端实时计算:
- current_price（从行情API获取）
- current_return_pct = (current - entry) / entry * 100
- 触发判断: current >= tp_price? / current <= sl_price? / timeout?
- 统计: 持仓数/盈数/损数
```

### 2.2 后端改造（极简）

**每tick只做**:
```python
# 1. 只更新"新触发"的记录（从holding→locked）
# 查询: 只查is_locked=0的记录（未结算）
SELECT id, bond_code, entry_price, tp_price, sl_price, max_hold, tick_time
FROM quant_screen_hits 
WHERE trade_date = :today AND is_locked = 0

# 2. 判断哪些新触发
updates = []
for row in pending:
    if 触发条件:
        updates.append({
            'exit_price': 触发价,
            'final_return_pct': 计算收益,
            'is_locked': 1,
            'lock_reason': 'tp/sl/timeout'
        })

# 3. 只UPDATE新触发的（数量很少）
if updates:
    batch_update(updates)  # 通常一天几十条，不是每tick几百条
```

**关键**: 持仓中的记录**不UPDATE**，前端自己算浮动收益

### 2.3 前端计算逻辑（JavaScript）

```javascript
// 从后端获取命中记录（静态数据）
const hits = await fetch('/api/hits?date=today');

// 从WebSocket/轮询获取实时行情
const prices = await fetch('/api/realtime_prices');

// 实时计算
hits.forEach(hit => {
    if (hit.is_locked) {
        // 已结算：显示final_return_pct
        hit.display_return = hit.final_return_pct;
        hit.status = hit.lock_reason;
    } else {
        // 持仓中：实时计算
        const currentPrice = prices[hit.bond_code];
        hit.display_return = ((currentPrice - hit.entry_price) / hit.entry_price * 100).toFixed(4);
        
        // 触发判断（前端只做展示判断，最终触发由后端确认）
        if (currentPrice >= hit.take_profit_price) {
            hit.status = 'profited (pending)';
        } else if (currentPrice <= hit.stop_loss_price) {
            hit.status = 'stopped (pending)';
        } else if (超时) {
            hit.status = 'timeout (pending)';
        } else {
            hit.status = 'holding';
        }
    }
});

// 统计
const stats = {
    holding: hits.filter(h => !h.is_locked).length,
    profited: hits.filter(h => h.lock_reason === 'take_profit' || 
                               (h.lock_reason === 'max_time' && h.final_return_pct >= 0)).length,
    stopped: hits.filter(h => h.lock_reason === 'stop_loss' ||
```

## 三、方案对比

| 维度 | 当前方案（数据库计算） | 前端计算方案 |
|------|---------------------|-------------|
| **每tick数据库操作** | 查询100条 + UPDATE 100条 | 查询100条 + UPDATE 0-5条（仅新触发） |
| **数据库压力** | 高（每tick大量UPDATE） | 极低（只UPDATE状态变更） |
| **后端计算量** | 高（Python循环+计算） | 低（只判断触发） |
| **前端复杂度** | 低（只展示） | 中（需要实时计算） |
| **实时性** | 依赖数据库UPDATE频率 | 极高（前端即时计算） |
| **数据一致性** | 强（单数据源） | 中（前端计算可能短暂不一致） |
| **实现难度** | 已完成 | 小改后端 + 前端增加计算 |
| **网络传输** | 传计算后结果 | 传原始数据，前端算 |

## 四、推荐方案：前端计算（性能更优）

### 4.1 为什么更好

1. **数据库压力降低90%**: 从每tick UPDATE 100条 → 只UPDATE新触发的几条
2. **实时性更高**: 前端算，不依赖后端数据库UPDATE
3. **扩展性好**: 命中记录再多（1000条），前端计算无压力
4. **后端更简单**: 只做"触发判定"，不做"全量更新"

### 4.2 修改难度

| 组件 | 改动量 | 说明 |
|------|--------|------|
| **后端** | 小 | 简化 `_track_pending_exits`，只处理触发判定，不UPDATE持仓中 |
| **前端** | 中 | 增加实时计算逻辑，需要获取实时行情价格 |
| **API** | 小 | 可能需要一个"批量获取实时价格"的接口 |

**总体难度**: ⭐⭐ 较小（1-2小时工作量）

### 4.3 计算逻辑复杂度

**前端计算**:
- 浮动收益: `(current - entry) / entry * 100` — 简单
- 触发判断: 3个if判断 — 简单
- 统计: filter计数 — 简单

**结论**: 计算逻辑非常简单，前端完全胜任

### 方案B：混合优化（当前方案+批量优化）

如果坚持后端计算，可以优化:
- 只UPDATE价格变化超过0.5%的（减少UPDATE数量）
- 批量UPDATE改为异步队列
- 但复杂度增加，效果不如前端计算
