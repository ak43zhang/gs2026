**优化日期**: 2026-08-04  
**实施**: AI Assistant  
**验证**: 新旧结果 ALL_CONSISTENT（diff=0）

---

## 一、问题背景

股债交集回溯功能上线后，用户反馈**遍历时间范围内所有tick太慢**，尤其是全天的tick（约4428个时间点）需要遍历数分钟。

用户期望：**一次性加载数据，内存中计算，快速返回结果**。

---

## 二、瓶颈精确定位（代码实测，非猜测）

### 2.1 当前逐tick查询链路

```python
for time_str in timestamps:  # 全天约4428个时间点
    stock_data = _get_ranking_fast('stock', ...)                    # 查询1
    stock_data = _enrich_stock_data(...)                            # 查询2
    stock_data = _enrich_change_pct_and_main_net(...)               # 查询3-4 (change_pct + main_net)
    bond_data = _get_ranking_fast('bond', ...)                      # 查询5
    bond_data = _enrich_bond_data(...)                              # 查询6-7 (change_pct + amount + price)
    过滤 + 交集
```

### 2.2 三个致命性能瓶颈

| 瓶颈 | 具体问题 | 影响 |
|------|----------|------|
| **① 每tick重建MySQL连接池** | `_get_change_pct_from_mysql` 内部 `create_engine(Config.MYSQL_URI)` 每次调用都新建引擎+连接池 | 4428tick × 多次调用 = 上万次建池 |
| **② 每tick单独查sssj表** | sssj表约250万行全天数据，每tick按 `time=?` 查一次 | 4428次单点查询 |
| **③ 增量计数器被打断** | `_get_ranking_fast` 的增量计数器股票债券交替调用，频繁触发全量 GROUP BY | 首次/后退时~300ms |

### 2.3 数据量实测

| 表 | 全天数据量 |
|----|-----------|
| monitor_gp_top30_{date} | 约10-13万行 |
| monitor_zq_top30_{date} | 约2985行（实测） |
| **monitor_gp_sssj_{date}** | **约250万行（唯一瓶颈）** |
| monitor_zq_sssj_{date} | 约30万行 |

**结论**：只有 sssj（尤其是股票 sssj 250万行）是瓶颈。top30 表很小，一次性加载无压力。

## 三、优化方案设计

### 3.1 核心思路

> **一次性加载小表 + 分批加载大表 + 内存遍历切片**

与用户的期望一致："一次性加载数据，内存中计算"。

### 3.2 方案架构

```
【一次性加载】
  ├─ top30全量（股+债）→ 构建count时间线 + window_count时间线
  ├─ 股债映射缓存（get_cache）
  ├─ 绿名单集合（当天Redis/历史MySQL）
  └─ 债券行业映射（_get_bond_industry_batch）

【按tick分批（每批100个tick）】
  for 批 in 分批(timestamps, 每批100):
      批开始, 批结束 = 批[0], 批[-1]
      
      # 只加载该批次时间窗口 + 候选code的sssj
      stock_sssj = SELECT ... WHERE code IN(候选) AND time BETWEEN 批开始 AND 批结束
      bond_sssj  = 同理
      
      for tick in 批:
          # 从预加载的时间线切片 + sssj切片 组装数据（0次DB）
          组装stock_data → 过滤(UnifiedPipeline) → 交集
          组装bond_data → 过滤(UnifiedPipeline) → 交集
      
      释放本批sssj内存  # 内存有界

【返回】所有results
```

### 3.3 关键优化点

#### 优化点1：code过滤（大幅砍行数）

sssj 表记录全市场每只股票每个tick的数据，但回溯只关心 top30 出现过的 code（约570只，非全市场5000只）。

```sql
-- 优化前（加载全市场）
SELECT stock_code, time, change_pct, main_net_amount FROM monitor_gp_sssj_{date}

-- 优化后（只加载候选code）
SELECT stock_code, time, change_pct, main_net_amount 
FROM monitor_gp_sssj_{date} 
WHERE stock_code IN (:c0, :c1, ..., :c570)
```

#### 优化点2：按tick分批（你的思路，默认每批100）

每批只加载该时间窗口的 sssj，处理完即释放内存。

| 场景 | 批数 | sssj查询次数 |
|------|------|-------------|
| 全天(4428tick, 每批100) | ~44批 | ~88次（股债各44次） |
| 窄窗口(20tick) | 1批 | 2次 |

对比原来：8856次 → **降到88次**

#### 优化点3：SSE流式进度

新增 `/api/backtrace/run-stream` SSE 端点，实时推送进度：

```javascript
// 前端收到的SSE事件
{"type": "start", "total": 4428}
{"type": "preload", "msg": "加载排行数据(top30)..."}
{"type": "progress", "done": 100, "total": 4428, "batch": 1, "batches": 44, "found": 14}
{"type": "progress", "done": 200, "total": 4428, "batch": 2, "batches": 44, "found": 28}
{"type": "done", "data": {...}}
```

### 3.4 时间线预计算（一次性）

**count时间线**：top30行按time升序，running累加每个code的count。

```python
# 指针扫描一次，每个tick保存count快照
for t in timestamps:
    while idx < len(rows) and rows[idx].time <= t:
        counter[code] += 1
        idx += 1
    count_timeline[t] = dict(counter)
```

**window_count时间线**：对每个10分钟窗口，取窗口内最新记录的 `window_count` 列值。

```python
# 按窗口分组，同窗口内升序遍历，最新值覆盖
for t in timestamps:
    ws = window_start(t)  # 如 14:29 → 14:20:00
    while idx < len(rows) and rows[idx].time <= t and window_start(rows[idx].time) == ws:
        window_latest[code] = rows[idx].window_count
        idx += 1
    wc_timeline[t] = dict(window_latest)
```

## 六、技术要点总结

### 6.1 字段来源（100%沿用现有逻辑）

| 字段 | 来源 | 计算方式 |
|------|------|----------|
| count | top30表 | 累计行数（running counter） |
| window_count | top30表window_count列 | 当前10分钟窗口内最新记录值，无则0 |
| change_pct | sssj表 | time=t那一刻的值 |
| main_net_amount | sssj表 | time=t那一刻的值 |
| amount/price | 债券sssj表 | time=t那一刻的值 |
| bond_code/industry_name | 股债映射缓存 | get_cache.get_mappings_smart |
| is_green/is_green_bond | 绿名单集合 | 当天Redis/历史MySQL |

### 6.2 核心不变保证

1. **过滤逻辑不变**：每tick仍走同一 `UnifiedPipeline`（谓词各自独立取交集 → 排行基于候选池S）
2. **字段计算不变**：组装出的数据字段与现有 `_enrich_*` 函数产出完全一致
3. **绿名单语义不变**：转债在绿名单则整条股债对剔除
4. **谓词/排行切换不变**：后端管道支持 predicate/ranking 模式

### 6.3 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 分批大小 | 100 tick/批 | 平衡查询次数与内存（44批×2=88次查询） |
| sssj时间范围 | 按批次窗口 | 只加载需要的数据，不拉全天250万行 |
| code过滤 | top30候选codes | 砍掉全市场无关股票，大幅减少行数 |
| top30加载 | 一次性全量 | 小表（十几万行），无压力 |
| count时间线 | 从开盘累计 | count是累计值，不能截断 |
| window_count时间线 | 从开盘累计 | 窗口可能跨截断点 |
| 进度推送 | SSE流式 | 实时展示处理进度，用户体验好 |

## 七、已知限制与后续优化

### 7.1 已知限制

1. **窄窗口也加载top30全量**：如果用户选择单tick（如14:29:00），top30仍从开盘加载。不过top30小（~13万行），耗时<1秒，可接受。
2. **不支持实时回溯**：当前回溯走MySQL全量，不走Redis实时缓存。回溯是历史数据分析，非实时监控，此限制合理。

### 7.2 后续可优化

1. **SSE断线重连**：前端可添加断线检测+自动重连+增量继续
2. **结果分页**：全天可能返回数千条交集结果，前端可按时间分批展示
3. **top30增量预加载**：如果窄窗口成为高频场景，可加top30按时间裁剪（需确保count累计正确）
4. **预加载缓存**：同一日期多次回溯，可缓存top30时间线和映射
