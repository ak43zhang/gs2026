# 统一字段回填引擎设计方案

> 版本: v5.0  
> 更新日期: 2026-07-19  
> 关联文件: `scripts/backfill_unified.py`, `scripts/compute_engine.py`, `scripts/field_registry.py`

---

## 一、需求背景

### 1.1 业务场景

实时监控系统（`monitor_bond.py`）在盘中逐tick计算各类指标并写入MySQL的`sssj`日表。当出现以下场景时，需要对历史数据进行回填：

1. **新增指标**：新增字段（如`weighted_slope_15m`），历史表中无该列数据
2. **算法更新**：指标计算逻辑修改后，需要重算历史数据
3. **数据修复**：因异常导致部分时段数据缺失，需要补填
4. **扩展窗口**：计算窗口扩展（如2.5分钟→15分钟），需要重算以利用更长历史

### 1.2 核心约束

| 约束 | 说明 |
|------|------|
| 算法一致性 | 回填计算必须与实时计算使用**完全相同**的函数 |
| 数据安全 | 回填过程中不得损坏原始数据（价格、成交量等） |
| 大数据量 | 单日表150万-200万行，30天回填总量4500万-6000万行 |
| 时序依赖 | 指标计算依赖历史数据（如15分钟斜率需要前900秒的价格序列） |
| 并行能力 | 支持多进程并行处理不同日期 |

## 三、数据流设计

### 3.1 单表处理流程

```
┌──────────────────────────────────────────────────────────────┐
│                    单表处理流程 (process_single_day)            │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  Step 1: Schema检查                                          │
│     └── 确认表存在、确保计算字段列存在                          │
│     └── 自动修复ext_indicators列类型（VARCHAR→TEXT）            │
│                                                              │
│  Step 2: 时间分片读取（不依赖长连接）                           │
│     └── SELECT DISTINCT time → 获取所有时间点                  │
│     └── 每100个时间点一次独立SELECT查询                         │
│     └── 每批次约 100tick × 670债券 = ~67000行                  │
│                                                              │
│  Step 3: 逐tick计算（有状态，时序依赖）                         │
│     └── ComputeEngine.process_tick(df_tick, time)             │
│     └── 内部维护价格缓存、斜率历史等状态                        │
│     └── 跨chunk边界状态自动保留                                │
│                                                              │
│  Step 4: 分批写入（BatchWriter UPDATE JOIN）                    │
│     └── 每积累50000行结果 → 触发flush                          │
│     └── 创建临时表 → INSERT → UPDATE JOIN → 清理                │
│     └── 每批5000行一个UPDATE JOIN（避免超时）                    │
│                                                              │
│  Step 5: 完成                                                │
│     └── 打印统计信息，返回结果                                 │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 时序依赖与状态管理

**核心问题**：指标计算有时序依赖（如15分钟斜率需要前900秒的数据），数据分批读取时如何保证跨批次的计算正确性？

**解决方案**：`ComputeEngine` 是有状态对象，创建一次，贯穿整个表的处理。

```python
compute_engine = ComputeEngine()  # 创建一次，维护跨chunk状态

for df_batch in load_table_data_streaming(...):  # 数据分批读取
    for tick_time, df_tick in grouped:           # 逐tick处理
        compute_engine.process_tick(...)          # 状态自动累积
```

**ComputeEngine 内部状态**：
| 状态 | 用途 | 生命周期 |
|------|------|----------|
| `ext_price_cache` | 个券价格历史（deque） | 整个表处理期间 |
| `ext_mkt_price_cache` | 大盘价格历史 | 整个表处理期间 |
| `ext_prev_slopes` | 上一次斜率值（加速度计算） | 整个表处理期间 |
| `slope_buffers` | 短期/长期斜率缓冲 | 整个表处理期间 |

**约束**：数据必须按时间正序处理，chunk内和chunk间都是时间递增的。

### 3.3 分片策略选择

| 方案 | 可行性 | 原因 |
|------|--------|------|
| **按时间分片**（当前） | ✅ 唯一正确方案 | 大盘指标需要每tick的全量债券数据 |
| 按债券分片 | ❌ 不可行 | 大盘均价=所有债券均价，缺少部分债券会导致计算错误 |
| 随机分片 | ❌ 不可行 | 破坏时序依赖 |

## 四、字段体系

### 4.1 字段注册表（field_registry.py）

共13个计算字段，分为5类：

| 类别 | 字段名 | 存储方式 | 数据类型 | 说明 |
|------|--------|----------|----------|------|
| **rank** | `amount_rank` | 直接列 | INT | 成交额排名 |
| **rank** | `min1_amount_rank` | 直接列 | INT | 1分钟成交额排名 |
| **min1** | `min1_change_pct` | 直接列 | FLOAT | 1分钟涨跌幅 |
| **min1** | `min1_amount` | 直接列 | FLOAT | 1分钟成交额 |
| **slope** | `slope_short` | 直接列 | FLOAT | 短期斜率(3分钟) |
| **slope** | `slope_long` | 直接列 | FLOAT | 长期斜率(15分钟) |
| **slope** | `peak_vol_bias` | 直接列 | FLOAT | 峰值成交量偏差 |
| **slope** | `high_distance` | 直接列 | FLOAT | 高点距离 |
| **market** | `mkt_slope_short` | 直接列 | FLOAT | 大盘短期斜率 |
| **market** | `mkt_slope_long` | 直接列 | FLOAT | 大盘长期斜率 |
| **market** | `mkt_peak_vol_bias` | 直接列 | FLOAT | 大盘峰值偏差 |
| **market** | `mkt_high_distance` | 直接列 | FLOAT | 大盘高点距离 |
| **ext_json** | `ext_indicators` | TEXT列(JSON) | TEXT | 扩展指标集合 |

### 4.2 ext_indicators JSON结构

`ext_indicators` 列存储一个JSON字符串，包含10个子指标：

```json
{
    "weighted_slope_2m": 0.0015,
    "weighted_slope_5m": 0.0023,
    "weighted_slope_15m": 0.0018,
    "change_1m_pct": 0.05,
    "price_acceleration": 0.0002,
    "mkt_weighted_slope_2m": 0.0008,
    "mkt_weighted_slope_5m": 0.0012,
    "mkt_weighted_slope_15m": 0.0009,
    "mkt_change_1m_pct": 0.03,
    "mkt_price_acceleration": 0.0001
}
```

### 4.3 字段映射

用户可以用子指标名指定回填范围，系统自动映射到实际数据库字段：

```
用户指定: weighted_slope_2m → 实际回填: ext_indicators (整个JSON)
用户指定: slope_short → 实际回填: slope_short (独立列)
用户指定: 不指定 → 回填所有13个字段
```

## 五、性能参数

### 5.1 关键参数

| 参数 | 值 | 说明 |
|------|-----|------|
| `chunk_time_count` | 100 | 每次读取100个时间点的数据 |
| `FLUSH_SIZE` | 50,000 | 积累5万行结果后触发写入 |
| `batch_size` (BatchWriter) | 5,000 | 每次UPDATE JOIN处理5000行 |
| `pool_size` (per-process) | 3 | 每个进程的数据库连接池大小 |
| `connect_timeout` | 60s | 数据库连接超时 |
| `read_timeout` | 600s | 数据库读取超时 |
| `write_timeout` | 600s | 数据库写入超时 |

### 5.2 性能指标

基于实测数据（单表~150万行，~670债券，~2300个tick）：

| 阶段 | 耗时 | 说明 |
|------|------|------|
| 时间点查询 | ~1秒 | SELECT DISTINCT time |
| 每chunk读取 | ~3-5秒 | 100 tick × 670债券 = 67000行 |
| 每chunk计算 | ~2-3秒 | 逐tick调用process_tick |
| 每次flush写入 | ~15-20秒 | 50000行 ÷ 5000/批 = 10个UPDATE JOIN |
| **单表总计** | **~12-17分钟** | 约22-23次flush |

### 5.3 多进程性能

| 进程数 | 单表耗时 | 30天总耗时 | 说明 |
|--------|----------|----------|------|
| 1 | ~15分钟 | ~7.5小时 | 顺序处理 |
| 4 | ~15分钟/表 | ~2小时 | 4表并行，受MySQL IO限制 |
| 8 | ~15分钟/表 | ~1小时 | 可能受连接数限制 |

## 六、数据安全设计

### 6.1 安全保证

| 场景 | 行为 | 数据影响 |
|------|------|----------|
| 程序正常完成 | 所有计算字段更新 | ✅ 计算字段更新，原始字段不变 |
| 程序中途崩溃 | 部分行已更新 | ✅ 已更新行有正确值，未更新行保持原值 |
| 单行UPDATE失败 | 跳过该行 | ✅ 该行保持原值，不影响其他行 |
| MySQL连接断开 | 当前flush中断 | ✅ 已commit的行正确，未commit的回滚 |
| ext_indicators列类型错误 | 自动ALTER TABLE修复 | ✅ 修复后正常写入 |

### 6.2 为什么安全？

```sql
-- 回填只执行UPDATE，永远不执行DELETE/DROP/TRUNCATE
UPDATE sssj_table 
SET ext_indicators = '{"weighted_slope_2m": 0.05, ...}'  -- 只改计算字段
WHERE bond_code = '123001' AND time = '09:30:00'         -- 精确定位

-- bond_name, price, amount, open, high, low... 这些列永远不在SET中
```

### 6.3 可重复执行

回填脚本可以安全地重复执行同一张表：
- `--force` 模式：强制重算所有字段，覆盖已有值
- `--skip-existing` 模式：跳过已有字段列，只计算新增的
- 部分完成后重跑：已完成的行会被重新覆盖（结果相同），未完成的会被补充

## 七、使用方式

### 7.1 命令行参数

```bash
# 单日回填（全部字段）
python scripts/backfill_unified.py --date 20260718

# 日期范围（自动过滤交易日）
python scripts/backfill_unified.py --start 20260701 --end 20260731

# 指定字段
python scripts/backfill_unified.py --date 20260718 --fields ext_indicators slope_short

# 多进程并行
python scripts/backfill_unified.py --start 20260701 --end 20260731 --workers 4

# 跳过已有字段（增量模式）
python scripts/backfill_unified.py --start 20260701 --end 20260731 --skip-existing

# 强制重算
python scripts/backfill_unified.py --date 20260718 --force
```

### 7.2 代码配置模式

修改 `DEFAULT_CONFIG` 后直接运行：

```python
DEFAULT_CONFIG = {

    'skip_existing': False,
    'force': True,
    'workers': 4,
}
```

## 八、算法一致性保证

### 8.1 统一函数导入

```python
# compute_engine.py 顶部：
def _import_unified_functions():
    """强制从 monitor_bond.py 导入，失败则报错"""
    from monitor_bond import (
        calc_bond_ext_indicators,
        calc_mkt_ext_indicators,
        _calc_weighted_slope,
        _calc_slope
    )

# 失败直接报错，不允许fallback到本地实现
_UNIFIED_FUNCS = _import_unified_functions()
```

### 8.2 一致性验证

| 检查项 | 保证方式 |
|--------|----------|
| 算法函数 | 强制从monitor_bond.py导入，同一份代码 |
| 计算窗口 | field_registry统一定义（EXT_WINDOW_SECONDS=900） |
| 半衰期参数 | monitor_bond.py中定义，回填直接使用 |
| 渐进式阈值 | 统一定义（5点/5分钟，8点/15分钟） |
| 状态管理 | ComputeEngine模拟实时的全局状态变量 |

## 九、异常处理

### 9.1 已知异常及处理

| 异常 | 原因 | 处理方式 |
|------|------|----------|
| `Data too long` | ext_indicators列是VARCHAR | 自动ALTER TABLE改为TEXT |
| `Lost connection` | 读取超时 | 时间分片设计避免长连接 |
| `Lock wait timeout` | 表锁竞争 | 小批次UPDATE(5000行)降低锁时间 |
| 进程OOM | 全表加载内存 | 时间分片读取，内存恒定 |
| 列不存在 | 新字段未创建 | SchemaManager自动ALTER TABLE ADD |

### 9.2 容错设计

```python
try:
    result = process_single_day_standalone(date_str, ...)
except Exception:
    # 单日失败不影响其他日期
    # 返回失败结果，主进程记录并继续
    return (date_str, False, traceback.format_exc(), 0, 0)
```

## 十、与实时系统的关系

### 10.1 对比

| 维度 | 实时系统 (monitor_bond.py) | 回填引擎 (backfill_unified.py) |
|------|---------------------------|-------------------------------|
| 触发方式 | 盘中每3秒自动触发 | 手动执行/定时任务 |
| 数据来源 | 实时行情API | MySQL历史表 |
| 计算函数 | `calc_bond_ext_indicators` | 同（强制导入） |
| 状态管理 | 模块级全局变量 | ComputeEngine实例变量 |
| 写入方式 | 逐tick覆盖写入 | 批量UPDATE JOIN |
| 并发 | 单进程 | 支持多进程 |

### 10.2 数据流向

```
盘中实时:
  行情API → monitor_bond.py → calc_*() → MySQL sssj表

盘后回填:
  MySQL sssj表 → backfill_unified.py → compute_engine → calc_*() → MySQL sssj表 (UPDATE)
                      ↑ 读取原始价格                              ↑ 写入计算字段
```

## 十二、未来优化方向

| 方向 | 优先级 | 说明 |
|------|--------|------|
| 单日内并行（按债券分组） | 低 | 需要解决大盘指标依赖问题 |
| 增量检测（抽样验证完整性） | 中 | 避免重复回填已完成的表 |
| 写入优化（LOAD DATA INFILE） | 中 | 比UPDATE JOIN更快，但需要额外处理 |
| 断点续传 | 低 | 当前重跑成本可接受 |
| Web界面进度展示 | 低 | 当前命令行输出已足够 |
