# 涨停行概选股 —— "主线前5行概"选股功能 设计方案

> 状态：**已确认 / 实施中**　｜　作者：AI 助手　｜　日期：2026-08-11
> 目标：在「涨停行概选股」面板增加一个按钮，一键载入"主线前5的所有股票去重后的行业+概念"作为查询条件，并支持按不同时间点的主线来查。

## 决策定稿（2026-08-11）
- **A 时间维度**：复用涨停面板现有「日期 + 历史时间轴滑块」。
- **B 盘中排序口径**：最终态用 `confidence + stock_count`；盘中时点无 confidence，用"截至该刻归属股票数"排序，UI 标注。
- **C 仅取前N个**：基于**主线股票最终的行业/概念分组统计**（每个行业/概念被多少只主线股票命中），**降序取前 N**。默认全量，提供"仅取前N个"下拉。
- **D 按钮放置**：复用 ztbPanel 标签区，新增按钮，不新开 tab。
- **E 查询语义**：命中这些主线行概的**全市场股票 + 可转债**（即走现有 `/api/stock-picker/query`，返回全市场匹配 + 债券信息），**不是**只看主线那批股票本身。
- 前5固定默认为 5，接口用 `top` 参数保留可配置。

## 实施补充确认（已核实）
- `mysql_util.get_mysql_tool()` 与 `common.url` 同库（`gs`），三表 `stock_anomaly_mainline` / `stock_anomaly` / `cache_stock_industry_concept_bond` 均可访问 → service 统一用 `get_mysql_tool()`。
- 蓝图 `stock_picker_bp` 已在 `blueprint_registry.py` 注册，新增路由挂在该蓝图下即可，无需改注册。
- **E 的实现要点**：新按钮只负责"灌标签"，查询仍走用户点击现有「🔄 查询」→ `queryZtbStocksLatest()` → `/api/stock-picker/query`（全市场 + 债券）。为保证"全市场"语义，**主线选股按钮在"最新涨停"模式与"时间轴"模式下，查询都走 `/api/stock-picker/query`（全市场），不走 `/api/ztb/snapshot/filter`（仅快照涨停股）**。时间轴模式仅用于决定"取哪个时点的主线"，不改变"全市场查询"这一语义。

---

## 一、需求理解

1. 在 **涨停行概选股**（`stock_picker.html` 的 `ztbPanel`）增加一个按钮。
2. 点击后：取 **当天主线排名前 5** 的主线 → 汇总这些主线覆盖的**所有股票** → 用这些股票查出它们的**行业 + 概念** → **去重** → 作为「已选标签」灌入查询条件。
3. 用户随后点「查询」，走现有交叉选股逻辑，得到命中这些行业/概念的股票列表。
4. **支持按不同时间的主线**：既能查当天最终态的主线前5，也能查盘中某个时间点的主线前5。

## 二、现状分析（已核实）

### 2.1 涨停选股前后端链路
- 页面：`src/gs2026/dashboard2/templates/stock_picker.html`，`ztbPanel` 面板
- 路由：`src/gs2026/dashboard2/routes/stock_picker.py`
- 服务：`src/gs2026/dashboard2/services/stock_picker_service.py`
- 已有能力：
  - `/api/stock-picker/ztb-tags?date=` → 返回涨停股的行业/概念标签（带 count）
  - `/api/stock-picker/query?tags=industry:xxx,concept:yyy&date=` → 交叉选股核心查询
  - `ztbPanel` 已有两种模式：**最新涨停** / **历史时间轴**（滑块选盘中时刻，走 `/api/ztb/timestamps`、`/api/ztb/snapshot`）
  - 内存宽表缓存 `_stock_cache`：`stock_code → {stock_name, industries(set), concepts(set), bond}`

### 2.2 主线数据源（两套，均现成）

| 维度 | 表 / 接口 | 内容 | 排序依据 |
|---|---|---|---|
| **最终态**（当天收盘定格） | `stock_anomaly_mainline` 表<br>已有接口 `/api/anomaly/mainlines?date=` | 每条主线一行：`mainline_name`、`confidence`、`stock_count`、`related_stocks`(JSON股票列表)、`first_seen_time`/`last_updated_time` | `confidence DESC, stock_count DESC` ✅ |
| **盘中时间点态** | `stock_anomaly` 表 | 逐股异动：`anomaly_time`、`mainline_names`(JSON归属主线名) | 需按 `anomaly_time <= T` 聚合，用"截至该刻归属股票数"排序 |

### 2.3 关键验证结果
- ✅ 主线 `related_stocks` 里的股票代码是 **6位纯数字**（如 `600272`），与宽表 `cache_stock_industry_concept_bond.stock_code` 格式**完全一致**，实测前30个代码命中宽表 30/30。
- ✅ 因此 "主线股票 → 行业/概念" 可**直接复用内存缓存 `_stock_cache`**，无需新查询。
- ✅ 行业/概念名 → code 的映射可复用 `init_pinyin_searcher()` 的 `items`（每项带 `type`）。
- ✅ 盘中时间点重建可行：实测截至 10:30:00 能从 `stock_anomaly` 聚合出主线排名（示例日 78 条已分析异动，覆盖 09:27~14:52）。
- ⚠️ **口径差异**：最终态主线有 `confidence`；盘中重建态**没有** confidence，只能用"截至该刻的归属股票数"排序。两者排名结果会不同（示例日最终态 top1=机器人概念，10:30 时点 top1=独立个股/医药商业）。

## 三、方案设计

### 3.1 总体思路
> 新增一个 **载入主线前5行概** 按钮，复用涨停面板已有的「日期选择器 + 历史时间轴滑块」作为时间维度，点击后调用新接口拿到去重后的行业+概念标签，灌入现有已选标签区，用户再点「查询」走现有交叉选股链路。

**时间维度天然复用**：
- 「最新涨停」模式下点按钮 → 取 `ztbDate` 对应日期的**最终态**主线前5（走主线表）。
- 「历史时间轴」模式下点按钮 → 取 `ztbDate` + 当前滑块时间 `_currentTime` 的**盘中时点**主线前5（走 `stock_anomaly` 重建）。

### 3.2 后端新增

**接口**：`GET /api/stock-picker/mainline-tags`
- 参数：
  - `date`：YYYYMMDD（必填）
  - `time`：HH:MM:SS（可选；不传=最终态，传=盘中时点重建）
  - `top`：主线数量，默认 5
- 返回（结构对齐现有 `ztb-tags`，前端渲染可复用）：
```json
{
  "code": 0,
  "data": {
    "date": "20260810",
    "time": null,
    "mainlines": [
      {"name": "机器人概念", "stock_count": 12, "confidence": 95}
    ],
    "stock_codes": ["600272", "..."],
    "industries": [{"name": "医药商业", "type": "industry", "code": "881xxx", "count": 3}],
    "concepts":   [{"name": "国企改革", "type": "concept", "code": "886xxx", "count": 5}]
  }
}
```

**Service 新增函数**：`stock_picker_service.get_mainline_tags(date, time=None, top=5)`
1. **取前5主线的股票代码集合**：
   - `time` 为空：`SELECT mainline_name, confidence, stock_count, related_stocks FROM stock_anomaly_mainline WHERE trading_date=:d AND status='active' ORDER BY confidence DESC, stock_count DESC LIMIT :top`，解析 `related_stocks` 收集 code。
   - `time` 非空：`SELECT anomaly_time, stock_code, mainline_names FROM stock_anomaly WHERE trading_date=:d AND ai_status='done' AND mainline_names IS NOT NULL`，Python 侧过滤 `anomaly_time<=T`，按 `mainline_names` 聚合成 `{主线名: set(股票)}`，取股票数 top5，收集这些主线的 code。
2. **股票 → 行业/概念（复用 `_stock_cache`）**：对每个 code 取 `industries`、`concepts`，累加到 `industry_counter`/`concept_counter`（count = 该行业/概念在主线股票中出现次数，用于前端排序）。
3. **名称 → code**：用 `init_pinyin_searcher().items` 建 `ind_name2code` / `con_name2code`（按 type 分开，避免同名行业/概念串码）。
4. 按 count 降序返回 `industries` / `concepts`。

> 注：日期转换沿用现有约定（`date[:4]-date[4:6]-date[6:8]` → 主线表 `trading_date`；`stock_anomaly.trading_date` 同为 DATE）。

### 3.3 前端新增（`stock_picker.html` 的 ztbPanel）

**按钮位置**（见决策点D，下面是推荐方案）：在 `ztbActionSection` 顶部控制区加按钮
```
📎 载入主线前5行概
```
**点击逻辑** `loadMainlineTags()`：
1. 取 `ztbDate`；若 `_ztbMode === 'timeline'` 且有 `_currentTime`，附带 `time` 参数。
2. `fetch('/api/stock-picker/mainline-tags?date=..&time=..')`。
3. 拿到 `industries`/`concepts` → 写入 `ztbAllIndustries`/`ztbAllConcepts` 与 `ztbSelectedTags`（默认全选）→ 调 `renderZtbIndustries()`/`renderZtbConcepts()`/`updateZtbSelectedCount()`（**全部复用现有函数**）。
4. 在标签区上方显示一行来源提示：`来自主线前5：机器人概念、雅下水电…（截至 10:30:00）`。
5. 用户点现有「🔄 查询」→ 走现有 `queryZtbStocks()`（最新模式=`/api/stock-picker/query`）。

> 复用现有 `renderZtbIndustries/renderZtbConcepts/toggleZtbTag/queryZtbStocks/renderResults`，前端增量很小。

## 四、需要你拍板的决策点

| # | 决策点 | 选项 | 我的建议 |
|---|---|---|---|
| **A** | 时间维度实现 | (1) 复用现有日期+时间轴滑块；(2) 只做按日期最终态 | **(1)**：改动小又满足"按不同时间"需求 |
| **B** | 盘中时点排序口径 | 最终态用 `confidence+stock_count`；盘中态**无 confidence**，用"截至该刻归属股票数" | 接受该差异，并在 UI 标注"盘中时点按股票数排名" |
| **C** | 去重标签数量控制 | (1) 全量去重灌入；(2) 按出现频次取 topN（如 top20）防标签爆炸 | **(2) 默认全量但按频次降序**，另加一个"仅取前N个"下拉，用户可控 |
| **D** | 按钮放置 | (1) 复用 ztb 标签区，替换为主线行概；(2) 新开第三个 tab「主线选股」 | **(1)**：符合你"在涨停面板加按钮"的描述，改动最小 |
| **E** | "查询条件"语义确认 | 把去重后的行业+概念作为标签 → 交叉选股 → 命中这些标签的**全市场股票**（按命中个数分组） | 确认是否就是这个语义（而非只展示主线那批股票本身） |

> 特别提示 C/E：前5主线可能覆盖 60+ 只股票，去重后行业+概念标签可能达 50~100 个，全量作为 OR 条件会命中**大量**股票、且"命中个数"分组会很分散。这也是我建议加"仅取前N个"控制的原因。

## 五、工作量与影响面

- **后端**：新增 1 个路由 + 1 个 service 函数（~80 行），不改动现有函数。
- **前端**：新增 1 个按钮 + 1 个 `loadMainlineTags()`（~50 行），复用现有渲染/查询。
- **数据库**：无需建表、无需改表。
- **风险**：低。主要风险是标签爆炸（决策点C 已应对）与盘中口径差异（决策点B 已标注）。
- **不影响**：现有交叉选股、涨停选股、时间轴功能均不动。
