## 1. 公告分析评分优化方案


> 版本: V1.0  
> 日期: 2026-05-02  
> 状态: 已审核通过

## 一、现状诊断

### 1.1 当前评分逻辑

```python
# result_processor.py → _extract_notice_record()
risk_map  = {'高': 75, '中': 50, '低': 25}   # 影响力度 → risk_score
type_map  = {'利好': 75, '中性': 50, '利空': 25}  # 消息类型 → type_score
```

仅根据1个维度做固定映射，每个评分只有3个离散值（25/50/75）。

### 1.2 数据分布（总量154,551条）

| 组合 | 平均分 | 数量 | 占比 |
|------|--------|------|------|
| 低+中性 | 38 | 103,498 | **67.0%** |
| 中+中性 | 50 | 25,338 | 16.4% |
| 低+利好 | 50 | 8,261 | 5.3% |
| 高+利空 | 50 | 5,731 | 3.7% |
| 中+利空 | 38 | 5,350 | 3.5% |
| 中+利好 | 62 | 3,529 | 2.3% |
| 高+中性 | 62 | 2,366 | 1.5% |
| 高+利好 | 75 | 286 | 0.2% |
| 低+利空 | 25 | 192 | 0.1% |

### 1.3 三大致命问题

#### 问题1：67%数据堆积在同一分数，零区分度

超过2/3的公告得分都是38（低+中性），完全无法筛选出值得隔夜的标的。

#### 问题2：积极vs保守评分倒挂

| 隔夜态度 | 数量 | 风险分 | 类型分 | 评分范围 |
|----------|------|--------|--------|---------|
| 积极（应该隔夜） | 439 | 33.3 | 48.7 | 25-75 |
| 保守（应该回避） | 113 | 43.1 | 34.7 | 25-50 |
| 中性 | 448 | 29.5 | 53.0 | 25-75 |

本应隔夜的"积极"组，风险分(33)反而低于"保守"组(43)。评分不仅没有区分度，方向还是反的。

#### 问题3：忽略隔夜超短最关键的维度

| 已有字段 | 对隔夜超短的价值 | 是否参与评分 |
|----------|----------------|-------------|
| open_prediction 开盘预判 | ⭐⭐⭐⭐⭐ 最核心 | ❌ 未使用 |
| market_expectation 市场预期 | ⭐⭐⭐⭐ 放大波动 | ❌ 未使用 |
| duration 持续性 | ⭐⭐⭐ 一日游不值得隔夜 | ❌ 未使用 |
| risk_level 影响力度 | ⭐⭐⭐ 基础过滤 | ✅ 映射过粗 |
| notice_type 消息类型 | ⭐⭐ 方向参考 | ✅ 利空=25不合理 |

### 1.4 评分档位与消息类型分布

| 档位 | 数量 | 利好 | 利空 | 利空占比 |
|------|------|------|------|---------|
| 高分档(≥60) | 6,181 | 3,815 | 0 | 0.0% |
| 中分档(40-60) | 39,330 | 8,261 | 5,731 | 14.6% |
| 低分档(<40) | 109,040 | 0 | 5,542 | 5.1% |

高分档中0条利空（因为利空=25，永远进不了高分档），这对隔夜超短是严重缺陷——强利空信号同样具有高操作价值。

## 二、优化方案

### 2.1 核心思路

- **保留** `risk_score` + `type_score`（向后兼容，优化映射逻辑）
- **新增** `overnight_score`（隔夜综合评分 0-100），专为隔夜超短决策优化

### 2.2 新增字段

```sql
ALTER TABLE analysis_notice_detail_2026 
  ADD COLUMN overnight_score TINYINT UNSIGNED DEFAULT 0 
  COMMENT '隔夜综合评分(0-100)' AFTER type_score;
```

### 2.3 overnight_score 评分公式

```
overnight_score = 开盘预判分(40%) + 影响力度分(25%) + 市场预期分(20%) + 持续性分(15%)
```

#### ① 开盘预判分（权重40%，满分40）

| 开盘预判 | 得分 | 逻辑 |
|----------|------|------|
| 大幅高开(>5%) | 40 | 隔夜做多最佳信号 |
| 大幅低开(>5%) | 38 | 隔夜做空/回避强信号 |
| 高开(2-5%) | 30 | 有隔夜价值 |
| 低开(2-5%) | 28 | 方向明确，有操作价值 |
| 小幅高开(0-2%) | 18 | 幅度有限，性价比低 |
| 小幅低开(0-2%) | 15 | 幅度有限 |
| 平开 | 5 | 隔夜无意义 |
| 空值/未知 | 5 | 默认最低 |

> 关键设计：大幅低开也给高分（38），因为方向明确本身就有隔夜价值。隔夜超短需要的是"波动"而非"方向"。

#### ② 影响力度分（权重25%，满分25）

| 影响力度 | 得分 |
|----------|------|
| 高 | 25 |
| 中 | 12 |
| 低 | 3 |

#### ③ 市场预期分（权重20%，满分20）

| 市场预期 | 得分 |
|----------|------|
| 超预期 | 20 |
| 低于预期 | 18 |
| 符合预期 | 8 |
| 空值/未知 | 5 |

#### ④ 持续性分（权重15%，满分15）

| 持续性 | 得分 |
|----------|------|
| 2-3日 | 15 |
| 一周以上 | 13 |
| 持续发酵 | 12 |
| 一日游 | 6 |
| 空值/未知 | 5 |

### 2.4 评分档位对应操作建议

| 档位 | 分数 | 含义 | 操作建议 |
|------|------|------|---------|
| S级 | 85-100 | 极强隔夜信号 | 重仓隔夜（配合方向判断） |
| A级 | 70-84 | 强隔夜信号 | 可积极隔夜 |
| B级 | 50-69 | 一般信号 | 轻仓试探或观望 |
| C级 | 30-49 | 弱信号 | 不建议隔夜 |
| D级 | 0-29 | 无隔夜价值 | 完全回避 |

### 2.5 risk_score 优化

```python
# 旧逻辑：3个固定值
risk_map = {'高': 75, '中': 50, '低': 25}

# 新逻辑：影响力度 × 市场预期 组合
def calc_risk_score(risk_level, market_expectation):
    base = {'高': 70, '中': 45, '低': 20}.get(risk_level, 45)
    bonus = {'超预期': 20, '低于预期': 15, '符合预期': 5}.get(market_expectation, 0)
    return min(base + bonus, 99)
```

| 组合 | 新评分 |
|------|--------|
| 高+超预期 | 90 |
| 高+低于预期 | 85 |
| 高+符合预期 | 75 |
| 中+超预期 | 65 |
| 中+符合预期 | 50 |
| 低+任何 | ≤40 |

### 2.6 type_score 优化

```python
# 旧逻辑：利空永远=25
type_map = {'利好': 75, '中性': 50, '利空': 25}

# 新逻辑：方向强度评分（利空也可以得高分）
def calc_type_score(notice_type, open_prediction):
    gap_score = _parse_gap_level(open_prediction)  # 0-4
    direction = {'利好': 1, '利空': -1, '中性': 0}.get(notice_type, 0)
    clarity = abs(direction) * 30 + gap_score * 10 + 20
    return min(int(clarity), 99)
```

## 3. 公告分析-公告类型字典动态读取


## 修改日期
2026-04-30

## 修改背景

公告分析Prompt中的"公告类型字典"原来是**硬编码**在代码中的272个类型，维护困难（新增/修改类型需要改代码重新部署）。同时，AI返回的`公告类型`字段没有被提取和存储到数据库中，造成信息丢失。

## 修改内容

### 1. 数据库表结构

```sql
ALTER TABLE analysis_notice_detail_2026 
ADD COLUMN notice_category VARCHAR(64) DEFAULT '' AFTER notice_type;
```

**说明：**
- `notice_type` 字段（已有）= `enum('利好','利空','中性')` — 存储消息类型
- `notice_category` 字段（新增）= `VARCHAR(64)` — 存储公告类型分类（如"业绩暴增超预期"、"定向增发"等）

### 2. 字典动态读取

**字典来源表：** `notice_type`（272条记录，`flag=1`启用）

```python
# get_notice_analysis()中新增：
notice_type_dic_sql = "select type from notice_type where flag='1'"
notice_type_dic_str = ','.join(pd.read_sql(notice_type_dic_sql, conn)['type'].astype(str))
```

**Prompt中使用：**
```python
# 修改前（硬编码272个类型）
公告类型（公告类型字典：业绩暴增超预期,业绩预增合预期,...年报盈转亏）

# 修改后（动态读取）
公告类型（公告类型字典：""" + notice_type_dic_str + """）
```

### 3. 提取和存储

**`_extract_notice_record()`新增：**
```python
'notice_category': str(notice.get('公告类型', '')).strip()[:64],
```

**`process_notice()`的key_fields新增：**
```python
key_fields = ['risk_level', 'notice_type', 'notice_category',  # ← 新增
              'judgment_basis', 'key_points', ...]
```

## 修改文件

| 文件 | 修改内容 |
|------|----------|
| `deepseek_analysis_notice.py` | `deepseek_ai()`签名新增`notice_type_dic_str`参数 |
| `deepseek_analysis_notice.py` | Prompt硬编码字典 → 动态变量 |
| `deepseek_analysis_notice.py` | `get_notice_analysis()`新增字典查询 |
| `deepseek_analysis_notice.py` | `_retry_one_by_one()`签名同步传参 |

## 数据流

```
get_notice_analysis()
    ├─ 查询 notice_type 表 → notice_type_dic_str（272个类型逗号分隔）
    └─ deepseek_ai(query_list, notice_type_dic_str, ...)
        ├─ Prompt: 公告类型（公告类型字典：{notice_type_dic_str}）
        ├─ AI返回JSON: {"公告集合": [{"公告类型": "业绩暴增超预期", ...}]}
        └─ process_notice(json_data)
            ├─ _extract_notice_record() → notice_category = "业绩暴增超预期"
            └─ batch_insert_on_duplicate() → 写入 notice_category 字段
```

## 4. P2-领域和公告分析MySQL批量插入优化


## 修改日期
2026-04-30

## 修改背景

AI分析模块（领域分析、公告分析）在将DeepSeek返回的JSON拆分入库时，采用逐条INSERT方式写入MySQL，每条记录一次网络往返，性能低下。

## 问题分析

### 领域分析（event_driven）
```
DeepSeek返回 ~30条消息JSON
    └─ result_processor.process_domain()
        └─ for msg in messages:  ← 30次循环
            └─ _save_domain_to_mysql(record)  ← 30次独立INSERT
```
**瓶颈：** 30次数据库往返

### 公告分析（notice）
```
DeepSeek返回 5-15条公告JSON
    └─ result_processor.process_notice()
        └─ for notice in notices:  ← 5-15次循环
            └─ _save_notice_to_mysql(record)  ← 5-15次独立INSERT
```
**瓶颈：** 5-15次数据库往返

## 优化方案

将逐条INSERT改为`batch_insert_on_duplicate()`批量插入（已在`mysql_util.py`中实现）。

### 优化后流程
```
process_domain() / process_notice()
    ├─ 提取所有记录到列表
    ├─ mysql_tool.batch_insert_on_duplicate()  ← 1次批量INSERT
    └─ Redis逐条写入（保持不变）
```
