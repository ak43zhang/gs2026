# 监控页面慢接口分析与增量排行优化方案

## 文档信息
- **日期**: 2026-07-06
- **问题**: 股票/债券上攻排行API响应时间超过2400ms
- **目标**: 实时tick场景降至~10ms，后退/重建场景降至~300ms

---

## 一、问题现象

### 日志记录
```
[SlowAPI] GET /api/monitor/attack-ranking/stock | 2438.48ms | DB: 2q/195.48ms | Redis: 0q/0.00ms
[SlowAPI] GET /api/monitor/market-overview | 2359.87ms | DB: 2q/189.68ms | Redis: 0q/0.00ms
```

### 核心矛盾
- 中间件追踪的DB耗时仅 195ms（2次查询）
- 总响应时间 2438ms
- **~2243ms 未被追踪**

## 二、根因分析

### 2.1 market-overview 接口（已修复）

**问题**: 两次 `DataService()` 实例化，每次创建新的SQLAlchemy engine（连接池初始化~500ms）

```python
# 问题代码
ds = DataService()           # ❌ ~500ms 连接池初始化
market_avg = ds._query_market_avg(...)

ds = DataService()           # ❌ 又 ~500ms
bond_market_avg = ds._query_bond_market_avg(...)
```

**修复**: 改用 `_get_shared_engine()` 直接查询，commit `f41d3c9`

### 2.2 attack-ranking/stock 接口（本次优化目标）

**耗时分解**:
```
总耗时: 2438ms
├── data_service.get_ranking_at_time()  ~2000ms
│   ├── DataService 自有 engine 连接     ~500ms（非共享连接池）
│   └── GROUP BY COUNT(*) 全表聚合       ~1500ms
├── _enrich_change_pct_and_main_net()   ~200ms (中间件追踪)
└── _enrich_stock_data()                ~200ms (缓存命中)
```

**核心瓶颈SQL**:
```sql
SELECT code, name, COUNT(*) AS count
FROM monitor_gp_top30_20260706
WHERE time <= '15:00:00'    -- 覆盖全天 ~23万行（3秒/tick × 30条/tick × 7800tick）
GROUP BY code, name
ORDER BY count DESC
```

**为什么每次都这么慢**:
- 每3秒一个tick，表每天新增 ~23万行
- 每次API调用都从头聚合整张表
- 使用 DataService 自有 engine（非共享，每次新建连接）

---

## 三、优化方案：增量计数器

### 3.1 核心思路

每个tick只新增~30行数据，但原方案每次扫描全表（~23万行）重新聚合。

**优化**: 维护内存累计计数器，每个tick只查增量行（~30行），累加到计数器。

```
tick T:   计数器 = { 688416: 5, 301536: 4, ... }     ← 已有
tick T+1: 增量查询 = SELECT ... WHERE time > T AND time <= T+1  → 30行
          计数器 = { 688416: 6, 301536: 5, ... }     ← 累加
```

### 3.2 实现代码

```python
# 进程级增量缓存
_rank_incremental = {}       # { 'stock:20260706': { code: {'name':x, 'count':n} } }
_rank_last_time = {}         # { 'stock:20260706': '09:32:06' }


def _get_ranking_fast(asset_type, date, time_str, limit):
    """
    通用增量排行查询（stock/bond共用）
    
    路径1 - 时间前进（实时tick/滑动前进）:
        只查 time > last AND time <= current（~30行），内存累加
    路径2 - 时间后退 / 首次加载 / 宕机重启:
        共享引擎全量 GROUP BY 一次，重建计数器
    """
    from sqlalchemy import text
    engine = _get_shared_engine()
    
    prefix = 'gp' if asset_type == 'stock' else 'zq'
    table = f"monitor_{prefix}_top30_{date.replace('-', '')}"
    cache_key = f"{asset_type}:{date}"
    
    last_time = _rank_last_time.get(cache_key)
    counters = _rank_incremental.get(cache_key)
    
    if counters is not None and last_time and time_str > last_time:
        # ✅ 路径1: 时间前进 → 增量查询（~10ms）
        sql = text(f"SELECT code, name FROM {table} WHERE time > :last AND time <= :current")
        with engine.connect() as conn:
            rows = conn.execute(sql, {'last': last_time, 'current': time_str}).fetchall()
        for r in rows:
            code, name = r[0], r[1]
            if code in counters:
                counters[code]['count'] += 1
            else:
                counters[code] = {'name': name, 'count': 1}
    else:
        # ⚠️ 路径2: 后退/首次/重启 → 全量重建（~300ms）
        sql = text(f"""
            SELECT code, name, COUNT(*) as cnt FROM {table}
            WHERE time <= :time_str GROUP BY code, name
        """)
        with engine.connect() as conn:
            rows = conn.execute(sql, {'time_str': time_str}).fetchall()
        counters = {r[0]: {'name': r[1], 'count': r[2]} for r in rows}
    
    # 更新缓存
    _rank_incremental[cache_key] = counters
    _rank_last_time[cache_key] = time_str
    
    # 排序输出
    sorted_items = sorted(counters.items(), key=lambda x: -x[1]['count'])
    if limit:
        sorted_items = sorted_items[:limit]
    return [{'code': code, 'name': v['name'], 'count': v['count'], 'rank': i+1}
            for i, (code, v) in enumerate(sorted_items)]
```

### 3.3 各场景执行路径

| 场景 | 条件判断 | 执行路径 | 耗时 |
|------|---------|---------|------|
| 实时tick（每3秒） | time_str > last_time | 路径1: 增量30行 | ~10ms |
| 时间轴前进滑动 | time_str > last_time | 路径1: 增量 | ~10ms |
| 时间轴后退滑动 | time_str < last_time | 路径2: 全量重建 | ~300ms |
| 宕机重启首次 | counters=None | 路径2: 全量重建 | ~300ms |
| 切换日期 | cache_key不同 → counters=None | 路径2: 全量重建 | ~300ms |

### 3.4 时序示例

```
【实时tick（每3秒）】
  tick 1 (09:25:03) → counters=None       → 路径2: 全量重建 (~300ms) ← 仅第一次
  tick 2 (09:25:06) → 09:25:06 > 09:25:03 → 路径1: 增量30行 (~10ms)
  tick 3 (09:25:09) → 09:25:09 > 09:25:06 → 路径1: 增量30行 (~10ms)
  ...
  tick N (15:00:00) → time > last          → 路径1: 增量30行 (~10ms)

【宕机重启】
  重启后第1次 → counters=None → 路径2: 全量重建 (~300ms)
  重启后第2次 → time > last   → 路径1: 增量 (~10ms)

【时间轴后退滑动】
  15:00 → 09:32 → 09:32 < 15:00 → 路径2: 全量重建 (~300ms)
  09:32 → 09:33 → 09:33 > 09:32 → 路径1: 增量 (~10ms)
```

## 五、关键保证

| 维度 | 说明 |
|------|------|
| **逻辑正确性** | 增量累加结果 ≡ 全量 GROUP BY COUNT(*) 结果 |
| **无外部依赖** | 纯内存计数器，不依赖Redis/额外表 |
| **自愈能力** | 重启自动走路径2重建，无需手动干预 |
| **通用性** | stock/bond 共用同一函数，asset_type 参数区分 |
| **隔离性** | cache_key 含日期，不同日期互不干扰 |
| **线程安全** | Flask 默认单线程处理请求，无并发问题 |
