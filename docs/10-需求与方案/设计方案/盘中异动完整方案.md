## 一、问题背景

### 当前实现的缺陷

盘中异动的「市场主线」展示中，分析结论来源有误：

**前端 `calcMainlinesFromData()` 中的逻辑（anomaly.html 第1590行）**：

```javascript
// 提取催化事件（从第一只归属该主线的股票的异动原因中取）
if (!mainlineMap[name].catalyst && item.ai_analysis) {
    mainlineMap[name].catalyst = item.ai_analysis['异动原因'] || '';
}
```

- 主线的「分析展示」= 第一只归入该主线的股票的 `异动原因`
- `异动原因` 是针对个股的分析（如"某公司获华为大单，短期催化"）
- 展示出来就是：主线名"华为产业链" → 分析内容却是"XX公司获华为大单导致涨停"
- **结论太依赖某只个股，不是主线本身的分析**

### 已有但未利用的数据

每只股票的 `ai_analysis['主线归属']` 中包含主线级字段：

```json
{
    "mainline_name": "华为产业链",
    "mainline_reason": "华为Mate70供应链备货需求爆发，带动核心供应商集体异动",
    "catalyst": "华为宣布Mate70提前量产，供应链开始大规模备货",
    "evidence": "该公司是华为核心光学模组供应商，订单直接受益"
}
```

`mainline_reason` 和 `catalyst` 是主线级描述，`evidence` 是个股级。但前端没用这些字段。

## 三、核心设计理念

### 分离静态分析与动态追踪

```
┌─────────────────────────────────────────────┐
│ 静态层（AI合成，里程碑触发，最多2次/主线）       │
│   · 核心驱动逻辑                              │
│   · 催化事件解读                              │
│   · 市场意义与持续性判断                       │
└─────────────────────────────────────────────┘
┌─────────────────────────────────────────────┐
│ 动态层（算法生成，每只新增追加，无AI成本）       │
│   · 发展阶段：发酵→扩散→高潮→分歧              │
│   · 发展动态：时间线式追踪                      │
│   · 实时指标：成员数/置信度变化                  │
└─────────────────────────────────────────────┘
```

**为什么这样拆分？**
- 核心分析应该稳定，不因每只新股加入而反复变动
- 动态状态应该实时，用户能看到主线最新发展
- AI成本可控：每条主线每天最多2次合成调用

## 四、里程碑触发策略

### 触发条件

| 里程碑 | 触发条件 | AI操作 | 合成级别 |
|--------|----------|--------|----------|
| **形成** (formation) | 首次达到 2 只成员 | ✅ 首次合成 | formation |
| **确认** (confirmed) | 首次达到 5 只 OR 置信度首次≥85% | ✅ 升级合成 | confirmed |
| **中间状态** (3-4只) | 非里程碑 | ❌ 不触发AI | - |
| **后续加入** (6只+) | 非里程碑 | ❌ 不触发AI | - |

### 为什么选这两个节点？

- **2只**：主线首次被确认为真实存在（从"独立个股"变为"有主线"），此时需要建立核心定性
- **5只**：置信度达85%+，数据充足，可以做更深入的综合分析
- **不选3只**：3只时主线仍在发展中，核心逻辑在2只时已建立，无需重新分析
- **不选每只**：频繁重做会导致结论不断漂移，用户体验差

### 防重复触发

- `synthesis_level` 字段记录已完成的合成级别
- formation 只触发一次（`synthesis_level` 从 NULL → 'formation'）
- confirmed 只触发一次（`synthesis_level` 从 'formation' → 'confirmed'）

## 六、阶段判定算法

```python
def calc_market_stage(stock_count, confidence, last_join_minutes_ago):
    """根据规则计算主线当前阶段（无AI成本）"""
    if stock_count <= 2 and confidence < 50:
        return '发酵期'
    elif stock_count <= 4 and confidence < 80:
        return '扩散期'
    elif last_join_minutes_ago <= 20:
        return '高潮期'   # 仍有新成员快速加入
    else:
        return '分歧期'   # 扩散放缓，可能见顶
```

### 阶段含义

| 阶段 | 特征 | 操作建议 |
|------|------|----------|
| 发酵期 | 2只，置信度低，刚形成 | 观察，等待确认 |
| 扩散期 | 3-4只，置信度中等 | 关注龙头表现 |
| 高潮期 | 5只+，仍有新成员快速加入 | 短线活跃，注意高位风险 |
| 分歧期 | 扩散放缓，超过20分钟无新成员 | 谨慎，可能见顶 |

## 八、动态追踪条目生成（模板化，无AI）

每只新股加入时自动追加 `developments` 条目：

```python
def build_development_entry(stock_name, role, evidence, stock_count, confidence, is_milestone=False):
    """生成动态追踪条目"""
    # 截取证据关键部分
    evidence_brief = evidence[:30] + '...' if len(evidence) > 30 else evidence
    
    entry_text = f"{stock_name}加入（{role}），{evidence_brief}"
    
    entries = [{"time": current_time_str, "text": entry_text}]
    
    # 里程碑标记
    if is_milestone == 'formation':
        entries.append({"time": current_time_str, "text": f"【主线形成】2只成员，开始追踪"})
    elif is_milestone == 'confirmed':
        entries.append({"time": current_time_str, "text": f"【主线确认】{stock_count}只成员，置信度{confidence}%"})
    
    return entries
```

## 十一、成本与风险评估

### AI 调用成本
- 每条主线每天最多 2 次合成（formation + confirmed）
- 典型交易日 3-8 条主线 → 6-16 次额外 AI 调用
- 相比现有 Phase 2 每只股票 1 次调用（日均 20-50 次），增加约 30%

### 风险点
- 合成时主线成员可能还未全部分析完 → 解决：formation 在 2 只时触发，信息足够做初步定性
- AI 返回格式异常 → 解决：复用现有 `repair_llm_json` + fallback 到前端聚合模式
- 合成耗时影响 Phase 2 流速 → 解决：合成可异步执行，不阻塞主流程

### 回退策略
- 前端做双层 fallback：优先用 `mainline_summary` → 退而用 `主线归属.mainline_reason` → 最后用 `异动原因`
- 合成失败不影响现有功能，只是展示退回旧模式

### 修改方案

**后端**：新增 API `/api/anomaly/latest-trading-date`

```python
@anomaly_bp.route('/latest-trading-date', methods=['GET'])
def get_latest_trading_date():
    """获取最近的交易日（如果今天不是交易日则返回上一个交易日）"""
    today = date.today().strftime('%Y-%m-%d')
    sql = text("""
        SELECT trade_date FROM data_jyrl 
        WHERE trade_date <= :today AND trade_status = '1'
        ORDER BY trade_date DESC LIMIT 1
    """)
    with engine.connect() as conn:
        result = conn.execute(sql, {'today': today})
        row = result.fetchone()
    
    trading_date = row[0] if row else today
    return jsonify({'success': True, 'date': trading_date})
```

**前端**：页面加载时先获取交易日再加载数据

def get_stock_locate_data(stock_code: str, date: str = None) -> dict:
    """获取股票定位数据"""
    if date is None:
        date = datetime.now().strftime('%Y%m%d')
    
    # 1. 查询股票基本信息
    stock_info = get_stock_info(stock_code)
    if not stock_info:
        return None
    
    # 2. 查询所属主线（行业/概念）
    mainline = get_mainline_by_stock(stock_code, date)
    
    # 3. 查询最强标的（同行业/同概念）
    strongest = get_strongest_in_mainline(mainline, date, exclude=stock_code)
    
    # 4. 查询可转债
    bond = get_bond_by_stock(stock_code)
    
    # 5. 查询异动记录
    anomalies = get_stock_anomalies(stock_code, date)
    
    return {
        'stock': stock_info,
        'mainline': mainline,
        'strongest': strongest,
        'bond': bond,
        'anomalies': anomalies
    }

def get_mainline_by_stock(stock_code: str, date: str) -> dict:
    """根据股票查询所属主线"""
    # 从行业表查询
    sql = """
        SELECT industry as name, GROUP_CONCAT(stock_code) as stocks
        FROM analysis_industry_{date}
        WHERE stock_code = %s
        GROUP BY industry
    """.format(date=date)
    
    # 或从概念表查询
    # ...
    
    return {'name': '行业名称', 'stocks': ['code1', 'code2']}

def get_bond_by_stock(stock_code: str) -> dict:
    """根据股票查询可转债"""
    # 从映射表查询
    mapping = get_stock_bond_mapping(stock_code)
    if mapping and mapping.get('bond_code'):
        return {
            'code': mapping['bond_code'],
            'name': mapping['bond_name'],
            'price': get_bond_price(mapping['bond_code'])
        }
    return None

def get_stock_anomalies(stock_code: str, date: str) -> list:
    """查询股票异动记录"""
    # 从异动表查询
    table = f"anomaly_events_{date}"
    sql = f"""
        SELECT time, type, description
        FROM {table}
        WHERE stock_code = %s
        ORDER BY time DESC
        LIMIT 50
    """

    return [{'time': '10:30:00', 'type': '拉升', 'desc': '快速上涨5%'}]

## 6. 盘中异动潜在最强标的挖掘系统设计方案


## 一、需求背景

当前系统已具备：
- 市场主线识别（基于已涨停股票）
- 市场最强标的排名（基于主线参与度）

新增需求：
- 基于已识别主线，挖掘**尚未涨停但可能即将涨停**的潜在标的
- 提供介入点建议，辅助短线交易决策

## 二、核心功能

### 2.1 功能概述

| 功能模块 | 说明 |
|---------|------|
| 自动挖掘 | 每新增1个`done`股票，自动触发潜在标的挖掘 |
| 手动挖掘 | 用户点击按钮，实时触发挖掘 |
| 双模式展示 | 实时模式显示最新，复盘模式跟随时间轴 |
| 可切换面板 | 市场最强标的 / 潜在最强标的 标签切换 |

### 2.2 展示内容

每只潜在标的包含：
- 股票代码/名称
- 排名（1-10）
- 涉及主线数量
- 涉及主线详情（名称、原因、证据）
- 综合评分（0-100）
- 建议介入点
- 风险等级
- 选股逻辑总结

- 每条主线必须有明确的催化事件，不能仅凭"同行业"归类
- 如果当前股票不属于任何已有主线，但与之前某些股票有共同催化，则形成新主线
- 如果完全是个股逻辑（如业绩大增、股权激励），标记为独立个股
- 标记为"⚠️未分析"的股票没有原因和主线信息，只做时间线参考，不要纳入关联分析

【当前新涨停股票】

{watchlist_section}

{all_stocks_summary}

【已识别的市场主线】
{existing_mainlines}

【分析任务】
1. 分析当前股票的涨停原因（优先参考盘前预判消息，其次AI推理）
2. 逐一检查每条已有主线，判断当前股票是否归属：
   - 归属条件：有共同的催化事件或驱动逻辑
   - 一只股票可归属多条主线
   - 不归属则跳过，不要强行归类
3. 检查是否可以和之前某些股票形成新主线：
   - 2只及以上已分析股票有共同催化 → 建立新主线
   - 新主线命名要简洁精准（如"低空经济"、"AI算力"、"锂电反转"）
4. 对于归属的每条主线，评估角色：
   - 龙头：最先涨停 or 辨识度/弹性最高
   - 跟风：逻辑相关但非核心标的
   - 补涨：明显滞后跟随
5. 主线置信度规则：
   - 2只确认=40, 3只=60, 4只=75, 5只+=85+
   - 同一只股票归属多条主线时，每条主线独立计算置信度

【输出JSON格式】

## 9. 盘中异动分析系统设计


## 一、系统概述

盘中异动分析系统是整个分析闭环的**盘中信号链**，与盘前预判（领域/新闻/公告分析）和盘后复盘（涨停分析）形成完整的内循环：

```
盘前预判 ──→ 盘中验证 ──→ 盘后复盘 ──→ 反馈预判权重
(领域/新闻/公告)  (异动分析)    (涨停分析)
```

**核心目标**：通过实时监测股票首次涨停异动，结合盘前预判消息，挖掘异动原因及联动板块。

---

## 二、数据源

### 2.1 三表融合的 watchlist 数据

watchlist 从三张分析结果表中提取关注标的，时间区间与智能报告一致：

| 数据源 | 表名 | 过滤条件 | 时间条件 |
|--------|------|---------|---------|
| 领域分析 | `analysis_domain_detail_2026` | `news_type='利好' AND news_size='重大'` | `event_time >= '{start} 15:00:00' AND event_time < '{end} 09:30:00'` |
| 新闻分析 | `analysis_news_detail_2026` | `news_type='利好' AND composite_score >= 50` | `publish_time >= '{start}' AND publish_time <= '{end}'` |
| 公告分析 | `analysis_notice_detail_2026` | `overnight_score >= 70 AND notice_type='利好'` | `notice_date >= '{start}' AND notice_date <= '{end}'` |

### 2.2 股票代码与消息提取

| 数据源 | 股票代码字段 | 消息字段 | 行业/概念字段 |
|--------|-------------|---------|-------------|
| 领域分析 | `stock_codes` (JSON数组) | `key_event` | `sectors` (JSON), `concepts` (JSON) |
| 新闻分析 | `leading_stocks` (JSON数组) | `title` | `sectors` (JSON), `concepts` (JSON) |
| 公告分析 | `stock_code` (直接字段) | `notice_title` | 无（需通过 stock_code 查 `cache_stock_industry_concept_bond`） |

## 五、完整流程时序

### T日 盘后（15:05-18:00）—— 领域/新闻/公告分析运行（不动）

已有分析进程自动写入三张结果表：

```
analysis_domain_detail_2026  分析_domain_detail_2026  analysis_news_detail_2026
├── key_event: "工信部集成电路扶持政策2.0"      ├── title: "青松股份净利润增长"     ├── notice_title: "海泰科收购预案"
├── stock_codes: ["002049", "603501"]            ├── leading_stocks: ["300132"]      ├── stock_code: "301022"
├── sectors: ["半导体"]                          ├── sectors: ["化学制品"]            ├── overnight_score: 100
└── concepts: ["芯片"]                           └── concepts: ["化妆品概念"]         └── notice_type: "利好"
```

### T+1日 盘前 08:30 —— watchlist 生成

`realtime/watchlist.py` 通过 cron 自动执行：

1. 使用 `get_start_end()` 获取时间区间
2. 从三张表中分别查询符合条件的记录
3. 提取 stock_codes / leading_stocks / stock_code
4. 合并去重（同一股票代码只保留一条，合并消息列表）
5. 标注数据来源（domain / news / notice）
6. 写入 Redis `anomaly:watchlist:{T+1}`

### T+1日 盘中 09:30-15:00 —— 异动检测 + AI分析

#### 增量涨停检测（monitor_stock.py）

每个 tick 数据写入后：
1. 获取当前 tick 涨停股票集合
2. 与上一 tick 做差集 → 得到增量涨停
3. 对每只增量涨停股票：
   - Redis SADD 去重（确保只记首次）
   - 查 watchlist 获取盘前预判消息
   - 查 stock_name
   - 写入 `stock_anomaly` 表

**覆盖所有涨停方式**：竞价涨停、盘中封板、回封（Redis去重确保只记首次）

#### AI分析（realtime/anomaly_analyzer.py）

独立进程，每3秒轮询：
1. 查询 `ai_status='pending'` 的异动
2. 逐条加分布式锁
3. 构造 Prompt（带盘前预判背景 + 数据来源标注）
4. DeepSeek 分析
5. 更新异动表（分析结果 + forecast_match）
6. 释放锁，处理下一条

### 前端展示（/anomaly 页面）

- 独立页面，导航栏位置：数据监控 → 盘中异动 → 数据采集
- 样式与 monitor.html 一致
- 每5秒轮询 `/api/anomaly/list`
- 显示：异动时间、股票代码/名称、涨跌幅、**数据来源标注**、盘前预判消息、AI分析结果

## 七、内循环关联机制

```
领域分析输出 stock_codes + key_event
    ↓
新闻分析输出 leading_stocks + title
    ↓
公告分析输出 stock_code + notice_title
    ↓
watchlist.py 三表融合 → 同一股票代码合并消息，标注来源
    ↓
Redis anomaly:watchlist:{date}
    ↓
盘中异动检测 → 查 watchlist → 匹配到盘前预判消息
    ↓
AI分析 Prompt 中带入盘前预判背景 + 来源标注
    ↓
分析输出 forecast_match (exact/partial/none)
    ↓
存入 stock_anomaly 表，供下次盘前 watchlist 参考
```

**关联准确性保证**：不是猜测关联，而是三张分析表已经明确输出了股票代码和具体消息，watchlist 直接用代码精确匹配。

## 五、完整流程时序

### T日 盘后（15:05-18:00）—— 领域/新闻/公告分析运行（不动）

已有分析进程自动写入三张结果表：

```
analysis_domain_detail_2026  分析_domain_detail_2026  analysis_news_detail_2026
├── key_event: "工信部集成电路扶持政策2.0"      ├── title: "青松股份净利润增长"     ├── notice_title: "海泰科收购预案"
├── stock_codes: ["002049", "603501"]            ├── leading_stocks: ["300132"]      ├── stock_code: "301022"
├── sectors: ["半导体"]                          ├── sectors: ["化学制品"]            ├── overnight_score: 100
└── concepts: ["芯片"]                           └── concepts: ["化妆品概念"]         └── notice_type: "利好"
```

### T+1日 盘前 08:30 —— watchlist 生成

`realtime/watchlist.py` 通过 cron 自动执行：

1. 使用 `get_start_end()` 获取时间区间
2. 从三张表中分别查询符合条件的记录
3. 提取 stock_codes / leading_stocks / stock_code
4. 合并去重（同一股票代码只保留一条，合并消息列表）
5. 标注数据来源（domain / news / notice）
6. 写入 Redis `anomaly:watchlist:{T+1}`

### T+1日 盘中 09:30-15:00 —— 异动检测 + AI分析

#### 增量涨停检测（monitor_stock.py）

每个 tick 数据写入后：
1. 获取当前 tick 涨停股票集合
2. 与上一 tick 做差集 → 得到增量涨停
3. 对每只增量涨停股票：
   - Redis SADD 去重（确保只记首次）
   - 查 watchlist 获取盘前预判消息
   - 查 stock_name
   - 写入 `stock_anomaly` 表

**覆盖所有涨停方式**：竞价涨停、盘中封板、回封（Redis去重确保只记首次）

#### AI分析（realtime/anomaly_analyzer.py）

独立进程，每3秒轮询：
1. 查询 `ai_status='pending'` 的异动
2. 逐条加分布式锁
3. 构造 Prompt（带盘前预判背景 + 数据来源标注）
4. DeepSeek 分析
5. 更新异动表（分析结果 + forecast_match）
6. 释放锁，处理下一条

### 前端展示（/anomaly 页面）

- 独立页面，导航栏位置：数据监控 → 盘中异动 → 数据采集
- 样式与 monitor.html 一致
- 每5秒轮询 `/api/anomaly/list`
- 显示：异动时间、股票代码/名称、涨跌幅、**数据来源标注**、盘前预判消息、AI分析结果

## 七、内循环关联机制

```
领域分析输出 stock_codes + key_event
    ↓
新闻分析输出 leading_stocks + title
    ↓
公告分析输出 stock_code + notice_title
    ↓
watchlist.py 三表融合 → 同一股票代码合并消息，标注来源
    ↓
Redis anomaly:watchlist:{date}
    ↓
盘中异动检测 → 查 watchlist → 匹配到盘前预判消息
    ↓
AI分析 Prompt 中带入盘前预判背景 + 来源标注
    ↓
分析输出 forecast_match (exact/partial/none)
    ↓
存入 stock_anomaly 表，供下次盘前 watchlist 参考
```

**关联准确性保证**：不是猜测关联，而是三张分析表已经明确输出了股票代码和具体消息，watchlist 直接用代码精确匹配。
