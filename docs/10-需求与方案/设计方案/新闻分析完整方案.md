## 1. P2-新闻分析MySQL批量插入优化


## 优化背景

**问题：** `deepseek_analysis_news_combine.py`中MySQL插入很慢

**原因分析：**
- AI分析返回15-20条消息
- 逐条执行INSERT（15-20次数据库操作）
- 每次INSERT都是独立连接+网络往返

**优化目标：** 将15-20次INSERT合并为1次批量INSERT

## 优化方案

### 1. 新增批量插入方法（mysql_util.py）

```python
def batch_insert_on_duplicate(self, table_name: str, records: list, key_fields: list = None) -> int:
    """
    【P2优化】批量插入数据，支持ON DUPLICATE KEY UPDATE
    
    将多条记录合并为1条INSERT语句，大幅提升写入性能。
    
    Args:
        table_name: 目标表名
        records: 记录列表，每条记录是字典 {field: value}
        key_fields: 用于ON DUPLICATE KEY UPDATE的字段列表
        
    Returns:
        int: 成功插入/更新的记录数，-1表示失败
    """
```

**特点：**
- 可复用：任何需要批量插入的场景都可以使用
- 可移植：不依赖特定业务逻辑
- 支持ON DUPLICATE KEY UPDATE

### 2. 修改新闻分析入库逻辑（news_result_processor.py）

**优化前：**
```python
for msg in messages:  # 15-20条
    record = extract_record(msg, ...)
    save_to_mysql(record)  # 15-20次INSERT
```

**优化后：**
```python
# 先提取所有记录
records = [extract_record(msg, ...) for msg in messages]

# 【P2优化】批量插入（1次INSERT）
mysql_tool.batch_insert_on_duplicate(
    'analysis_news_detail_2026', 
    records, 
    key_fields=['importance_score', 'business_impact_score', ...]
)
```

## 性能对比

| 指标 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| MySQL插入次数 | 15-20次 | 1次 | **15-20x** |
| 网络往返 | 15-20次 | 1次 | **15-20x** |

## 2. 新闻分析MySQL插入慢优化方案


## 问题分析

### 当前流程

```
deepseek_ai分析完成
    ↓
① 标记原始表已分析（UPDATE）
② 插入分析结果JSON（INSERT）
    ↓
process_batch拆分入库
    ↓
逐条处理（15-20条）
    ↓
每条：extract_record → save_to_mysql → save_to_redis
    ↓
MySQL：单条INSERT ON DUPLICATE KEY UPDATE（15-20次）
Redis：pipeline批量（1次）
```

### 性能瓶颈

**瓶颈1：MySQL单条插入（最大问题）**
```python
# 当前：逐条插入，每条都执行SQL
for msg in messages:  # 15-20条
    record = extract_record(msg, ...)
    save_to_mysql(record)  # 每条执行1次INSERT
```
问题：
- 15-20条消息 = 15-20次INSERT
- 每次INSERT都是独立的数据库操作
- 网络往返 + 事务开销 = 慢

**瓶颈2：连接管理**
```python
def save_to_mysql(record):
    mysql_tool.update_data(sql)  # 每次新建连接
```
问题：
- 每条记录都新建数据库连接
- 连接建立/断开开销大

**瓶颈3：SQL拼接**
```python
sql = f"""INSERT INTO analysis_news_detail_2026 ...
    VALUES (...)
    ON DUPLICATE KEY UPDATE ..."""
```
问题：
- 单条SQL字符串拼接
- 无法利用批量插入优化

## 优化方案

### 方案A：批量插入（推荐）

**核心思路：** 多条记录合并为1条INSERT

```python
def save_to_mysql_batch(records: List[Dict]) -> bool:
    """批量插入多条记录"""
    if not records:
        return False
    
    try:
        # 构建批量VALUES
        values_list = []
        for record in records:
            def esc(val):
                if val is None:
                    return 'NULL'
                s = str(val).replace("'", "\\'").replace("\\", "\\\\")
                return f"'{s}'"
            
            publish_time_sql = esc(record['publish_time']) if record['publish_time'] else 'NULL'
            
            value_tuple = f"""({esc(record['content_hash'])}, {esc(record['source_table'])},
                {esc(record['title'])}, {esc(record['content'])},
                {publish_time_sql}, {esc(record['source'])},
                {record['importance_score']}, {record['business_impact_score']}, {record['composite_score']},
                {esc(record['news_size'])}, {esc(record['news_type'])},
                {esc(record['sectors'])}, {esc(record['concepts'])},
                {esc(record['leading_stocks'])}, {esc(record['sector_details'])},
                {esc(record['deep_analysis'])},
                {esc(record['analysis_version'])}, NOW())"""
            values_list.append(value_tuple)
        
        # 批量INSERT
        values_str = ',\n'.join(values_list)
        sql = f"""INSERT INTO analysis_news_detail_2026 
            (content_hash, source_table, title, content, publish_time, source,
             importance_score, business_impact_score, composite_score,
             news_size, news_type, sectors, concepts, leading_stocks, sector_details,
             deep_analysis, analysis_time, analysis_version)
            VALUES {values_str}
            ON DUPLICATE KEY UPDATE
                importance_score = VALUES(importance_score),
                business_impact_score = VALUES(business_impact_score),
                composite_score = VALUES(composite_score),
                news_size = VALUES(news_size),
                news_type = VALUES(news_type),
                sectors = VALUES(sectors),
                concepts = VALUES(concepts),
                leading_stocks = VALUES(leading_stocks),
                sector_details = VALUES(sector_details),
                deep_analysis = VALUES(deep_analysis),
                analysis_time = VALUES(analysis_time),
                analysis_version = VALUES(analysis_version)"""
        
        mysql_tool.update_data(sql)
        return True
    except Exception as e:
        logger.error(f"批量MySQL写入失败: {e}")
        return False
```

**修改process_batch：**
```python
def process_batch(json_data: str, source_table: str, version: str) -> Dict[str, int]:
    # ... 解析JSON ...
    
    records = []
    for msg in messages:
        record = extract_record(msg, source_table, version)
        if record:
            records.append(record)
    
    # 【优化】批量插入MySQL
    if records:
        if save_to_mysql_batch(records):  # 1次批量插入
            stats['mysql_ok'] = len(records)
        else:
            stats['failed'] = len(records)
    
    # Redis保持逐条（已有pipeline优化）
    for record in records:
        if save_to_redis(record):
            stats['redis_ok'] += 1
```

**预期性能提升：**
- 当前：15-20次INSERT = 15-20次网络往返
- 优化：1次批量INSERT = 1次网络往返
- 提升：15-20倍

### 方案B：连接池复用

**问题：** `update_data`每次新建连接

**优化：** 使用SQLAlchemy连接池
```python
# 已有engine，直接使用
with engine.begin() as conn:
    conn.execute(text(sql))
```

### 方案C：异步写入

**思路：** MySQL和Redis并行执行
```python
import asyncio

async def save_async(record):
    mysql_task = asyncio.create_task(save_to_mysql_async(record))
    redis_task = asyncio.create_task(save_to_redis_async(record))
    await asyncio.gather(mysql_task, redis_task)
```

## 推荐方案

**方案A（批量插入）+ 方案B（连接池）**

理由：
1. 批量插入是最大瓶颈，优化效果最明显
2. 连接池复用减少连接建立开销
3. 改动范围小，风险可控

## 二、方案A: 实时拦截验证

### 2.1 流程图

```
DeepSeek返回JSON
    ↓
[实时验证] ← 新增步骤
    ↓
    ├─ 验证通过 → 正常入库 → 写Redis缓存
    └─ 验证失败 → 不入库 → 记录日志 → 标记源表 → 后续重跑
```

### 2.2 验证规则

| 字段 | 理论区间 | 验证规则 | 处理方式 |
|------|----------|----------|----------|
| 重要程度评分 | 0-15 | `0 <= score <= 15` | 拦截不入库 |
| 业务影响维度评分 | -20 ~ +20 | `-20 <= score <= 20` | 拦截不入库 |
| 综合评分 | 计算值 | `composite = importance * 4 + biz_impact` | 强制重算 |
| 消息类型 | 枚举值 | `['利好', '利空', '中性']` | 拦截不入库 |
| 消息大小 | 计算值 | 根据综合评分映射 | 强制重算 |

### 2.3 修改范围

| 文件 | 修改内容 |
|------|----------|
| `news_result_processor.py` | 新增 `validate_news_record()` 函数 |
| `news_result_processor.py` | 修改 `extract_record()` 调用验证 |
| `news_result_processor.py` | 修改 `process()` 处理验证失败 |

### 2.4 优点

- 异常数据不污染数据库
- 问题发现及时，可立即重跑
- 数据质量有保障

### 2.5 缺点

- 修改核心处理流程，有风险
- 验证规则调整需重启服务
- 极端情况下可能误杀正常数据

## 一、问题背景

**案例**: "经济日报：用好我国的词元优势"
- 重要程度分理论区间: 0-15
- 实际结果: 45 (超出区间)

**根因分析**:
- DeepSeek AI 返回的评分数据可能存在异常
- 当前代码虽有 `max(-128, min(127, importance))` 等截断处理，但仅做数据截断，未标记异常数据
- 异常数据直接入库，导致后续分析偏差

---

## 二、验证规则设计

### 2.1 字段验证规则

| 字段 | 理论区间 | 验证规则 | 异常处理 |
|------|----------|----------|----------|
| `重要程度评分` | 0-15 | `0 <= score <= 15` | 标记异常，不入库 |
| `业务影响维度评分` | -20 ~ +20 | `-20 <= score <= 20` | 标记异常，不入库 |
| `综合评分` | 计算值 | `composite = importance * 4 + biz_impact` | 强制重算，不采信AI返回值 |
| `消息类型` | 枚举值 | `['利好', '利空', '中性']` | 标记异常，不入库 |
| `消息大小` | 计算值 | 根据综合评分映射 | 强制重算，不采信AI返回值 |

### 2.2 综合评分计算

```python
# 强制按公式计算，不采信AI返回的综合评分
composite = importance * 4 + biz_impact

# 消息大小映射（根据综合评分）
def _map_news_size(composite_score: int) -> str:
    if composite_score >= 50: return '重大'
    if composite_score >= 30: return '大'
    if composite_score >= 10: return '中'
    return '小'
```

## 三、验证流程

### 3.1 数据流

```
DeepSeek返回JSON
    ↓
[数据验证] ← 新增步骤
    ↓
    ├─ 验证通过 → 正常入库
    └─ 验证失败 → 标记异常 → 不入库 → 记录日志 → 后续重跑
```

### 3.2 验证函数设计

```python
def validate_news_record(msg: dict) -> tuple[bool, str, dict]:
    """
    验证新闻分析数据
    
    Args:
        msg: AI分析结果中的单条消息字典
        
    Returns:
        (is_valid: bool, error_msg: str, corrected_data: dict)
        - is_valid: 是否通过验证
        - error_msg: 错误描述（验证失败时）
        - corrected_data: 修正后的数据（验证通过时）
    """
    errors = []
    corrected = msg.copy()
    
    # 1. 验证重要程度评分
    importance = _safe_int(msg.get('重要程度评分', 0))
    if not (0 <= importance <= 15):
        errors.append(f"重要程度评分{importance}超出区间[0,15]")
    
    # 2. 验证业务影响维度评分
    biz_impact = _safe_int(msg.get('业务影响维度评分', 0))
    if not (-20 <= biz_impact <= 20):
        errors.append(f"业务影响维度评分{biz_impact}超出区间[-20,20]")
    
    # 3. 强制重算综合评分（不采信AI返回值）
    composite = importance * 4 + biz_impact
    corrected['综合评分'] = composite
    
    # 4. 强制重算消息大小
    corrected['消息大小'] = _map_news_size(composite)
    
    # 5. 验证消息类型
    news_type = msg.get('消息类型', '中性')
    if news_type not in ['利好', '利空', '中性']:
        errors.append(f"消息类型'{news_type}'不在允许值['利好','利空','中性']中")
    
    # 6. 验证必填字段
    content_hash = _safe_str(msg.get('消息id', ''))
    if not content_hash:
        errors.append("消息id为空")
    
    if errors:
        return False, "; ".join(errors), {}
    
    return True, "", corrected
```

## 一、问题描述

### 问题 1：点击热门板块后数据未按评分倒序排序

**现象**: 用户点击热点板块列表中的某个板块后，展示的新闻/领域数据没有按照评分从高到低排序。

**根本原因**:
- `filterBySector()` 函数调用 API 时没有传递 `sort` 参数
- 后端默认按 `time`（时间）排序
- 用户期望看到该板块下评分最高的事件

### 问题 2：点击板块后自动刷新未保持筛选条件

**现象**: 点击板块筛选后，30秒自动刷新时会重置为默认列表，丢失板块筛选条件。

**根本原因**:
- `setInterval` 只调用 `loadNews()`，使用全局默认变量
- 没有记录当前正在查看的板块筛选状态
- 刷新时未携带板块参数

## 8. 新闻分析性能优化

## 一、问题分析

### 1.1 慢查询原因

#### `/api/news/list`

#### `/api/news/stats`
1. **时间范围计算**: 每次调用都重新计算交易日时间范围
2. **聚合查询**: 使用多个 `SUM(CASE WHEN...)`，数据量大时慢

## 9. 新闻分析时间范围设计


**版本**: v1.0  
**日期**: 2026-04-15  
**作者**: OpenClaw  

---

## 1. 需求概述

### 1.1 背景
新闻分析当前按自然日展示数据，但用户期望按**交易日时间范围**展示，确保数据连续性。

### 1.2 目标
- 当前时间模式：展示上一个交易日收盘到当前时间的新闻
- 日期选择模式：展示所选日期上一个交易日收盘到该日期24点的新闻
- 短时间补偿：时间范围低于6小时时，扩展到上上个交易日

---

## 2. 时间范围定义

### 2.1 当前时间模式（无日期选择）

```
范围：上一个交易日 15:00 → 当前时间

例外情况（时间范围 < 6小时）：
范围：上上个交易日 15:00 → 当前时间
```

**示例**：
| 当前时间 | 上个交易日 | 时间范围 | 是否扩展 |
|---------|-----------|---------|---------|
| 4月15日 10:00 | 4月14日 | 19小时 | 否 |
| 4月15日 16:00 | 4月14日 | 25小时 | 否 |
| 4月15日 20:00（数据少）| 4月14日 | 5小时 | 是 → 4月13日15:00 |

### 2.2 日期选择器模式

```
范围：所选日期的上一个交易日 15:00 → 所选日期 23:59:59
```

**示例**：
| 选择日期 | 上个交易日 | 时间范围 |
|---------|-----------|---------|
| 4月15日（周二）| 4月14日（周一）| 4/14 15:00 ~ 4/15 24:00 |
| 4月14日（周一）| 4月11日（周五）| 4/11 15:00 ~ 4/14 24:00 |
| 4月12日（周六）| 4月11日（周五）| 4/11 15:00 ~ 4/12 24:00 |

---

## 3. 核心算法

### 3.1 时间范围计算

```python
def get_news_time_range(target_date=None, target_time=None):
    """
    计算新闻分析的时间范围
    
    Args:
        target_date: 选择的日期（None表示当前时间模式）
        target_time: 当前时间（仅当前时间模式使用）
    
    Returns:
        dict: {
            'start_time': datetime,      # 范围开始
            'end_time': datetime,        # 范围结束
            'display_date': date,        # 显示日期
            'trading_day': date,         # 参考交易日
            'is_extended': bool,         # 是否已扩展
            'hours_span': float          # 时间跨度（小时）
        }
    """
    trading_days = get_trading_days_from_jyrl()
```

## 1. 需求概述

### 1.1 背景
新闻分析当前按自然日展示数据，但用户期望按**交易日时间范围**展示，确保数据连续性。

### 1.2 目标
- 当前时间模式：展示上一个交易日收盘到当前时间的新闻
- 日期选择模式：展示所选日期上一个交易日收盘到该日期24点的新闻
- 短时间补偿：时间范围低于6小时时，扩展到上上个交易日

---

## 2. 时间范围定义

### 2.1 当前时间模式（无日期选择）

```
范围：上一个交易日 15:00 → 当前时间

例外情况（时间范围 < 6小时）：
范围：上上个交易日 15:00 → 当前时间
```

**示例**：
| 当前时间 | 上个交易日 | 时间范围 | 是否扩展 |
|---------|-----------|---------|---------|
| 4月15日 10:00 | 4月14日 | 19小时 | 否 |
| 4月15日 16:00 | 4月14日 | 25小时 | 否 |
| 4月15日 20:00（数据少）| 4月14日 | 5小时 | 是 → 4月13日15:00 |

### 2.2 日期选择器模式

```
范围：所选日期的上一个交易日 15:00 → 所选日期 23:59:59
```

**示例**：
| 选择日期 | 上个交易日 | 时间范围 |
|---------|-----------|---------|
| 4月15日（周二）| 4月14日（周一）| 4/14 15:00 ~ 4/15 24:00 |
| 4月14日（周一）| 4月11日（周五）| 4/11 15:00 ~ 4/14 24:00 |
| 4月12日（周六）| 4月11日（周五）| 4/11 15:00 ~ 4/12 24:00 |

```python
            'hours_span': float          # 时间跨度（小时）
        }

        today = now.date()
```

```sql

  -- 主键与关联
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '自增主键',
  `content_hash` VARCHAR(64) NOT NULL COMMENT '新闻内容hash（关联news_cls2026.内容hash）',

  `content` TEXT COMMENT '新闻正文',
  `publish_time` DATETIME NOT NULL COMMENT '发布时间',
  `source` VARCHAR(64) DEFAULT '' COMMENT '新闻来源（财联社/第一财经等）',
  
  -- AI 评分字段（全部独立列）
  `importance_score` TINYINT NOT NULL DEFAULT 0 COMMENT '重要程度评分（0-15）',
  `business_impact_score` SMALLINT NOT NULL DEFAULT 0 COMMENT '业务影响维度评分（-60至60）',
  `composite_score` SMALLINT NOT NULL DEFAULT 0 COMMENT '综合评分（重要程度×4+业务影响）',
  
  -- AI 分类字段
  `news_size` ENUM('重大','大','中','小') NOT NULL DEFAULT '小' COMMENT '消息大小',
  `news_type` ENUM('利好','利空','中性') NOT NULL DEFAULT '中性' COMMENT '消息类型',
  
  -- 关联板块/概念（JSON 数组存储，支持 MySQL 5.7+ JSON 函数查询）
  `sectors` JSON COMMENT '涉及板块（JSON数组）',
  `concepts` JSON COMMENT '涉及概念（JSON数组）',
  `leading_stocks` JSON COMMENT '龙头个股代码（JSON数组）',
  
  -- 板块详情（完整的板块分析明细）
  `sector_details` JSON COMMENT '板块详情（含个股关联原因）',
  
  -- 元数据
  `analysis_version` VARCHAR(32) DEFAULT '' COMMENT 'AI分析语料版本',
  `analysis_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT 'AI分析完成时间',
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '记录创建时间',
  
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_content_hash` (`content_hash`),
  KEY `idx_publish_time` (`publish_time`),
  KEY `idx_composite_score` (`composite_score`),
  KEY `idx_news_type` (`news_type`),
  KEY `idx_news_size` (`news_size`),
  KEY `idx_source_table` (`source_table`),
  KEY `idx_analysis_time` (`analysis_time`),
  -- 复合索引：前端常用查询（按时间倒序 + 类型筛选）
  KEY `idx_time_type` (`publish_time`, `news_type`),
  KEY `idx_time_score` (`publish_time`, `composite_score`),
  -- 全文索引：支持标题+内容搜索
  FULLTEXT KEY `ft_title_content` (`title`, `content`) WITH PARSER ngram
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='新闻AI分析结果明细表（一条新闻一条记录）';
```

### 3.2 设计说明

| 设计决策 | 原因 |
|---------|------|
| `content_hash` 唯一索引 | 防止同一条新闻重复入库，也用于关联原始表 |
| 冗余 `title`/`content`/`publish_time` | 前端展示时避免 JOIN 原始新闻表，单表即可完成全部查询 |
| 评分字段用数值类型 | 支持 `ORDER BY`、范围查询、聚合统计 |
| `news_size`/`news_type` 用 ENUM | 固定字典值，存储空间小，查询效率高 |
| `sectors`/`concepts` 用 JSON | 数组长度不固定，JSON 类型支持 `JSON_CONTAINS` 查询 |
| `sector_details` 用 JSON | 板块详情结构复杂，保留完整结构，前端按需解析 |
| 复合索引 `idx_time_type` | 覆盖「按时间倒序 + 按类型筛选」的最高频查询 |
| 全文索引 `ft_title_content` | 支持标题+内容的中文全文搜索（ngram 解析器） |

## 四、Redis 缓存设计

### 4.1 缓存架构

```
[AI 分析完成] → [拆分 JSON] → [写入 MySQL] + [写入 Redis]
                                                  ↓
                              [前端新闻中心] ← [读取 Redis]
                                                  ↓ (缓存未命中)
                                              [回源 MySQL]
```

### 4.2 Redis Key 设计

| Key | 类型 | 说明 | TTL |
|-----|------|------|-----|
| `news:detail:{content_hash}` | Hash | 单条新闻完整数据 | 48h |
| `news:timeline:{date}` | Sorted Set | 当日新闻时间线（score=时间戳） | 72h |
| `news:type:{date}:{type}` | Sorted Set | 按类型分组时间线（利好/利空/中性） | 72h |
| `news:top:{date}` | Sorted Set | 当日高分新闻排行（score=综合评分） | 72h |
| `news:sector:{date}:{sector}` | Set | 当日涉及某板块的新闻 hash 集合 | 72h |
| `news:latest` | List | 最新 N 条新闻的 content_hash（FIFO） | 永久 |
| `news:stats:{date}` | Hash | 当日统计（总数/利好数/利空数/重大数） | 72h |

```sql
  KEY `idx_news_size` (`news_size`),
  KEY `idx_source_table` (`source_table`),
  KEY `idx_analysis_time` (`analysis_time`),
  -- 复合索引：前端常用查询（按时间倒序 + 类型筛选）
  KEY `idx_time_type` (`publish_time`, `news_type`),
  KEY `idx_time_score` (`publish_time`, `composite_score`),
  -- 全文索引：支持标题+内容搜索
  FULLTEXT KEY `ft_title_content` (`title`, `content`) WITH PARSER ngram
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='新闻AI分析结果明细表（一条新闻一条记录）';
```

### 3.2 设计说明

| 设计决策 | 原因 |
|---------|------|
| `content_hash` 唯一索引 | 防止同一条新闻重复入库，也用于关联原始表 |
| 冗余 `title`/`content`/`publish_time` | 前端展示时避免 JOIN 原始新闻表，单表即可完成全部查询 |
| 评分字段用数值类型 | 支持 `ORDER BY`、范围查询、聚合统计 |
| `news_size`/`news_type` 用 ENUM | 固定字典值，存储空间小，查询效率高 |
| `sectors`/`concepts` 用 JSON | 数组长度不固定，JSON 类型支持 `JSON_CONTAINS` 查询 |
| `sector_details` 用 JSON | 板块详情结构复杂，保留完整结构，前端按需解析 |
| 复合索引 `idx_time_type` | 覆盖「按时间倒序 + 按类型筛选」的最高频查询 |
| 全文索引 `ft_title_content` | 支持标题+内容的中文全文搜索（ngram 解析器） |

## 四、Redis 缓存设计

### 4.1 缓存架构

```
[AI 分析完成] → [拆分 JSON] → [写入 MySQL] + [写入 Redis]
                                                  ↓
                              [前端新闻中心] ← [读取 Redis]
                                                  ↓ (缓存未命中)
                                              [回源 MySQL]
```

### 4.2 Redis Key 设计

| Key | 类型 | 说明 | TTL |
|-----|------|------|-----|
| `news:detail:{content_hash}` | Hash | 单条新闻完整数据 | 48h |
| `news:timeline:{date}` | Sorted Set | 当日新闻时间线（score=时间戳） | 72h |
| `news:type:{date}:{type}` | Sorted Set | 按类型分组时间线（利好/利空/中性） | 72h |
| `news:top:{date}` | Sorted Set | 当日高分新闻排行（score=综合评分） | 72h |
| `news:sector:{date}:{sector}` | Set | 当日涉及某板块的新闻 hash 集合 | 72h |
| `news:latest` | List | 最新 N 条新闻的 content_hash（FIFO） | 永久 |
| `news:stats:{date}` | Hash | 当日统计（总数/利好数/利空数/重大数） | 72h |

## 九、性能优化

### 9.1 读取性能对比

| 场景 | 改造前 | 改造后 |
|------|--------|--------|
| 获取最新 20 条新闻 | 全表扫描 22,300 条大 JSON → **~2-5s** | Redis ZREVRANGE + Pipeline HGETALL → **~5-15ms** |
| 按类型筛选 | 全表扫描 + 应用层过滤 → **~3-8s** | Redis ZREVRANGE(type) → **~5-10ms** |
| 按评分筛选 | 不支持 | Redis ZREVRANGE(top) / MySQL 索引 → **~5-20ms** |
| 全文搜索 | 不支持 | MySQL 全文索引 → **~50-200ms** |
| 单条详情 | 不支持直接查询 | Redis HGETALL → **~1-3ms** |

### 9.2 索引优化

```sql

KEY idx_news_type (news_type)
KEY idx_news_size (news_size)
KEY idx_source_table (source_table)
KEY idx_analysis_time (analysis_time)
KEY idx_time_type (publish_time, news_type)
KEY idx_time_score (publish_time, composite_score)
FULLTEXT KEY ft_title_content (title, content) WITH PARSER ngram
```
