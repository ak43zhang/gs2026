# 统一条件评估引擎改造方案

## 1. 背景与问题

### 1.1 当前现状

系统中存在三个独立的条件评估逻辑，各自实现方式不同，导致：
- 修改回测逻辑时，选债和回填不会同步更新
- 新功能（条件组、字段间比较）只在回测中实现，选债/回填不支持
- `conditions_json` 格式兼容问题导致实时选债静默失败

| 系统 | 文件位置 | 评估方式 | 支持的功能 |
|------|---------|---------|-----------|
| 量化回测 | `services/backtest_bond.py` | `_build_sql_where` → SQL WHERE | 条件组、字段间比较、JSON字段 |
| 量化选债(实时) | `services/quant_screen_core.py` | `apply_scheme_conditions` → pandas | 仅平铺条件列表 |
| 量化回填 | `test/backfill_today.py` | 调用 `apply_scheme_conditions` | 同上 |

### 1.2 核心问题

1. **格式不兼容**：活跃方案 `conditions_json` 存储为 `{"conditions": [...], "groups": [...]}`（新版dict格式），但 `apply_scheme_conditions` 只支持旧版 `[...]`（flat array），导致实时选债和回填静默崩溃，返回空结果。

2. **逻辑不同步**：回测中新增的"条件组"和"字段间比较"功能，在选债和回填中完全不支持。

3. **维护成本高**：三处独立实现，每次修改需要同步三个文件，容易遗漏。

---

## 2. 设计目标

**一个核心函数，三处调用。修改条件评估逻辑只需改一处，量化回测、量化选债、量化回填同步生效。**

- 统一条件评估引擎放在 `quant_screen_core.py`
- 回测从 SQL WHERE 改为 pandas 评估（与选债/回填完全一致）
- 支持所有已实现的功能：条件组、字段间比较、between、JSON字段展开

---

## 3. 目标架构

```
quant_screen_core.py（唯一条件评估核心）
│
├── normalize_conditions(raw)
│   输入: 旧版list / 新版dict / 任意格式
│   输出: {"conditions": [...], "groups": [...]}
│
├── expand_ext_indicators(df) → df
│   展开ext_indicators JSON列为独立列（统一处理）
│
├── evaluate_conditions(df, conditions_config) → pd.Series(bool)
│   【核心函数】统一条件评估，返回布尔mask
│   ├── _eval_condition_list(df, conditions) → mask (AND)
│   └── _eval_single_condition(df, c) → mask
│       ├── 普通比较: field op value
│       ├── 字段间比较: field op compare_field
│       └── between: field >= val AND field <= val2
│
└── apply_scheme_conditions(df, schemes) → (matches, stats)
    多方案批量评估入口（实时选债 + 回填共用）
    内部调用 normalize_conditions + evaluate_conditions
```

## 4. 核心函数设计

### 4.1 normalize_conditions(raw) → dict

**作用**：标准化条件格式，兼容所有历史版本。

**输入**：
- 旧版格式: `[{field, op, value}, ...]`
- 新版格式: `{"conditions": [...], "groups": [...]}`
- 空值: `None`, `[]`, `{}`

**输出**：
```python
{
    "conditions": [...],  # 基础条件列表
    "groups": [...]       # 条件组列表
}
```

### 4.2 expand_ext_indicators(df) → df

**作用**：将 `ext_indicators` JSON 列展开为独立的 DataFrame 列。

**逻辑**：
1. 检查 `ext_indicators` 列是否存在
2. 解析 JSON 字符串为字典
3. 使用 `pd.json_normalize` 展开为独立列
4. 合并到原 DataFrame（不覆盖已有列）

**展开后的列**：
- `weighted_slope_2m`
- `change_1m_pct`
- `price_acceleration`
- `mkt_weighted_slope_2m`
- `mkt_change_1m_pct`
- `mkt_price_acceleration`

### 4.3 evaluate_conditions(df, conditions_config) → pd.Series

**作用**：统一的条件评估引擎，返回布尔 mask。

**参数**：
- `df`: 数据 DataFrame（需已展开 ext_indicators）
- `conditions_config`: dict 或 list（自动调用 normalize_conditions）

**返回**：`pd.Series(bool)`，True 表示该行满足所有条件。

**评估逻辑**：
```
最终mask = 基础条件(AND) AND 条件组A AND 条件组B ...

条件组（mode='and'）: 组内条件 AND
条件组（mode='or' + subgroups）: 子条件组间 OR（子组内 AND）
```

### 4.4 _eval_single_condition(df, c) → pd.Series

**作用**：评估单个条件。

**支持的操作符**：`>`, `>=`, `<`, `<=`, `=`, `!=`, `between`

**支持的模式**：
- 普通比较: `field > 0.5`
- 字段间比较: `slope_short > slope_long`（`is_field_compare=True`）
- 区间: `field BETWEEN val1 AND val2`

**字段不存在处理**：返回全 True（跳过该条件，不影响其他条件）

### 4.5 apply_scheme_conditions(df, schemes) → (matches, stats)

**作用**：多方案批量评估入口（实时选债 + 回填共用）。

**逻辑**：
1. 遍历每个方案
2. 对每个方案调用 `normalize_conditions` + `evaluate_conditions`
3. 收集命中结果，按涨幅排序
4. 返回 (matches列表, stats字典)

## 5. 三处调用方式改造

### 5.1 量化回测（backtest_bond.py）

**改造前**：
```python
# SQL方式：条件嵌入WHERE子句
where_clause, params = _build_sql_where(conditions)
signal_sql = f"SELECT ... FROM {table} WHERE {where_clause} AND time >= :start AND time <= :end"
df_signals = pd.read_sql(signal_sql, engine, params=params)
```

**改造后**：
```python
from gs2026.dashboard2.services.quant_screen_core import (
    normalize_conditions, evaluate_conditions, expand_ext_indicators
)

# 阶段1: 加载数据（只按时间范围过滤，不含条件WHERE）
load_sql = text(f"""
    SELECT bond_code, bond_name, time, price, change_pct, amount,
           amount_rank, min1_change_pct, min1_amount, min1_amount_rank,
           slope_short, slope_long, peak_vol_bias, high_distance,
           mkt_slope_short, mkt_slope_long, mkt_peak_vol_bias, mkt_high_distance,
           ext_indicators
    FROM {table}
    WHERE time >= :time_start AND time <= :time_end
""")
df_all = pd.read_sql(load_sql, engine, params={'time_start': time_start, 'time_end': time_end})

# 阶段2: 展开 ext_indicators JSON
df_all = expand_ext_indicators(df_all)

# 阶段3: 统一条件评估（一次性过滤全部数据）
conditions_config = {'conditions': conditions, 'groups': groups}
mask = evaluate_conditions(df_all, conditions_config)
df_signals = df_all[mask]

# 阶段4: 后续去重 + 盈亏计算（保持不变）
```

**关键点**：
- `_build_sql_where` 移除（不再需要）
- 字段校验保留（`VALID_FIELDS` 检查）
- 后续的去重、盈亏计算逻辑不变

### 5.2 量化选债-实时（monitor_bond.py）

**改造前**：
```python
# run_quant_screen_on_tick 中手动展开 ext_indicators
if 'ext_indicators' in df_now.columns:
    ext_parsed = df_now['ext_indicators'].apply(...)
    ext_expanded = pd.json_normalize(ext_parsed)
    for col in ext_expanded.columns:
        if col not in df_now.columns:
            df_now[col] = ext_expanded[col].values

matches, stats = apply_scheme_conditions(df_now, _qs_scheme_cache)
```

**改造后**：
```python
from gs2026.dashboard2.services.quant_screen_core import (
    apply_scheme_conditions, expand_ext_indicators
)

# 使用统一的展开函数
df_now = expand_ext_indicators(df_now)

# apply_scheme_conditions 内部已处理格式兼容
matches, stats = apply_scheme_conditions(df_now, _qs_scheme_cache)
```

**改动点**：
- 移除手动 JSON 展开代码（6行），改用 `expand_ext_indicators`
- `_load_qs_schemes` 无需修改（`normalize_conditions` 在 `apply_scheme_conditions` 内部处理）

### 5.3 量化回填（test/backfill_today.py）

**改造前**：
```python
from gs2026.dashboard2.services.quant_screen_core import apply_scheme_conditions

for tick_time in tick_times:
    df = pd.read_sql(...)
    matches, stats = apply_scheme_conditions(df, schemes)  # 格式不兼容会崩溃
```

**改造后**：
```python
from gs2026.dashboard2.services.quant_screen_core import (
    apply_scheme_conditions, expand_ext_indicators
)

for tick_time in tick_times:
    df = pd.read_sql(...)
    df = expand_ext_indicators(df)  # 新增：展开JSON
    matches, stats = apply_scheme_conditions(df, schemes)  # 格式自动兼容
```

**改动点**：
- 添加 `expand_ext_indicators` 调用
- `apply_scheme_conditions` 内部自动处理格式兼容

## 6. 性能评估

### 6.1 回测性能对比

| 指标 | 改造前(SQL WHERE) | 改造后(pandas) |
|------|------------------|---------------|
| 数据加载 | 1次SQL(含条件) | 1次SQL(仅时间范围) |
| 数据量 | 仅匹配行(少量) | 全部行(~200万/天) |
| 条件评估 | MySQL引擎 | pandas向量化 |
| 网络开销 | 条件参数传输 | 无(本地计算) |
| 总耗时(单天) | ~2-3秒 | ~3-4秒 |
| 维护成本 | 3份独立逻辑 | **1份统一逻辑** |

### 6.2 内存评估

- 单天数据：~300债券 × ~7000tick × 20列 ≈ **150-200MB**
- 系统可用内存：16GB+，完全可接受
- 如需优化：可按小时分批加载

### 6.3 结论

性能差异在可接受范围内（+1秒），换来的是：
- 逻辑完全一致，无同步问题
- 维护成本降低（改一处生效三处）
- 新功能自动对三个系统生效
