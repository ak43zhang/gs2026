# 量化选债收益计算流程分析与改造方案

## 一、当前代码流程分析

### 1.1 命中记录生成（每分钟）
**位置**: `monitor_bond.py` ~1440行

```
每个tick:
  └─ 量化筛选条件匹配 → matches
  └─ 过滤：同分钟内同一债券只保存首次（_qs_seen_this_minute去重）
  └─ save_quant_screen_hits() 写入数据库
        字段: bond_code, tick_time, entry_price, tp_pct, sl_pct, max_hold_time
        状态: exit_reason = NULL (未平仓)
```

### 1.2 收益计算（当前实现）
**位置**: `_track_pending_exits()` ~1530-1615行

```
每个tick:
  └─ 查询所有 exit_reason IS NULL 的记录 (未平仓)
  └─ 逐条检查:
        ├─ 止盈: current_price >= entry_price * (1 + tp_pct/100)
        ├─ 止损: current_price <= entry_price * (1 - sl_pct/100)  
        └─ 超时: current_seconds >= entry_seconds + max_hold*60
  └─ 触发任一条件:
        ├─ 计算 profit_pct = (exit_price - entry_price) / entry_price * 100
        ├─ UPDATE 数据库: exit_time, exit_price, profit_pct, exit_reason, hold_seconds
        └─ 标记为已平仓 (exit_reason = 'tp'/'sl'/'timeout')
  └─ 批量打印: "退出跟踪: N条信号已平仓"
```

### 1.3 当前流程的问题

| 问题 | 说明 |
|------|------|
| **无实时收益打印** | 已平仓的记录只在平仓时打印一次，未平仓的不显示当前浮动收益 |
| **无"已有收益直接打印"逻辑** | 每个tick都重新计算所有未平仓记录，没有区分"已结算"和"未结算" |
| **计算逻辑不统一** | 止盈/止损/超时都统一用 exit_price=current_price，但用户期望的是触发时用触发价计算 |
| **缺少实时浮动收益** | 未触发止盈止损超时的记录，没有展示当前浮动盈亏 |

## 二、用户期望流程

### 2.1 核心要求

```
每个tick:
  ├─ 查询所有命中记录 (包括已平仓和未平仓)
  ├─ 分类处理:
  │   ├─ 【已有收益】exit_reason IS NOT NULL → 直接打印已有收益，跳过计算
  │   └─ 【未有收益】exit_reason IS NULL → 进行判断计算
  │       ├─ 止盈触发: current_price >= tp_price
  │       │   └─ 收益 = (tp_price - entry_price) / entry_price * 100
  │       ├─ 止损触发: current_price <= sl_price
  │       │   └─ 收益 = (sl_price - entry_price) / entry_price * 100
  │       ├─ 超时触发: time >= entry_time + max_hold
  │       │   └─ 收益 = (current_price - entry_price) / entry_price * 100
  │       └─ 均未触发: 实时浮动收益 = (current_price - entry_price) / entry_price * 100
  │           └─ 打印浮动收益，不标记平仓
  └─ 打印汇总: 已结算N条，未结算M条，当前浮动收益...
```

### 2.2 关键差异点

| 维度 | 当前实现 | 用户期望 |
|------|---------|---------|
| **处理范围** | 只处理未平仓记录 | 处理全部记录，已平仓的直接打印 |
| **收益计算时机** | 只在平仓时计算 | 每个tick都计算（浮动收益实时显示） |
| **触发价格** | 统一用 current_price | 止盈止损用触发价，超时用 current_price |
| **结算标记** | 触发即UPDATE标记exit_reason | 同上，但已结算的不再重复计算 |
| **打印频率** | 只在平仓时批量打印 | 每个tick都打印（已结算+未结算） |

## 三、改造方案

### 3.1 方案A：最小改动（推荐）

**修改范围**: 仅修改 `_track_pending_exits()` 函数

**改动点**:
1. **查询范围扩展**: 从 `exit_reason IS NULL` 改为 `无筛选`（查询全部命中记录）
2. **分类处理**: 新增 `if row.exit_reason: print_and_skip()` 逻辑
3. **收益计算细化**:
   - 止盈触发: `profit = (tp_price - entry) / entry`
   - 止损触发: `profit = (sl_price - entry) / entry`
   - 超时触发: `profit = (current - entry) / entry`
   - 未触发: `floating_profit = (current - entry) / entry`，打印但不UPDATE
4. **打印增强**: 每个tick输出两类信息
   - 已结算: "[结算] code=XXX profit=X% reason=tp"
   - 未结算: "[浮动] code=XXX profit=X% 持仓=N分钟"

### 3.2 方案B：完整重构（更彻底）

**新增独立模块**: `profit_tracker.py`

**功能**:
- 维护内存中的命中记录缓存
- 每个tick只计算"变化"（价格变动或状态变更）
- 支持自定义打印格式
- 数据库异步写入（不阻塞tick处理）

**优点**: 更清晰，性能更好
**缺点**: 改动大，需要更多测试

## 四、实施建议

### 推荐：方案A（最小改动）

理由:
1. 改动范围小（一个函数 ~80行）
2. 风险低，不引入新模块
3. 符合用户"审核通过再实施"的要求

### 具体修改步骤

1. **备份** `monitor_bond.py`
2. **修改** `_track_pending_exits()` 函数:
   - 查询全部记录（去掉 `exit_reason IS NULL` 条件）
   - 循环内增加分支判断
   - 已结算：直接打印，continue
   - 未结算：判断触发条件，计算收益，UPDATE
   - 均未触发：计算浮动收益，打印，不UPDATE
3. **测试** 验证逻辑正确
