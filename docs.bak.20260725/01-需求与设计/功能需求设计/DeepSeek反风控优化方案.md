## 二、对照风控清单发现的风险点

### 🔴 高风险（可能导致封禁）

#### 1. 无请求间隔控制（风控规则：三.2）

**问题**：`deepseek_ai()` 函数的 for 循环中，连续对同一账号发送多条query，无间隔控制。

```python
# 当前代码（event_driven版）
for i in query_list:
    analysis: str = deepseek_analysis(query, _headless)  # 连续调用，无间隔
```

**风控触发**：「无人类停顿，每秒连续发送对话，无自然操作间隔」→ 临时冻结7天起步

**建议**：每次AI调用后增加 30-90秒 随机间隔

---

#### 2. 无指数退避机制（风控规则：三.2）

**问题**：`deepseek_analysis()` 调用失败时直接返回 `{}`，无重试退避。

```python
except Exception as e:
    logger.error(f"[DeepSeek] 分析异常（已捕获，返回空结果）: {e}")
    return result  # 直接返回，外层可能立即重试
```

**风控触发**：「无退避机制高频请求，持续触发429」→ API永久封禁

**建议**：失败后指数退避（30s → 60s → 120s → 240s），连续失败3次后休眠30分钟

---

#### 3. 无账号冷却机制（风控规则：三.2、三.4）

**问题**：`DistributedAccountPool` 释放账号后，下次可能立即再次分配同一账号。

**风控触发**：「1小时超50次连续请求」→ 功能限流/临时冻结

**建议**：账号使用后强制冷却 5-10 分钟才能再次分配

---

#### 4. 无封禁信号检测（风控规则：一）

**问题**：代码不检测页面是否出现「账号已被临时停用」「请完成验证」等封禁提示。

```python
# send_query() 只检测回复内容，不检测异常提示
```

**风控触发**：封禁后继续重试 → 加重处罚升级

**建议**：登录后和发送query后检测封禁/验证码关键词，触发时标记账号为frozen

---

### 🟡 中风险（可能触发限流）

#### 5. 凌晨高频调用无限制（风控规则：三.4）

**问题**：程序7×24运行，凌晨2-6点仍然高频请求。

**风控触发**：「凌晨2-6点持续高频率批量请求（风控重点扫描时段）」→ 限流/冻结

**建议**：凌晨2-6点自动降速或暂停

---

#### 6. 每次创建新会话（风控规则：三.1）

**问题**：每次调用都新建浏览器 → 登录 → 发送 → 关闭。频繁登录行为异常。

**风控触发**：「短时间频繁切换浏览器无痕/多账号切换」→ 设备指纹拉黑

**建议**：同一账号保持会话，发送多条query后再关闭（会话复用）

---

#### 7. 单次粘贴超长文本（风控规则：三.4）

**问题**：使用 `.fill()` 一次性填入整个prompt（可能数千字），无人工特征。

```python
page.get_by_placeholder("Message DeepSeek").fill(query)  # 一次性粘贴
```

**风控触发**：「一次性粘贴上万字长文本」「密码管理器自动填充」

**建议**：保持现有 `.fill()` 即可（这是"粘贴"行为，人类也会粘贴），但在粘贴前加一个随机的"选择全部→删除"动作模拟

---

### 🟢 低风险（已有防护，可微调）

#### 8. UserAgent 列表过少

**现状**：只有5个 UserAgent，长期使用会形成固定指纹模式。

**建议**：扩充到 15-20 个，包含 Edge、Firefox 等不同浏览器

---

#### 9. 直连模式IP固定

**现状**：PROXY_MODE="direct" 时始终使用相同IP。

**风控触发**：同一IP高频请求

**建议**：直连模式下也应控制单日总请求量（已通过 ai_call_counter 实现 ✅）

---

## 三、优化建议优先级排序

| 优先级 | 优化项 | 实施难度 | 效果 |
|--------|--------|---------|------|
| P0 | 请求间隔控制（30-90s随机） | 低 | 防止高频封禁 |
| P0 | 指数退避机制 | 低 | 防止失败后加速封禁 |
| P0 | 封禁信号检测 | 中 | 及时止损，保护账号 |
| P1 | 账号冷却机制 | 中 | 降低单账号使用密度 |
| P1 | 凌晨降速 | 低 | 避开重点扫描时段 |
| P2 | 会话复用（同账号多query） | 高 | 减少频繁登录 |
| P3 | UserAgent扩充 | 低 | 指纹多样性 |

## 四、推荐实施方案

### 方案A：最小改动（只改 `deepseek_analysis_event_driven.py`）

在 `deepseek_analysis()` 函数中增加：
1. 调用前随机间隔 30-90s
2. 失败后指数退避
3. 封禁关键词检测

**改动量**：~30行代码
**风险**：低（不改变整体架构）

### 方案B：中等改动（改 `session.py` + `event_driven.py`）

在方案A基础上：
4. `session.py` 中增加封禁检测（登录后/发送后）
5. 账号池增加冷却时间字段
6. 增加凌晨降速逻辑

**改动量**：~80行代码
**风险**：中（改动会话管理逻辑）

### 方案C：全面优化（重构会话模式）

在方案B基础上：
7. 会话复用（同一浏览器发送多条query）
8. UserAgent大幅扩充
9. 智能调度（根据错误率动态调整频率）

**改动量**：~200行代码
**风险**：高（架构变化大）

## 五、建议

**推荐先实施方案A**，这是投入产出比最高的优化：
- 改动最小
- 覆盖最高风险项（P0）
- 不改变现有架构
- 可以后续渐进增加方案B/C的内容
