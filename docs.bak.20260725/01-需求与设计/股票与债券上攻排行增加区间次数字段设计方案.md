## 一、需求背景

### 1.1 业务需求
债券T+0交易需要更精细的时间维度发现机会，需在股票和债券上攻排行中增加"区间次数"字段，用于分析近15分钟内哪些票比较活跃。

### 1.2 核心目标
- 实时反映15分钟固定区间内的上攻累计次数
- 支持按区间次数排序，快速发现当前活跃品种
- 不影响现有功能，历史数据兼容

---

## 二、方案概述

### 2.1 核心设计
- **区间定义**：15分钟固定窗口（09:30-09:45, 09:45-10:00...）
- **计算方式**：内存缓存为主，数据库兜底
- **字段名称**：`window_count`（区间次数）
- **展示名称**："区间次数"

### 2.2 技术架构
```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│  monitor_stock  │────▶│  内存缓存模块   │────▶│  数据库写入     │
│  monitor_bond   │     │  (高性能O(1))  │     │  (持久化)       │

                       │  (数据库重建)  │
```

## 三、详细设计

### 3.1 区间划分规则

| 当前时间范围 | 区间起始 | 统计范围示例 |
|-------------|---------|-------------|
| 09:30:00-09:44:59 | 09:30:00 | 09:30:05统计09:30:00-09:30:05(5秒) |
| 09:45:00-09:59:59 | 09:45:00 | 09:50:00统计09:45:00-09:50:00(5分钟) |
| 10:00:00-10:14:59 | 10:00:00 | 10:00:00重置为0，新区间开始 |

### 3.2 计算逻辑

```python
# 15分钟取整计算
def calculate_window_start(time_str: str) -> str:
    hh, mm, _ = time_str.split(':')
    hour, minute = int(hh), int(mm)
    window_start = (minute // 15) * 15
    return f"{hour:02d}:{window_start:02d}:00"

# 每次写入时：本区间内已出现次数 + 1
window_count = current_count + 1
```

### 3.3 内存缓存设计

**数据结构**：
```python
# key: (date, window_start, code)
# value: count
_window_count_cache: Dict[Tuple[str, str, str], int] = {}
```

**核心操作**：
- `get_window_count(code, date, time)`：获取并递增
- `_clear_old_window_cache(date, current_window)`：跨区间清理
- `_rebuild_from_db(...)`：宕机恢复

### 3.4 宕机恢复机制

**场景**：程序重启后，内存缓存为空

**恢复流程**：
1. 第一笔数据写入，缓存未命中
2. 自动查询数据库：统计本区间内该代码已出现次数
3. 重建缓存，后续写入正常

**SQL重建查询**：
```sql
SELECT COUNT(*) FROM {table} 
WHERE code = '{code}' 
AND time >= '{window_start}' 
AND time < '{current_time}'
```

## 八、性能分析

### 8.1 时间复杂度

| 操作 | 复杂度 | 说明 |
|------|--------|------|
| 内存缓存读取 | O(1) | 哈希表查找 |
| 内存缓存写入 | O(1) | 哈希表更新 |
| 跨区间清理 | O(n) | n为上一区间代码数，通常<100 |
| 宕机恢复查询 | O(1) | 单次COUNT查询 |

### 8.2 空间复杂度

- 每个区间最多存储30只票 × 4个区间/小时 = 120条记录
- 每条记录：key(约30字节) + value(4字节) ≈ 34字节
- 总内存占用：< 5KB

## 九、风险评估

### 9.1 潜在风险

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 内存缓存丢失 | 宕机后第一笔数据可能从0开始 | 数据库重建机制 |
| 数据库字段不存在 | 查询报错 | try-except兼容处理 |
| 跨区间瞬间不一致 | 09:45:00时刻数据跳变 | 业务上可接受，符合预期 |

### 9.2 回滚方案

1. **数据库**：`ALTER TABLE DROP COLUMN window_count`
2. **代码**：删除`window_count_cache.py`，移除兼容代码块
3. **前端**：删除表头和数据行相关代码
